Question 1

Basic Inheritance Syntax

Which of the following correctly declares a class Dog that inherits from class Animal?

  1. class Dog extends Animal { };
  2. class Dog : Animal { };
  3. class Dog : public Animal { };
  4. class Dog inherits Animal { };

Answer: C - class Dog : public Animal { };

Why C is correct:

C++ uses a colon (:) followed by an access specifier (public, protected, or private) and the base class name. Public inheritance is the most common and preserves the access levels of inherited members.

Why other options are wrong:

  • A: Incorrect - extends is Java syntax, not C++.
  • B: Incorrect - Missing the access specifier. Without it, the default is private inheritance, which is rarely what you want. Always be explicit with public.
  • D: Incorrect - inherits is not valid C++ syntax.
Question 2

What Gets Inherited?

Which of the following is NOT inherited by a derived class?

  1. Public member functions
  2. Protected member variables
  3. Constructors
  4. Private member variables

Answer: C - Constructors

Why C is correct:

Constructors are NOT inherited. Each class must define its own constructors because a derived class has additional members that the base class constructor doesn't know about. The derived class constructor must call a base class constructor explicitly via the initializer list.

Why other options are wrong:

  • A: Incorrect - Public member functions ARE inherited and become public members of the derived class.
  • B: Incorrect - Protected member variables ARE inherited. They're accessible from the derived class but not from outside the hierarchy.
  • D: Incorrect - Private member variables ARE inherited (they exist in the derived object), but they're not accessible from derived class member functions. The derived class must use public/protected accessors to work with them.
Question 3

Protected Access Specifier

What is the key difference between private and protected members?

  1. Protected members can be accessed from main(), private members cannot
  2. Protected members can be accessed by derived classes, private members cannot
  3. Protected members are faster to access than private members
  4. Protected members can only be used with inheritance, private members cannot

Answer: B - Protected members can be accessed by derived classes, private members cannot

Why B is correct:

The protected access specifier creates a "middle ground." Protected members are accessible from within the defining class AND from derived classes, but NOT from outside code (like main()). Private members are only accessible from within the defining class itself.

Why other options are wrong:

  • A: Incorrect - Protected members are NOT accessible from main() or any other external code. They're still hidden from the outside world, just like private members.
  • C: Incorrect - Access specifiers don't affect performance. They're compile-time checks. At runtime, all member access has the same performance.
  • D: Incorrect - Private members work exactly the same whether or not inheritance is used. Protected is specifically designed for inheritance hierarchies.
Question 4

Constructor Execution Order

When a derived class object is created, in what order are constructors executed?

  1. Derived class constructor, then base class constructor
  2. Base class constructor, then derived class constructor
  3. They execute simultaneously
  4. The order depends on the initializer list

Answer: B - Base class constructor, then derived class constructor

Why B is correct:

The base class constructor ALWAYS runs first. This makes sense: you need to build the foundation (base class part) before you can build the specialized parts (derived class members) on top of it. The base class constructor is called automatically (or explicitly via the initializer list) before the derived class constructor body runs.

Why other options are wrong:

  • A: Incorrect - This is backwards. If the derived constructor ran first, it might try to use base class members that haven't been initialized yet.
  • C: Incorrect - Constructors execute sequentially, not simultaneously.
  • D: Incorrect - The order is always base-then-derived, regardless of how the initializer list is written. The initializer list controls WHICH base constructor is called, not WHEN it's called.
Question 5

Destructor Execution Order

When a derived class object is destroyed, in what order are destructors executed?

  1. Base class destructor, then derived class destructor
  2. Derived class destructor, then base class destructor
  3. Only the derived class destructor is called
  4. The programmer must explicitly call both destructors

Answer: B - Derived class destructor, then base class destructor

Why B is correct:

Destructors run in REVERSE order of construction. The derived class destructor runs first to clean up derived class members, then the base class destructor runs automatically to clean up base class members. This is the opposite of constructor order and ensures proper cleanup.

Why other options are wrong:

  • A: Incorrect - This is backwards. You must tear down the derived parts before tearing down the base parts they depend on.
  • C: Incorrect - The base class destructor IS called automatically after the derived class destructor finishes.
  • D: Incorrect - The base class destructor is called automatically. You never explicitly call destructors in C++ (except in very advanced cases with placement new).
Question 6

Calling Base Constructor

How do you call a base class constructor from a derived class constructor?

  1. In the constructor body: Base(args);
  2. Before the constructor: Base(args); Derived() { }
  3. In the initializer list: Derived() : Base(args) { }
  4. Using super(args); in the constructor body

Answer: C - In the initializer list: Derived() : Base(args) { }

Why C is correct:

The member initializer list (the part after the : and before the {) is where you call the base class constructor. The syntax is : Base(arguments). This ensures the base class is constructed before the derived class constructor body runs.

Why other options are wrong:

  • A: Incorrect - Calling Base(args); in the constructor body would create a temporary Base object and immediately destroy it. It wouldn't initialize the base class part of your derived object.
  • B: Incorrect - Invalid syntax. You can't have code before the constructor definition.
  • D: Incorrect - super is Java/Python syntax, not C++. C++ uses the actual base class name.
Question 7

Function Redefinition vs Overloading

What is the difference between function redefinition and function overloading in inheritance?

  1. Redefinition changes the signature, overloading keeps it the same
  2. Redefinition keeps the signature the same, overloading changes it
  3. They are the same thing
  4. Redefinition is for constructors, overloading is for other functions

Answer: B - Redefinition keeps the signature the same, overloading changes it

Why B is correct:

Redefinition: A derived class function with the SAME signature (name, parameters, const-ness) as a base class function. It replaces the base version for derived objects.

Overloading: Functions with the same name but DIFFERENT signatures. Both versions co-exist and can be called based on arguments.

Why other options are wrong:

  • A: Incorrect - This is backwards. Redefinition requires matching signatures exactly.
  • C: Incorrect - They're different concepts with different purposes.
  • D: Incorrect - Redefinition and overloading apply to all member functions, not just constructors.
Question 8

"Is-A" Relationship

Which of the following demonstrates a proper "is-a" relationship suitable for inheritance?

  1. A Car has an Engine (Car inherits from Engine)
  2. A Student is a Person (Student inherits from Person)
  3. A House has Rooms (House inherits from Room)
  4. A Computer uses a Keyboard (Computer inherits from Keyboard)

Answer: B - A Student is a Person (Student inherits from Person)

Why B is correct:

This demonstrates the "is-a" relationship correctly. A Student IS A Person (with additional student-specific attributes like student ID, major, GPA). Inheritance should model this kind of specialization relationship.

Why other options are wrong:

  • A: Incorrect - This is a "has-a" relationship (composition). A Car HAS an Engine but is NOT an Engine. The Car class should contain an Engine member variable, not inherit from it.
  • C: Incorrect - Also "has-a." A House HAS Rooms but is NOT a Room. Use composition (array or vector of Room objects).
  • D: Incorrect - "Uses-a" relationship. A Computer USES a Keyboard but is NOT a Keyboard. This could be modeled with composition or association, not inheritance.
Question 9

Copy Constructor in Derived Classes

How should a derived class copy constructor call the base class copy constructor?

  1. Derived(const Derived& other) { Base(other); }
  2. Derived(const Derived& other) : Base::Base(other) { }
  3. Derived(const Derived& other) : Base(other) { }
  4. The base copy constructor is called automatically

Answer: C - Derived(const Derived& other) : Base(other) { }

Why C is correct:

In the initializer list, call Base(other). The compiler knows that other is a Derived object, which IS ALSO a Base object, so it correctly calls the Base copy constructor. This ensures all base class members are properly copied.

Why other options are wrong:

  • A: Incorrect - Calling Base(other); in the constructor body creates and destroys a temporary object. It doesn't initialize the base part of your derived object.
  • B: Incorrect - Invalid syntax. You don't use the :: scope resolution operator when calling constructors in initializer lists.
  • D: Incorrect - If you don't explicitly call a base constructor, C++ calls the base class DEFAULT constructor, not the copy constructor. Your base class members won't be copied.
Question 10

Access to Private Base Members

Can a derived class directly access private members of its base class?

  1. Yes, derived classes can access all inherited members
  2. No, derived classes must use public accessor functions
  3. Only if the derived class is declared as a friend
  4. Yes, but only in the derived class constructor

Answer: B - No, derived classes must use public accessor functions

Why B is correct:

Private members are inherited but NOT directly accessible from derived classes. This maintains encapsulation. The derived class must use the public or protected interface provided by the base class. If you need derived class access, make members protected instead of private.

Why other options are wrong:

  • A: Incorrect - Common misconception. Derived classes inherit private members (they exist in the object) but cannot access them directly.
  • C: Incorrect - The friend mechanism doesn't work this way. You can declare specific functions or classes as friends, but all derived classes don't automatically become friends.
  • D: Incorrect - The constructor has no special access privileges. Private is private, regardless of where you try to access it from within the derived class.
Question 11

Constructor Order Tracing

What is the output of the following code?

class Base {
public:
    Base() { cout << "B"; }
};

class Derived : public Base {
public:
    Derived() { cout << "D"; }
};

int main() {
    Derived d;
    return 0;
}

Output:

BD

Line-by-Line Trace:

  1. Line 11: Create Derived d;
  2. Derived constructor starts: Before the body runs, Base constructor is called automatically
  3. Base constructor: Prints "B"
  4. Base constructor completes
  5. Derived constructor body: Prints "D"
  6. Result: "BD"

Key Concept: Base class constructor ALWAYS runs before derived class constructor body, even if you don't explicitly call it.

Question 12

Destructor Order Tracing

What is the output of the following code?

class Base {
public:
    Base() { cout << "B"; }
    ~Base() { cout << "~B"; }
};

class Derived : public Base {
public:
    Derived() { cout << "D"; }
    ~Derived() { cout << "~D"; }
};

int main() {
    Derived d;
    return 0;
}

Output:

BD~D~B

Line-by-Line Trace:

  1. Construction: Base constructor prints "B", then Derived constructor prints "D" → "BD"
  2. Object d goes out of scope at end of main()
  3. Derived destructor runs first: Prints "~D" → "BD~D"
  4. Base destructor runs automatically: Prints "~B" → "BD~D~B"

Key Concept: Destruction happens in REVERSE order of construction. Derived destructor runs, THEN base destructor runs automatically.

Question 13

Function Redefinition Tracing

What is the output of the following code?

class Animal {
public:
    void speak() { cout << "Animal sound"; }
};

class Dog : public Animal {
public:
    void speak() { cout << "Woof"; }
};

int main() {
    Dog d;
    d.speak();
    return 0;
}

Output:

Woof

Explanation:

Dog redefines the speak() function. When you call d.speak() on a Dog object, the derived class version is called. The base class version is "hidden" for Dog objects.

Key Concept: Function redefinition provides specialized behavior in derived classes. The derived class version is called when the function is invoked on a derived object.

Question 14

Protected Member Access

Will this code compile? If yes, what's the output?

class Base {
protected:
    int value;
public:
    Base(int v) : value(v) {}
};

class Derived : public Base {
public:
    Derived(int v) : Base(v) {}
    void print() { cout << value; }
};

int main() {
    Derived d(42);
    d.print();
    return 0;
}

Answer: Yes, it compiles. Output is 42

Explanation:

  1. value is protected in Base, so Derived can access it directly
  2. Derived constructor calls Base(v), which sets value = 42
  3. print() accesses value directly (legal because it's protected)
  4. Outputs: 42

Key Concept: Protected members are accessible from derived classes. If value were private, this code would NOT compile.

Question 15

Multiple Derived Objects

What is the output?

class Counter {
public:
    Counter() { cout << "C"; }
    ~Counter() { cout << "~C"; }
};

int main() {
    Counter c1;
    Counter c2;
    return 0;
}

Output:

CC~C~C

Line-by-Line Trace:

  1. Line 7: Create c1, constructor prints "C" → "C"
  2. Line 8: Create c2, constructor prints "C" → "CC"
  3. End of main(): Local variables destroyed in REVERSE order of creation
  4. c2 destroyed first: Prints "~C" → "CC~C"
  5. c1 destroyed second: Prints "~C" → "CC~C~C"

Key Concept: Objects are destroyed in reverse order of creation (stack order: last in, first out).

Question 16

Calling Base Class Function

What is the output?

class Base {
public:
    void show() { cout << "Base"; }
};

class Derived : public Base {
public:
    void show() {
        Base::show();
        cout << "Derived";
    }
};

int main() {
    Derived d;
    d.show();
    return 0;
}

Output:

BaseDerived

Explanation:

  1. Call d.show() → calls Derived version
  2. Inside Derived::show(), Base::show() explicitly calls base version
  3. Base::show() prints "Base"
  4. Returns to Derived::show(), which prints "Derived"
  5. Result: "BaseDerived"

Key Concept: Use Base::functionName() to explicitly call the base class version of a redefined function.

Question 18

Complex Constructor Chain

What is the output?

class A {
public:
    A() { cout << "A"; }
};

class B : public A {
public:
    B() { cout << "B"; }
};

class C : public B {
public:
    C() { cout << "C"; }
};

int main() {
    C obj;
    return 0;
}

Output:

ABC

Explanation:

Multi-level inheritance: C inherits from B, which inherits from A.

  1. Creating C object triggers chain of constructor calls
  2. A constructor runs first: Prints "A"
  3. B constructor runs second: Prints "B"
  4. C constructor runs third: Prints "C"
  5. Result: "ABC"

Key Concept: In multi-level inheritance, constructors execute from the top of the hierarchy down. Destructors would execute in reverse: C, B, A.

Question 19

Find the Bug #1

This code won't compile. What's wrong?

class Base {
public:
    Base(int x) : value(x) {}
private:
    int value;
};

class Derived : public Base {
public:
    Derived(int x) {
        value = x;
    }
};

Bugs Found:

Bug #1: Derived constructor doesn't call Base constructor

The Derived constructor doesn't call a Base constructor. The compiler tries to call a default Base constructor (with no parameters), but Base only has a constructor that requires an int parameter.

Fix: Derived(int x) : Base(x) { }

Bug #2: Trying to access private member

Even if we fixed bug #1, value = x; is illegal because value is private in Base. Derived classes cannot access private base members.

Fix: Remove the assignment (it's unnecessary if we call Base(x))

Corrected Code:

class Derived : public Base {
public:
    Derived(int x) : Base(x) { }
};
Question 20

Find the Bug #2

What's wrong with this code?

class Animal {
protected:
    string name;
public:
    Animal(string n) : name(n) {}
};

class Dog : public Animal {
public:
    void setName(string n) {
        name = n;
    }
};

int main() {
    Dog d;
    d.setName("Buddy");
    return 0;
}

Bug: Dog constructor doesn't call Animal constructor

Problem:

When you create Dog d; in main(), the Dog default constructor is called. Since there's no explicit Dog constructor, C++ generates a default one. This default constructor tries to call Animal's default constructor, but Animal ONLY has a constructor that takes a string parameter.

Fix: Add a Dog constructor that calls Animal constructor

class Dog : public Animal {
public:
    Dog(string n) : Animal(n) { }

    void setName(string n) {
        name = n;
    }
};

Then in main(): Dog d("Buddy");

Or provide a default Animal constructor:

class Animal {
protected:
    string name;
public:
    Animal() : name("") { }  // Default constructor
    Animal(string n) : name(n) { }
};
Question 21

Find the Bug #3

What's the error in this copy constructor?

class Base {
public:
    Base(int v) : value(v) {}
    Base(const Base& other) : value(other.value) {}
protected:
    int value;
};

class Derived : public Base {
public:
    Derived(int v, double d) : Base(v), data(d) {}

    Derived(const Derived& other) {
        data = other.data;
    }

private:
    double data;
};

Bug: Derived copy constructor doesn't call Base copy constructor

Problem:

The Derived copy constructor doesn't call any Base constructor in its initializer list. C++ will try to call the default Base constructor, but Base doesn't have one. Additionally, even if it compiled, the base class value member wouldn't be copied.

Fix:

Derived(const Derived& other)
    : Base(other), data(other.data) { }

Explanation:

Calling Base(other) in the initializer list invokes the Base copy constructor, which properly copies the value member. The compiler knows that other is a Derived object, which IS ALSO a Base object, so it calls the appropriate constructor.

Question 22

Find the Bug #4

What's wrong with this protected usage?

class Account {
protected:
    double balance;
public:
    Account(double b) : balance(b) {}
};

class SavingsAccount : public Account {
public:
    SavingsAccount(double b) : Account(b) {}
};

int main() {
    SavingsAccount sa(1000.0);
    sa.balance += 500.0;
    return 0;
}

Bug: Accessing protected member from main()

Problem:

In main(), the code tries to access sa.balance directly. Even though balance is protected, that only means derived classes can access it. Code outside the class hierarchy (like main()) CANNOT access protected members.

Fix: Add a public function to modify balance

class Account {
protected:
    double balance;
public:
    Account(double b) : balance(b) {}
    void deposit(double amount) { balance += amount; }
};

int main() {
    SavingsAccount sa(1000.0);
    sa.deposit(500.0);  // Use public interface
    return 0;
}

Key Lesson: Protected members are only accessible from within the class and its derived classes, NOT from external code.

Question 23

Find the Bug #5

Why won't this function redefinition work as expected?

class Shape {
public:
    void draw() const {
        cout << "Drawing shape";
    }
};

class Circle : public Shape {
public:
    void draw() {
        cout << "Drawing circle";
    }
};

int main() {
    Circle c;
    c.draw();
    return 0;
}

Bug: Signature mismatch - const vs non-const

Problem:

This code WILL compile and run, but it's not actually redefinition - it's accidental overloading! The base class draw() is const, but the derived class draw() is NOT const. These are different signatures, so both functions exist.

Impact:

For regular Circle objects, the non-const version is called (as in main()). But if you have a const Circle object, it can only call the const version (inherited from Shape), which prints "Drawing shape" instead of "Drawing circle."

Fix: Match the const-ness

class Circle : public Shape {
public:
    void draw() const {  // Add const to match base signature
        cout << "Drawing circle";
    }
};

Key Lesson: For true redefinition, the signature must match EXACTLY: name, parameters, AND const-ness.

Question 24

True or False

Statement: When a derived class object is created, the base class constructor is called before the derived class constructor body executes.

True or False? Justify your answer.

Answer: TRUE

Justification:

This is absolutely true. The base class constructor ALWAYS executes before the derived class constructor body. This ensures that the base class part of the object is fully constructed before the derived class tries to add its own members. If you don't explicitly call a base constructor via the initializer list, C++ automatically calls the base class default constructor.

Example:

class Base {
public:
    Base() { cout << "Base"; }
};

class Derived : public Base {
public:
    Derived() { cout << "Derived"; }
};

Derived d;  // Prints: "BaseDerived"
Question 25

True or False

Statement: A derived class inherits the base class destructor.

True or False? Justify your answer.

Answer: FALSE

Justification:

Destructors are NOT inherited. Each class must have its own destructor (either user-defined or compiler-generated). However, when a derived class object is destroyed, its destructor runs first, THEN the base class destructor is automatically called. You don't (and shouldn't) explicitly call the base destructor - C++ handles it automatically.

Why this makes sense:

The derived class might allocate its own resources that need cleanup. The base class destructor doesn't know about these resources. So each class handles its own cleanup, and C++ chains the destructors automatically.

Question 26

True or False

Statement: Protected members can be accessed from any function that has a pointer or reference to the derived class.

True or False? Justify your answer.

Answer: FALSE

Justification:

This is false. Protected members are ONLY accessible from:

  • Member functions of the class itself
  • Member functions of derived classes

They are NOT accessible from outside the class hierarchy, even if you have a pointer or reference to the object.

Example:

class Base {
protected:
    int value;
};

void someFunction(Base* ptr) {
    ptr->value = 10;  // ERROR! Can't access protected member
}

class Derived : public Base {
    void memberFunc() {
        value = 10;  // OK! Accessing from derived class
    }
};
Question 27

True or False

Statement: If a base class has no default constructor, you must explicitly call a base class constructor in the derived class constructor's initializer list.

True or False? Justify your answer.

Answer: TRUE

Justification:

If you don't explicitly call a base constructor in the initializer list, C++ tries to call the base class's default constructor (the one with no parameters) automatically. If the base class doesn't have a default constructor, you'll get a compilation error.

Example:

class Base {
public:
    Base(int x) : value(x) {}  // No default constructor!
private:
    int value;
};

class Derived : public Base {
public:
    Derived() { }  // ERROR! Tries to call Base(), which doesn't exist
};

// CORRECT:
class Derived : public Base {
public:
    Derived() : Base(0) { }  // Explicitly call Base(int)
};

Key Rule: Always explicitly call the base constructor you want to use in the derived class initializer list.

Question 28

Implementation Challenge

Task: Implement a simple class hierarchy.

Create a Person base class and a Student derived class with the following specifications:

Person class:

  • Protected members: name (string), age (int)
  • Constructor: Person(string n, int a)
  • Function: void displayInfo() const - prints name and age

Student class (inherits from Person):

  • Private member: studentID (string)
  • Constructor: Student(string n, int a, string id)
  • Redefine: void displayInfo() const - prints name, age, and student ID

Test in main():

  • Create a Student: Student s("Lindiwe Khumalo", 20, "STU2025001");
  • Call s.displayInfo();

Complete Implementation:

#include <iostream>
#include <string>
using namespace std;

class Person {
public:
    Person(string n, int a) : name(n), age(a) {
        cout << "Person constructor called" << endl;
    }

    void displayInfo() const {
        cout << "Name: " << name << endl;
        cout << "Age: " << age << endl;
    }

protected:
    string name;
    int age;
};

class Student : public Person {
public:
    Student(string n, int a, string id)
        : Person(n, a), studentID(id) {
        cout << "Student constructor called" << endl;
    }

    void displayInfo() const {
        cout << "=== Student Information ===" << endl;
        Person::displayInfo();  // Call base version
        cout << "Student ID: " << studentID << endl;
    }

private:
    string studentID;
};

int main() {
    Student s("Lindiwe Khumalo", 20, "STU2025001");
    cout << endl;
    s.displayInfo();

    return 0;
}

Expected Output:

Person constructor called
Student constructor called

=== Student Information ===
Name: Lindiwe Khumalo
Age: 20
Student ID: STU2025001

Key Points:

  • Student constructor calls Person(n, a) in initializer list
  • name and age are protected so Student can access them
  • Student::displayInfo() calls Person::displayInfo() to avoid code duplication
  • Constructor messages show base constructor runs before derived constructor
