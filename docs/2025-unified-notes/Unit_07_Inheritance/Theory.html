Welcome to Inheritance

You've written classes. You've mastered constructors, destructors, and operator overloading. Now we're going to supercharge your classes with one of the most important features in object-oriented programming: inheritance.

Inheritance lets you create new classes based on existing ones. Instead of copying and pasting code between similar classes, you can say "this new class is just like that existing class, but with a few extras." This is code reuse at its finest.

Prerequisites

Before you start this unit, make sure you're comfortable with:

  • Classes and objects (member variables and functions)
  • Access specifiers (public and private)
  • Constructors (default, parameterized, and the member initializer list)
  • Destructors and memory management
  • The this pointer

If any of these feel shaky, go back to Units 3-4 and review. Inheritance builds directly on these fundamentals.

1. What is Inheritance?

Inheritance is the mechanism by which a new class (the derived class or child class) is created from an existing class (the base class or parent class). The derived class automatically gets all the members of the base class and can add its own.

The "Is-A" Relationship

Inheritance models what we call an "is-a" relationship:

  • An HourlyEmployee is an Employee
  • A Car is a Vehicle
  • A Circle is a Shape
  • A CheckingAccount is an Account

When you can say "X is a Y," you've found a good candidate for inheritance. The derived class is a more specific version of the base class.

Why Do We Need This?

Suppose you're building a payroll system. You have two types of employees:

  • Hourly employees: Paid based on hours worked and an hourly wage rate
  • Salaried employees: Paid a fixed salary each pay period

Both types have a name and a social security number. Without inheritance, you'd write: 

class HourlyEmployee {
private:
    string name;       // Duplicate code
    string ssn;        // Duplicate code
    double wageRate;
    double hours;
};

class SalariedEmployee {
private:
    string name;       // Duplicate code again!
    string ssn;        // Duplicate code again!
    double salary;
};

Notice the duplication? You're writing the same code for name and ssn twice. If you need to change how names work, you have to change it in multiple places. This is error-prone and wastes time.

Inheritance solves this by letting us create a general Employee class with the common features. Then both HourlyEmployee and SalariedEmployee can inherit from Employee and just add their specific features: 

class Employee {
protected:
    string name;
    string ssn;
public:
    // Common functions for all employees
};

class HourlyEmployee : public Employee {
    // Inherits name and ssn, adds:
private:
    double wageRate;
    double hours;
};

class SalariedEmployee : public Employee {
    // Inherits name and ssn, adds:
private:
    double salary;
};
Benefits of Inheritance:
  • Code reuse: Write common code once in the base class
  • Easier maintenance: Fix a bug in one place, not many
  • Logical organization: Clear hierarchy of relationships
  • Extensibility: Easy to add new derived types later

Basic Syntax

To create a derived class, use a colon (:) followed by public and the base class name: 

// Define the base class
class BaseClassName {
    // ... members ...
};

// Define a derived class
class DerivedClassName : public BaseClassName {
    // ... new members for the derived class ...
};

The public keyword before the base class name means we're using public inheritance. This is the most common type and is what we'll use throughout this unit. It preserves the access levels of inherited members. 

Class Hierarchy Example:

           +------------------+
           |    Employee      |
           |------------------|
           | - name: string   |
           | - ssn: string    |
           +------------------+
                   ^
                   |
         +---------+---------+
         |                   |
+-------------------+  +---------------------+
| HourlyEmployee    |  | SalariedEmployee    |
|-------------------|  |---------------------|
| - wageRate: double|  | - salary: double    |
| - hours: double   |  +---------------------+
+-------------------+
Key Concept: An object of a derived class contains all the members of the base class plus its own members. When you create an HourlyEmployee object, it has name, ssn, wageRate, and hours.
⚡ Swift Quiz
Quick Check: If you have a Car class that inherits from a Vehicle class, which is the base class and which is the derived class?
Answer: Vehicle is the base class (parent), and Car is the derived class (child). A Car is a Vehicle, so it inherits from Vehicle and adds car-specific features.

2. What Does a Derived Class Inherit?

When you create a derived class, it inherits:

  • All member variables from the base class (both public and private)
  • All member functions from the base class (both public and private)

However, there's a critical distinction between inheriting something and being able to access it.

Access Rules for Inherited Members

Just because a derived class inherits something doesn't mean it can access it directly:

  • public members of the base class → accessible from derived class
  • private members of the base class → inherited but not directly accessible from derived class

This is where many students get confused. Let's look at an example: 

class Employee {
public:
    string getName() const { return name; }
    void setName(string n) { name = n; }
private:
    string name;  // Private member
};

class HourlyEmployee : public Employee {
public:
    void printInfo() {
        // cout << name;  // ERROR! name is private in Employee
        cout << getName(); // CORRECT! Use the public function
    }
};

Why does this restriction exist? Encapsulation. The base class's private members are an implementation detail. If derived classes could access them directly, any change to those private members would break all derived classes. By forcing derived classes to use the public interface, we maintain flexibility.

Common Mistake: Trying to access private base class members directly from a derived class. This code won't compile: 
class Derived : public Base {
public:
    void badFunction() {
        cout << basePrivateMember;  // ERROR: Can't access private members!
    }
};
Solution: Use public accessor functions from the base class.

What Is NOT Inherited?

There are a few things that are not inherited by derived classes:

  • Constructors: Each class must define its own constructors
  • Destructors: Each class must define its own destructor (if needed)
  • Assignment operator: Each class must define its own if needed

Why? Because these special functions need to handle class-specific initialization and cleanup. A derived class has additional members that the base class doesn't know about, so it needs its own constructor to initialize them.

⚡ Swift Quiz
Quick Check: An HourlyEmployee object inherits a private member variable name from the Employee base class. Can an HourlyEmployee member function access name directly?
Answer: No. private members are inherited but not directly accessible from derived classes. The HourlyEmployee member function must use public getter/setter functions (like getName()) to access name.

3. The protected Access Specifier

We've seen public (accessible everywhere) and private (accessible only within the class). Now meet protected: the middle ground.

What is protected?

protected members are:

  • Accessible from within the base class (like private)
  • Accessible from within any derived class (unlike private)
  • Not accessible from outside the class hierarchy (like private)

In other words, protected says "this is for family only" - the base class and all its children can access it, but outsiders cannot.

Access Specifier Summary Table

+------------+----------------------+------------------------+
| Specifier  | Accessible from      | Accessible from        |
|            | same class?          | derived class?         |
+------------+----------------------+------------------------+
| public     | Yes                  | Yes                    |
| protected  | Yes                  | Yes                    |
| private    | Yes                  | No                     |
+------------+----------------------+------------------------+

+------------+------------------------+
| Specifier  | Accessible from        |
|            | main() or elsewhere?   |
+------------+------------------------+
| public     | Yes                    |
| protected  | No                     |
| private    | No                     |
+------------+------------------------+

When Should You Use protected?

Use protected when you want derived classes to have direct access to a member, but you still want to hide it from the general public. 

class Employee {
public:
    Employee(string n, string s) : name(n), ssn(s) {}
    string getName() const { return name; }

protected:
    // Derived classes can access these directly
    string name;
    string ssn;
};

class HourlyEmployee : public Employee {
public:
    HourlyEmployee(string n, string s, double rate)
        : Employee(n, s), wageRate(rate) {}

    void printCheck() const {
        // Can access name directly because it's protected
        cout << "Pay to: " << name << endl;
        cout << "SSN: " << ssn << endl;
    }

private:
    double wageRate;
};
Swift Note: While protected can be convenient, many programmers prefer to keep all data members private and provide protected accessor functions instead. This maintains better encapsulation - if you change the data representation in the base class, derived classes that use accessor functions won't break.
Important: Even though protected members are accessible from derived classes, they're still not accessible from main() or any other outside code. This is good - it maintains encapsulation while giving derived classes flexibility.
⚡ Swift Quiz
Quick Check: If a base class has a protected member variable, can you access it from main()?
Answer: No. protected members are only accessible from within the class itself and its derived classes. They are private to the rest of the world, including main().

4. Constructors in Derived Classes

Constructors are not inherited. Each class must define its own. But here's the challenge: a derived class object contains base class members. How do we initialize them?

Constructor Chaining

When you create a derived class object, C++ automatically calls a base class constructor first, then the derived class constructor. This is called constructor chaining. 

Creating a HourlyEmployee object:

Step 1: Call Employee constructor  ← Initialize name, ssn
Step 2: Call HourlyEmployee constructor  ← Initialize wageRate, hours

The base class part is built first, then the derived part is added.

How to Call the Base Class Constructor

Use the member initializer list to explicitly call the base class constructor: 

class Employee {
public:
    Employee(string n, string s) : name(n), ssn(s) {}
protected:
    string name;
    string ssn;
};

class HourlyEmployee : public Employee {
public:
    // Call Employee constructor via initializer list
    HourlyEmployee(string n, string s, double rate, double hrs)
        : Employee(n, s),    // Call base constructor
          wageRate(rate),    // Initialize own members
          hours(hrs)
    {
        // Constructor body (often empty)
    }

private:
    double wageRate;
    double hours;
};

The syntax is: 

DerivedConstructor(parameters)
    : BaseConstructor(arguments),
      member1(value1),
      member2(value2)
{
    // Constructor body
}

What If You Don't Call the Base Constructor?

If you don't explicitly call a base class constructor, C++ will automatically try to call the base class's default constructor (the one with no parameters). 

class Base {
public:
    Base() { cout << "Base default constructor" << endl; }
};

class Derived : public Base {
public:
    Derived() {
        // Base() is called automatically before this runs
        cout << "Derived constructor" << endl;
    }
};

This is fine if the base class has a default constructor. But if it doesn't, you'll get a compiler error. You must explicitly call a base class constructor in that case.

Common Mistake: Trying to initialize base class members in the derived class constructor body: 
// WRONG!
HourlyEmployee::HourlyEmployee(string n, string s, double rate)
{
    name = n;  // ERROR if name is private!
    ssn = s;   // Can't access private members
    wageRate = rate;
}
Correct Approach: Call the base constructor via the initializer list.

Constructor Execution Order

When a derived class object is created:

  1. Base class constructor executes first
  2. Member variables of the derived class are initialized
  3. Derived class constructor body executes

This order makes sense: you need a complete base object before you can build the derived parts on top of it.

⚡ Swift Quiz
Quick Check: When a Car object is created (where Car inherits from Vehicle), which constructor runs first: Vehicle or Car?
Answer: The Vehicle constructor runs first. The base class must be fully constructed before the derived class can add its parts. This ensures that all inherited members are properly initialized before the derived class constructor runs.

5. Destructors in Derived Classes

Like constructors, destructors are not inherited. But unlike constructors, you rarely need to explicitly call the base class destructor - C++ handles it automatically.

Automatic Destructor Chaining

When a derived class object is destroyed:

  1. Derived class destructor executes first
  2. Base class destructor executes second

This is the opposite order of construction. It makes sense: you need to tear down the derived parts before you can safely tear down the base parts. 

Destroying a HourlyEmployee object:

Step 1: Call ~HourlyEmployee() ← Clean up derived class members
Step 2: Call ~Employee()  ← Clean up base class members (automatic)

The derived part is destroyed first, then the base part.

What Does the Derived Destructor Need to Do?

The derived class destructor only needs to clean up its own members (delete any dynamic memory it allocated, close files it opened, etc.). The base class destructor will automatically handle cleaning up base class members. 

class Employee {
public:
    ~Employee() {
        cout << "Employee destructor called" << endl;
        // Clean up Employee-specific resources
    }
};

class HourlyEmployee : public Employee {
public:
    ~HourlyEmployee() {
        cout << "HourlyEmployee destructor called" << endl;
        // Clean up HourlyEmployee-specific resources
        // NO NEED to call ~Employee() - happens automatically
    }
};

Example with Dynamic Memory

If the derived class allocates dynamic memory, its destructor must free it: 

class Employee {
public:
    Employee() {
        name = new char[50];
    }
    ~Employee() {
        delete[] name;  // Employee cleans up its memory
    }
private:
    char* name;
};

class HourlyEmployee : public Employee {
public:
    HourlyEmployee() {
        timecard = new int[365];
    }
    ~HourlyEmployee() {
        delete[] timecard;  // HourlyEmployee cleans up its memory
        // ~Employee() called automatically next
    }
private:
    int* timecard;
};
Key Rule: Each class is responsible for cleaning up only the resources it allocated. The derived class destructor cleans up derived class resources. The base class destructor (called automatically) cleans up base class resources.
⚡ Swift Quiz
Quick Check: When a derived class object is destroyed, which destructor runs first: the base class's or the derived class's?
Answer: The derived class's destructor runs first. This is the opposite of construction. You must tear down the derived parts before tearing down the base parts. After the derived destructor finishes, C++ automatically calls the base class destructor.

6. Function Redefinition

Sometimes the behavior you inherit from a base class isn't quite right for your derived class. You can provide a new version of an inherited function - this is called function redefinition.

What is Function Redefinition?

When a derived class provides its own implementation of a function that exists in the base class, and the function signatures are identical (same name, same parameters, same const status), that's redefinition. 

class Employee {
public:
    void printCheck() const {
        cout << "Generic employee check" << endl;
    }
};

class HourlyEmployee : public Employee {
public:
    // Redefine printCheck for hourly employees
    void printCheck() const {
        cout << "Hourly employee check" << endl;
        cout << "Pay: $" << (wageRate * hours) << endl;
    }
private:
    double wageRate;
    double hours;
};

When you call printCheck() on an HourlyEmployee object, the derived class version runs. When you call it on an Employee object, the base class version runs.

Redefinition vs Overloading

Don't confuse these two concepts:

  • Overloading: Same name, different parameter lists (signatures differ)
  • Redefinition: Same name, same parameter list (signatures identical)
class Base {
public:
    void func(int x);  // Original function
};

class Derived : public Base {
public:
    void func(int x);      // REDEFINITION (same signature)
    void func(double x);   // OVERLOAD (different parameter)
};
Important: For redefinition, the signatures must match exactly. If they don't match, you've created an overload instead, and both versions will exist. This can lead to unexpected behavior if you thought you were redefining but actually overloaded.

Calling the Base Class Version

Sometimes you want to redefine a function but still use the base class version as part of your implementation. Use the scope resolution operator: 

class HourlyEmployee : public Employee {
public:
    void printCheck() const {
        Employee::printCheck();  // Call base class version first
        cout << "Additional hourly employee info" << endl;
    }
};

7. Common Mistakes to Avoid

Mistake #1: Forgetting to Call the Base Constructor

// WRONG
class HourlyEmployee : public Employee {
public:
    HourlyEmployee(string n, double rate) {
        // name = n;  // ERROR: can't access private members
        wageRate = rate;
    }
};

// CORRECT
class HourlyEmployee : public Employee {
public:
    HourlyEmployee(string n, string s, double rate)
        : Employee(n, s),  // Call base constructor
          wageRate(rate)
    {
    }
};

Mistake #2: Trying to Access Private Base Members

class Base {
private:
    int secret;
};

class Derived : public Base {
public:
    void bad() {
        secret = 10;  // ERROR: secret is private in Base
    }

    void good() {
        // Use public/protected interface instead
    }
};

Mistake #3: Confusing Redefinition with Overloading

class Base {
public:
    void func(int x);
};

class Derived : public Base {
public:
    // Intended to redefine, but accidentally overloaded
    void func(double x);  // Different parameter type!
};

// Now both func(int) and func(double) exist
// Base::func(int) is still inherited

Mistake #4: Not Understanding Constructor Order

// This won't work as expected
class Derived : public Base {
public:
    Derived() {
        // Trying to use base class members before they're initialized
        // But base constructor hasn't run yet in this body!
        // (It runs BEFORE this body, via initializer list)
    }
};

8. Summary

Key Concepts:
  • Inheritance creates an "is-a" relationship between classes
  • Derived classes inherit all members but can only access public/protected ones
  • protected members are accessible to derived classes but not outsiders
  • Constructors: base constructor runs first, use initializer list to call it
  • Destructors: derived destructor runs first, base called automatically
  • Function redefinition: same signature, different implementation
Swift Note: Quick Reference
  • Syntax: class Derived : public Base { };
  • Call base constructor: Derived() : Base(args) { }
  • Access protected members: Use directly in derived class
  • Redefine function: Match signature exactly
  • Call base version: Base::function()
