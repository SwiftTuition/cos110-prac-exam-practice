Example 1: Basic String Container

Basic

Let's create a simple class that stores a string in dynamically allocated memory. This is a straightforward example that shows the Big Three in their simplest form.

Problem Statement

Create a SimpleString class that:

  • Stores a C-style string (char array) dynamically
  • Properly copies strings when objects are copied
  • Cleans up memory when objects are destroyed
  • Handles assignment correctly

Explanation

Step 1: Constructor
Allocates memory for the string plus one extra byte for the null terminator (\0). Uses strcpy to copy the string into the allocated memory.
Step 2: Copy Constructor
Allocates NEW memory (deep copy) and copies the string from the other object. Both objects now have independent memory.
Step 3: Assignment Operator
First checks for self-assignment, then deletes the old memory, allocates new memory, and copies the string. Returns *this for chaining.
Step 4: Destructor
Frees the dynamically allocated memory. Called automatically when objects go out of scope.

Experiments

🔬 Experiment 1: What happens if you remove the + 1 from new char[length + 1]?

What happens: The program might crash or produce garbage output when printing.

Why: C-style strings need a null terminator (\0) at the end. Without the extra byte, strcpy writes past the end of the allocated memory (buffer overflow), causing undefined behavior.

The lesson: When allocating memory for C-style strings, always add 1 for the null terminator.

🔬 Experiment 2: Comment out the destructor. Does the code still work?

What happens: The code runs normally, but you have memory leaks!

Why: Each SimpleString object allocates memory with new, but without a destructor, that memory is never freed. In a long-running program, this exhausts available memory.

The lesson: Always write a destructor when your class uses dynamic memory.

🔬 Experiment 3: In the copy constructor, change data = new char[length + 1]; to data = other.data;. What's wrong?

What happens: You've created a shallow copy! Both objects point to the same string in memory.

Why: data = other.data; copies the pointer (address), not the string itself. When one object is destroyed, it deletes the memory. The other object's pointer becomes dangling.

The lesson: Deep copy means allocating NEW memory and copying VALUES, not addresses.

🔬 Experiment 4: Remove the self-assignment check in the assignment operator. Add str1 = str1; in main. What happens?

What happens: The program crashes or produces garbage.

Why: Without the check, delete[] data; deletes the string that other.data points to (which is the same as this->data in self-assignment). Then strcpy tries to copy from freed memory!

The lesson: Always check for self-assignment in the assignment operator.

🔬 Experiment 5: Change the return type of the assignment operator from SimpleString& to void. Does it still compile?

What happens: The code compiles and runs, but you can't chain assignments.

Why: Returning void means the operator doesn't return anything. Chaining like a = b = c; requires the operator to return a reference to the assigned object.

The lesson: Assignment operator should return ClassName& to enable chaining and match standard C++ behavior.

  • Supports copying Knightmare configurations (each copy gets independent weapons)
  • Handles mass-producing frames with the same loadout via assignment
  • Properly cleans up memory when frames are destroyed

Explanation

This example adds complexity by managing an array of strings (weapons). Each Knightmare Frame has its own independent weapon array.

Key Point 1: Deep Copy in Copy Constructor
When we copy a Knightmare, we allocate a completely new weapons array. This allows mass production - each copy can be modified independently without affecting the original.
Key Point 2: Assignment Preserves Pilot
Notice the assignment operator keeps the original pilot name but copies the weapon loadout. This models "refitting" an existing frame rather than creating a new one.
Key Point 3: Destructor Cleanup
Each frame's destructor deletes its own weapons array. Without this, we'd leak memory for every Knightmare created.

Experiments

🔬 Experiment 1: After copying, modify one of the weapons in massProduced. Does it affect lancelot's weapons?

What happens: No! The weapons are independent. Modifying massProduced doesn't affect lancelot.

Why: The copy constructor does a deep copy, allocating a separate weapons array for massProduced. They're completely independent.

The lesson: Deep copying creates truly independent objects.

🔬 Experiment 2: What if the assignment operator forgot to delete[] weapons; before allocating new memory?

What happens: Memory leak! The old weapons array is never freed.

Why: When you do standardFrame = lancelot;, standardFrame already has a weapons array. If we don't delete it before allocating a new one, we lose the pointer to the old array and can never free it.

The lesson: Always delete old memory in the assignment operator before allocating new memory.

🔬 Experiment 3: Change weaponCount in the original after copying. Does the copy's weapon count change?

What happens: No, the copy's weapon count stays the same.

Why: weaponCount is an integer (not a pointer), so it's copied by value automatically. The copy gets its own independent weaponCount variable.

The lesson: Non-pointer members are automatically copied independently. It's the pointer members that need special handling.

🔬 Experiment 4: What happens if you create a Knightmare with 0 weapons (weaponCount = 0)?

What happens: new string[0] is allowed in C++. It returns a valid pointer (not NULL), but you shouldn't access any elements.

Why: The C++ standard allows zero-size allocations. delete[] on this pointer is safe.

The lesson: Your code should handle edge cases like zero-size arrays gracefully. Consider adding validation to ensure weaponCount > 0.

Explanation

This example shows how return *this; enables method chaining, a powerful pattern for building fluent interfaces.

Method Chaining with this
The recordDefeat and promoteRank methods return Hero& (reference to the current object). This allows you to chain calls: hero.recordDefeat(0).recordDefeat(1).promoteRank(5). Each method modifies the object and returns *this so the next method can be called on it.
Deep Copy of Stats
The defeatCounts array is copied deeply in both the copy constructor and assignment operator. This ensures backup records don't affect the original hero's stats.

Experiments

🔬 Experiment 1: Change return *this; to return this; in recordDefeat. Does it compile?

What happens: Compilation error! The return type is Hero& (reference), but you're trying to return a pointer.

Why: this is a pointer, *this dereferences it to get the object. The return type must match: Hero& needs *this.

The lesson: For method chaining, return *this (the object), not this (the pointer).

🔬 Experiment 2: What if you change the return type from Hero& to Hero (remove the &)?

What happens: The code compiles but is inefficient. Each chained call creates a temporary copy!

Why: Returning Hero (by value) invokes the copy constructor for each call. Returning Hero& (by reference) returns the actual object without copying.

The lesson: For method chaining, always return by reference (ClassName&) to avoid unnecessary copies.

🔬 Experiment 3: Try chaining without returning *this. Make recordDefeat return void.

What happens: You can't chain anymore. saitama.recordDefeat(0).recordDefeat(1) won't compile.

Why: With void return, recordDefeat doesn't return anything. You can't call another method on nothing.

The lesson: Method chaining requires methods to return a reference to the object they're modifying.

🔬 Experiment 4: Add saitama = saitama; in main. Does the self-assignment check prevent problems?

What happens: Yes! The code detects self-assignment and returns immediately without doing anything.

Why: if (this == &other) checks if both pointers point to the same object. If they do, we skip the deletion and copying.

The lesson: Self-assignment checks prevent deleting your own data before trying to copy from it.

Example 4: Find the Bug

Challenge

The following code has bugs in the Big Three implementation. Your job is to find them!

The Code

#include <iostream>
using namespace std;

class Container {
private:
    int* values;
    int size;

public:
    Container(int s) {
        size = s;
        values = new int[size];
        for (int i = 0; i < size; i++) {
            values[i] = i * 10;
        }
    }

    Container(Container& other) {
        size = other.size;
        values = new int[size];
        for (int i = 0; i < size; i++) {
            values[i] = other.values[i];
        }
    }

    Container& operator=(const Container& other) {
        size = other.size;
        values = new int[size];
        for (int i = 0; i < size; i++) {
            values[i] = other.values[i];
        }
        return *this;
    }

    ~Container() {
        delete values;
    }

    void print() {
        cout << "Values: ";
        for (int i = 0; i < size; i++) {
            cout << values[i] << " ";
        }
        cout << endl;
    }
};

int main() {
    Container c1(3);
    c1.print();

    Container c2 = c1;
    c2.print();

    Container c3(2);
    c3 = c1;
    c3.print();

    return 0;
}

Challenge: There are at least 3 bugs in this code. Can you find them all?

Bug 1: Missing const in Copy Constructor

Location: Line 16: Container(Container& other)

What's wrong: The parameter should be const Container& other.

Why it's wrong: Without const, you can't copy from const objects or temporary objects. The copy constructor should not modify the source object.

Fix: Container(const Container& other)

Bug 2: Missing Self-Assignment Check

Location: Line 25: Assignment operator

What's wrong: No check for if (this == &other).

Why it's wrong: If you do c1 = c1;, the code allocates new memory without deleting the old memory first, causing a memory leak. Even worse, the old memory is lost forever since we didn't save the pointer.

Fix: Add at the start: 

if (this == &other) return *this;

Bug 3: Missing delete[] in Assignment Operator

Location: Line 26: Assignment operator

What's wrong: No delete[] values; before allocating new memory.

Why it's wrong: When you assign to an existing object, it already has allocated memory. If you don't delete it before allocating new memory, you leak the old memory.

Fix: Add before allocation: 

delete[] values;

Bug 4: Wrong Delete in Destructor

Location: Line 37: delete values;

What's wrong: Should be delete[] values;

Why it's wrong: values is allocated with new int[size] (array allocation), so it must be freed with delete[]. Using delete (without []) on an array is undefined behavior.

Fix: delete[] values;

Corrected Code

Container(const Container& other) {  // Added const
    size = other.size;
    values = new int[size];
    for (int i = 0; i < size; i++) {
        values[i] = other.values[i];
    }
}

Container& operator=(const Container& other) {
    if (this == &other) return *this;  // Self-assignment check

    delete[] values;  // Delete old memory

    size = other.size;
    values = new int[size];
    for (int i = 0; i < size; i++) {
        values[i] = other.values[i];
    }
    return *this;
}

~Container() {
    delete[] values;  // Use delete[] for arrays
}
Key Lessons:
  • Copy constructor parameter must be const ClassName&
  • Assignment operator must check for self-assignment
  • Assignment operator must delete old memory before allocating new
  • Match new[] with delete[], new with delete

  • Assignment operator: Check self-assignment, delete old, allocate new, return *this
  • Destructor: ~ClassName() - use delete[] for arrays
  • Method chaining: Return ClassName& and return *this;
