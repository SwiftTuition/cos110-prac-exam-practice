Problem 1: Check Balanced Parentheses

Task

Write a function that checks if parentheses, brackets, and braces in a string are balanced. For example:

  • "()" → balanced
  • "()[]{}" → balanced
  • "(]" → not balanced
  • "([)]" → not balanced (wrong nesting order)
  • "{[]}" → balanced

Why This Matters

Compilers use this exact technique to check if your C++ code has matching braces. When you write if (x > 0) { ... }, the compiler uses a stack to verify every opening brace has a matching closing brace.

How It Works - Step by Step

The basic idea: When you see an opening bracket, remember it by pushing onto the stack. When you see a closing bracket, check if it matches the most recent opening bracket (which is at the top of the stack).

Let's trace through "({[]})":

  1. Read '(' → It's an opening bracket, so push it onto the stack. Stack is now: ['(']
  2. Read '{' → It's an opening bracket, push it. Stack is now: ['(', '{']
  3. Read '[' → It's an opening bracket, push it. Stack is now: ['(', '{', '[']
  4. Read ']' → It's a closing bracket. Pop the stack (gives us '['). Check if '[' matches ']' → Yes! Continue. Stack is now: ['(', '{']
  5. Read '}' → It's a closing bracket. Pop the stack (gives us '{'). Check if '{' matches '}' → Yes! Continue. Stack is now: ['(']
  6. Read ')' → It's a closing bracket. Pop the stack (gives us '('). Check if '(' matches ')' → Yes! Continue. Stack is now empty: []
  7. We've read all characters and the stack is empty → The string is balanced!

Why does "([)]" fail?

  1. Read '(' → Push. Stack: ['(']
  2. Read '[' → Push. Stack: ['(', '[']
  3. Read ')' → Pop gives us '['. Does '[' match ')'? NO! Return false immediately.

The problem is that ')' should match with '(', but we have '[' in the way. The nesting is wrong.

Why does "(]" fail?

  1. Read '(' → Push. Stack: ['(']
  2. Read ']' → Pop gives us '('. Does '(' match ']'? NO! Return false.

Edge cases handled:

  • Too many closing brackets: If we see ')' but the stack is empty, there's no matching opening bracket. Return false (lines 68-70).
  • Too many opening brackets: If we finish reading the string but the stack still has items, there are unmatched opening brackets. Return false (line 81).
  • Wrong bracket type: If we pop '[' but see ')', they don't match. Return false (lines 74-76).
Time Complexity: O(n) where n is the length of the string. We visit each character exactly once.
Space Complexity: O(n) in the worst case (all opening brackets like "(((((").

How It Works - Step by Step

Why we need a queue (FIFO): Downloads finish in the order they were queued. The first episode Swift queued (Ep 58) should be the first episode he watches. If we used a stack (LIFO), he'd watch Episode 61 first, then 60, 59, 58 - completely backwards!

Let's trace through the operations:

Initial state: Queue is empty. head = NULL, tail = NULL

After queueDownload(58, "Part 1"):

  • Create a new node with Episode 58
  • Since the queue is empty (head == NULL), this is the first node
  • Set both head and tail to point to this node
  • Queue now looks like: [Ep 58], where head → Ep 58 ← tail

After queueDownload(59, "Part 2"):

  • Create a new node with Episode 59
  • The queue is NOT empty, so we add to the rear
  • Set tail->next to point to the new node (line 45)
  • Move tail to point to the new node (line 46)
  • Queue now looks like: [Ep 58] → [Ep 59], where head → Ep 58 and tail → Ep 59

After queueing all 4 episodes:

  • Queue: [Ep 58] → [Ep 59] → [Ep 60] → [Ep 61]
  • head points to Ep 58 (front)
  • tail points to Ep 61 (rear)

First watchNext() call:

  • Get the episode at head (Ep 58)
  • Save head in a temporary pointer (line 57)
  • Move head forward: head = head->next (line 58)
  • Delete the old head node (line 64)
  • Queue is now: [Ep 59] → [Ep 60] → [Ep 61]
  • head now points to Ep 59

Why check if (head == NULL) on line 60?

If we just removed the LAST node in the queue, head becomes NULL. But tail still points to the old (now deleted) node. We must also set tail = NULL to keep them in sync, otherwise the next queueDownload() will try to access freed memory and crash.

Key takeaway: Queues are perfect for "first-come, first-served" scenarios like download queues, print queues, or any situation where order matters.

What's Wrong?

The Bugs

Bug 1: Memory leak in undo() (line 35)

When we undo an action, we move head to the next node with head = head->next. But we never delete the old node! Each undo leaks memory.

Here's what happens:

  • Before undo: head → [Delete 'd'] → [Type 'World'] → [Type 'Hello'] → NULL
  • After head = head->next: head → [Type 'World'] → [Type 'Hello'] → NULL
  • Problem: The [Delete 'd'] node is still in memory, but we lost the pointer to it! We can never delete it now. It's leaked.

Bug 2: No destructor

When the UndoStack object is destroyed (at the end of main), all the remaining nodes leak. We need a destructor that deletes all nodes.

What We Fixed - Step by Step

Fix 1: Proper deletion in undo() (lines 43-45)

  1. Save the current head in a temporary pointer: Node* temp = head;
  2. Move head forward: head = head->next;
  3. Delete the old node using the temp pointer: delete temp;

We MUST use a temp pointer because if we write delete head first, we lose access to head->next (accessing freed memory is undefined behavior).

Fix 2: Added destructor (lines 19-25)

The destructor loops through all remaining nodes and deletes them one by one. This prevents memory leaks when the UndoStack object is destroyed.

Common mistake: Don't write delete head; head = head->next; - once you delete head, accessing head->next is undefined behavior! Always save head->next in a temp variable BEFORE deleting.

Second playNext() call:

  1. Remove "Amore" from queue
  2. Queue: [Humanisme] → [Esengo]
  3. Add "Amore" to history stack at the head
  4. Stack: sHead → [Amore] → [Eloko Oyo]
  5. historyCount = 2

Third playNext() call:

  1. Remove "Humanisme" from queue
  2. Add "Humanisme" to stack
  3. Stack: sHead → [Humanisme] → [Amore] → [Eloko Oyo]
  4. historyCount = 3 (now at MAX_HISTORY)

Fourth playNext() call (exceeds max history):

  1. Remove "Esengo" from queue
  2. Add "Esengo" to stack at the head
  3. Stack temporarily: [Esengo] → [Humanisme] → [Amore] → [Eloko Oyo]
  4. historyCount = 4, which exceeds MAX_HISTORY (3)

  6. Final stack: [Esengo] → [Humanisme] → [Amore]
  7. historyCount = 3

Why is this useful?

Real music players like Spotify work exactly like this! The "Up Next" queue is a FIFO queue, and the "Recently Played" list is essentially a limited-size stack showing your last few songs in reverse chronological order.
