Welcome to Stacks & Queues

You've already worked with linked lists, which let you build dynamic data structures. Now we're going to look at two specific ways to organize data: stacks and queues.

These are both Abstract Data Types (ADTs), which means they're defined by what they do, not how they're built. You can implement both stacks and queues using arrays or linked lists.

The difference between stacks and queues comes down to how you add and remove items:

  • Stack (LIFO): Last In, First Out - like a stack of plates
  • Queue (FIFO): First In, First Out - like a line at the bank
Prerequisites from Unit 10: You should be comfortable with:
  • Pointers and dynamic memory (new and delete)
  • Linked list nodes (struct with data and next pointer)
  • Inserting and removing nodes
  • Arrays and indexing

Section 1: Introduction to Stacks (LIFO)

What is a Stack?

A stack is a data structure where you can only add or remove items from one end, called the top. Think of it like a stack of plates in a cafeteria: you add plates to the top, and you take plates from the top.

This means the last item you add is the first item you remove. That's why stacks are called LIFO (Last In, First Out).

Stack visualization (LIFO):

    Push 30 →  [30]  ← Pop 30 (most recent)
               [20]
               [10]  ← Bottom (first item added)
               ----
               Top

Stack Operations

Every stack needs these basic operations:

  • push(item): Add an item to the top of the stack
  • pop(): Remove and return the item at the top
  • peek() or top(): Look at the top item without removing it
  • isEmpty(): Check if the stack has any items
  • isFull(): Check if the stack is full (only for array-based stacks)
Swift Note: All stack operations work on the top only. You never access items in the middle or at the bottom. This restriction is what makes stacks useful for specific problems.

Real-World Examples

Stacks are everywhere in programming:

  • Browser back button: Each page you visit goes on a stack. Click back, and you pop the most recent page.
  • Undo feature: Every action you take goes on a stack. Press undo, and you pop the last action.
  • Function calls: When you call a function, the computer pushes the return address onto a stack. When the function finishes, it pops that address to know where to continue.
  • Checking balanced parentheses: As you read characters, push opening brackets onto a stack. When you see a closing bracket, pop and check if it matches.

Time Complexity

Stack operations are extremely fast:

  • push(): O(1) - constant time
  • pop(): O(1) - constant time
  • peek(): O(1) - constant time

Because you only work with the top, you never need to search through the stack.

Section 2: Array-Based Stack Implementation

The simplest way to build a stack is with an array. You use an integer variable called top to track where the top of the stack is.

How It Works

Here's the basic idea:

  • Start with top = -1 (empty stack)
  • To push: increment top, then put the item at arr[top]
  • To pop: get the item at arr[top], then decrement top
Array-based stack with top = 2:

Index:  [0] [1] [2] [3] [4]
Array:  [10][20][30][ ][ ]
                 ↑
                top

Overflow and Underflow

Because arrays have a fixed size, you need to handle two error conditions:

  • Overflow: Trying to push when the stack is full (top == size - 1)
  • Underflow: Trying to pop when the stack is empty (top == -1)
Common Mistake: Forgetting to check if the stack is full before pushing, or empty before popping. Always validate before operations!

⚡ Swift Quiz Checkpoint #1
Question: You have an empty stack with capacity 3. You push 5, push 10, pop, push 15, push 20. What does peek() return?
Answer: 20
Step by step:
  • Push 5: Stack = [5], top = 0
  • Push 10: Stack = [5, 10], top = 1
  • Pop: Remove 10, Stack = [5], top = 0
  • Push 15: Stack = [5, 15], top = 1
  • Push 20: Stack = [5, 15, 20], top = 2
  • Peek returns arr[top] = arr[2] = 20
Remember: LIFO means the last item pushed (20) is at the top!

Section 3: Linked-List-Based Stack Implementation

You can also build a stack using a linked list. This gives you a huge advantage: no fixed size. You can push as many items as you want (until you run out of memory).

How It Works

The key insight: treat the head of the linked list as the top of the stack.

  • Push: Insert a new node at the head (O(1))
  • Pop: Delete the head node and return its value (O(1))
  • Peek: Return the head node's value without deleting it (O(1))
Linked-list stack (head is top):

Push 30:
head → [30|•] → [20|•] → [10|X]
       (top)             (bottom)

Pop:
head → [20|•] → [10|X]
       (top)    (bottom)

No Overflow!

Since linked lists grow dynamically, you don't need to check for overflow. You only need to check for underflow (popping from an empty stack).

Swift Note: Linked-list stacks are better when you don't know the maximum size ahead of time. Array-based stacks are faster (no new/delete overhead) when you know the size.

Memory leak prevention: If you only delete head, you free the first node but lose access to all the other nodes. They stay in memory forever (memory leak).

By calling pop() repeatedly, you delete each node one by one, moving head forward each time. When head becomes NULL, all nodes are freed.

Alternative: You could write a manual loop with delete, but calling pop() reuses code and ensures the same cleanup logic.

⚡ Swift Quiz Checkpoint #2
Question: In a linked-list stack, why do we insert at the head instead of the tail?
Answer: O(1) vs O(n) performance

Inserting at the head is O(1):
  • Create new node
  • Set new node's next to current head
  • Update head to new node
  • Done! Just 3 steps, no loops.
Inserting at the tail is O(n):
  • Start at head
  • Walk through entire list to find the last node
  • Insert after last node
  • Requires looping through all n nodes!
Stack operations must be O(1), so we insert at the head.

Section 4: Introduction to Queues (FIFO)

What is a Queue?

A queue is a data structure where you add items at one end (the rear) and remove items from the other end (the front). Think of it like a line at the bank: people join at the back and leave from the front.

This means the first item you add is the first item you remove. That's why queues are called FIFO (First In, First Out).

Queue visualization (FIFO):

Enqueue →  [10][20][30]  → Dequeue
          front      rear

Add to rear, remove from front

Queue Operations

Every queue needs these basic operations:

  • enqueue(item): Add an item to the rear of the queue
  • dequeue(): Remove and return the item at the front
  • front() or peek(): Look at the front item without removing it
  • isEmpty(): Check if the queue has any items
  • isFull(): Check if the queue is full (only for array-based queues)
Swift Note: Queues are the opposite of stacks. With a stack, the newest item leaves first. With a queue, the oldest item leaves first. This makes queues perfect for "fair" systems.

Real-World Examples

Queues are used for fair ordering and scheduling:

  • Print queue: Documents print in the order they were sent
  • Customer service: Customers are helped in the order they arrived
  • Breadth-first search: Explore nodes level by level in a tree or graph
  • Task scheduling: Operating systems use queues to manage tasks waiting for the CPU

Time Complexity

Like stacks, queue operations are fast:

  • enqueue(): O(1) - constant time
  • dequeue(): O(1) - constant time
  • front(): O(1) - constant time

Section 5: Array-Based Queue (Linear Queue)

The simplest way to build a queue is with an array. You use two integer variables: front (where items leave) and rear (where items enter).

How It Works

Here's the basic idea:

  • Start with front = 0 and rear = -1 (empty queue)
  • To enqueue: increment rear, then put the item at arr[rear]
  • To dequeue: get the item at arr[front], then increment front
Linear queue after some operations:

Index:  [0] [1] [2] [3] [4]
Array:  [ ] [20][30][40][ ]
             ↑       ↑
           front   rear

Problem: Index 0 is wasted space!

The Wasted Space Problem

Linear queues have a serious flaw. After several enqueue/dequeue operations, front moves forward, leaving empty spaces at the beginning of the array. You can't reuse those spaces!

Problem: Even if there's space at the front, once rear reaches the end of the array, the queue appears full. This wastes memory and limits capacity.

We'll solve this problem with circular queues in the next section.

Swift Note: Linear queues are rarely used in practice because of the wasted space problem. They're useful for understanding queue basics before moving to circular queues.

Section 6: Circular Queue Implementation

A circular queue solves the wasted space problem by treating the array as circular. When you reach the end, you wrap around to the beginning using the modulo operator (%).

How It Works

Instead of incrementing indices normally, you use modulo:

  • To enqueue: rear = (rear + 1) % capacity, then put item at arr[rear]
  • To dequeue: get item at arr[front], then front = (front + 1) % capacity
Circular queue wrapping around:

Index:  [0] [1] [2] [3] [4]
Array:  [50][ ] [30][40][   ]
         ↑           ↑
       rear        front

When rear = 4, next enqueue wraps to index 0!

Full vs Empty Detection

There's a tricky problem: when the queue is empty, front == rear. But when the queue is full and wraps around, front == rear again! How do you tell them apart?

Solution 1: Keep a counter of items in the queue

Solution 2: Keep one space empty. The queue is full when (rear + 1) % capacity == front

We'll use Solution 2 because it doesn't require an extra variable.

Experiment: Why do we use capacity = size + 1 in the constructor? What happens if we use capacity = size?

The one-space-empty trick: We keep one space always empty so we can tell the difference between full and empty.

If we used capacity = size exactly:

  • Empty: front == rear
  • Full after wrapping: front == rear again!
  • Can't tell them apart without an extra variable

By using capacity = size + 1:

  • Empty: front == rear
  • Full: (rear + 1) % capacity == front
  • Different conditions! No ambiguity.

The trade-off: We waste one array space, but we avoid needing a counter variable. For a queue of size 5, we allocate an array of size 6 but only use 5 spaces maximum.

⚡ Swift Quiz Checkpoint #3
Question: You have a circular queue with capacity 4 (array size 5). Starting empty, you enqueue 1, 2, 3, dequeue twice, then enqueue 4, 5, 6. What are the values of front and rear?
Answer: front = 2, rear = 1

Step by step (capacity = 5):
  • Start: front = 0, rear = 0 (empty)
  • Enqueue 1: arr[0] = 1, rear = 1
  • Enqueue 2: arr[1] = 2, rear = 2
  • Enqueue 3: arr[2] = 3, rear = 3
  • Dequeue: front = 1 (removed 1)
  • Dequeue: front = 2 (removed 2)
  • Enqueue 4: arr[3] = 4, rear = 4
  • Enqueue 5: arr[4] = 5, rear = (4+1) % 5 = 0 (wraps!)
  • Enqueue 6: arr[0] = 6, rear = (0+1) % 5 = 1
Final: front = 2, rear = 1. Queue contains [3, 4, 5, 6].

Section 7: Linked-List-Based Queue Implementation

You can also build a queue using a linked list. Like the linked-list stack, this gives you dynamic sizing with no fixed capacity.

How It Works

You need to keep track of both ends of the list:

  • head (front): Where you dequeue from
  • tail (rear): Where you enqueue to

Operations:

  • Enqueue: Insert at the tail (O(1) because we keep a tail pointer)
  • Dequeue: Delete from the head (O(1))
Linked-list queue:

head → [10|•] → [20|•] → [30|X] ← tail
      (front)          (rear)

Dequeue from head, enqueue at tail

Why We Need Both Pointers

Without a tail pointer, enqueuing would require walking through the entire list to find the end (O(n)). By keeping tail, we can enqueue in O(1).

Edge Case: When the queue becomes empty after a dequeue, you need to set tail = NULL as well, not just head = NULL. Otherwise tail points to freed memory!

Experiment: In the dequeue() function, why do we check if head == NULL after updating head?

Handling the last element: When you dequeue the last element in the queue, head becomes NULL. But tail still points to the old node (which we just deleted).

If we don't set tail = NULL, the next enqueue will try to access tail->next, which is a dangling pointer pointing to freed memory. This causes a crash or corruption!

By checking if (head == NULL), we know the queue is now empty, so we also set tail = NULL to keep both pointers in sync.

General rule: Whenever you modify head or tail, think about whether the other pointer needs updating too.

⚡ Swift Quiz Checkpoint #4
Question: Why can't we use the linked-list stack approach (insert/delete at head only) for a queue?
Answer: It would break FIFO ordering

Stack approach (head only):
  • Push (insert at head): O(1) ✓
  • Pop (delete from head): O(1) ✓
  • Result: LIFO (last in, first out)
Queue needs FIFO:
  • Enqueue at one end (tail): O(1) ✓
  • Dequeue from other end (head): O(1) ✓
  • Result: FIFO (first in, first out)
If we used head only for both operations, we'd get a stack, not a queue! The first item enqueued would be the last item dequeued, which violates the definition of a queue.

Section 8: Applications of Stacks and Queues

When to Use a Stack (LIFO)

Use a stack when you need to process things in reverse order, or when you need to "undo" operations:

  • Function call stack: When a function calls another function, the return address is pushed onto the stack. When the inner function returns, the address is popped.
  • Undo/Redo: Each action is pushed onto a stack. Undo pops the most recent action.
  • Balanced parentheses: Push opening brackets, pop when you see closing brackets. If they match, the expression is balanced.
  • Depth-First Search (DFS): Explore a tree or graph by going as deep as possible before backtracking.
  • Expression evaluation: Convert infix to postfix, then evaluate using a stack.

When to Use a Queue (FIFO)

Use a queue when you need to process things in the order they arrived, or when you need fair scheduling:

  • Print queue: Documents are printed in the order they were submitted.
  • Breadth-First Search (BFS): Explore a tree or graph level by level.
  • Task scheduling: Operating systems use queues to manage processes waiting for CPU time.
  • Buffering: Streaming video uses a queue to buffer incoming data.
  • Handling requests: Web servers use queues to handle incoming requests in order.
Swift Note: The key question is: "Does order matter, and if so, should I process the newest or the oldest first?" Newest → Stack. Oldest → Queue.

Section 9: Common Mistakes

1. Off-by-One Errors in Array Implementations

Getting the indices wrong is extremely common. Here's a buggy stack implementation:

void push(int value) {
    if (top == capacity) {
        cout << "Overflow!" << endl;
        return;
    }
    arr[top] = value;
    top++;
}

int pop() {
    if (top == -1) {
        cout << "Underflow!" << endl;
        return -1;
    }
    top--;
    return arr[top];
}

Can you spot the bugs? There are two issues in this code.

Bug 1 (line 2): Should be top == capacity - 1. If capacity is 5, valid indices are 0-4, so top can be at most 4.

Bug 2 (line 14): Should return arr[top] BEFORE decrementing top, not after. As written, we decrement first then return, which gives us the wrong element.

2. Forgetting to Update Both Pointers in Linked-List Queue

When dequeuing the last element, you must update both head and tail:

int dequeue() {
    if (isEmpty()) return -1;

    int value = head->data;
    Node* temp = head;
    head = head->next;
    delete temp;
    return value;
}

What's wrong here? This code has a subtle but serious bug.

The bug: When the queue becomes empty (head == NULL), tail still points to the freed node. The next enqueue will crash.

Fix: Add if (head == NULL) tail = NULL; after updating head.

3. Using == Instead of Modulo in Circular Queue

Forgetting to wrap indices causes out-of-bounds errors:

void enqueue(int value) {
    if (isFull()) return;
    arr[rear] = value;
    rear++;
}

What's the problem? This looks reasonable, but has a critical flaw.

The bug: When rear reaches the end of the array, incrementing it goes out of bounds. You must use rear = (rear + 1) % capacity to wrap around.

Why it matters: Without modulo, you'll write past the end of the array, corrupting memory and causing crashes.

4. Confusing Front and Rear

In a queue, items are added at the rear and removed from the front. Don't mix them up!

void enqueue(int value) {
    arr[front] = value;
    front = (front + 1) % capacity;
}

int dequeue() {
    int value = arr[rear];
    rear = (rear + 1) % capacity;
    return value;
}

Try to spot the error: This code compiles and runs, but doesn't behave like a queue.

The bug: This adds to the front and removes from the rear, which is backwards. The result is LIFO (a stack), not FIFO (a queue).

How to remember: Think of a real queue (line at a store). People join at the rear (back of line) and leave from the front.

5. Memory Leaks in Destructors

Forgetting to free all nodes in a linked-list destructor causes memory leaks:

~Stack() {
    delete head;
}

Is this correct? This looks like it cleans up the stack, but it doesn't.

The bug: Deleting head only frees the first node. All other nodes stay in memory forever (memory leak).

Why: When you delete head, you free that node but lose access to head->next. All remaining nodes are unreachable and can't be freed.

Fix: Loop through and delete all nodes, or call pop() until empty.

Debugging Tip: When your stack or queue behaves weirdly, print the values of top/front/rear after each operation. This helps you spot off-by-one errors immediately.
⚡ Swift Quiz Checkpoint #5
Question: What's the time complexity of searching for a specific value in a stack or queue?
Answer: O(n) - linear time

Even though push/pop/enqueue/dequeue are O(1), searching is O(n):
  • You can only access the top of a stack or front of a queue
  • To find a value, you must pop/dequeue items one by one until you find it
  • In the worst case, the value is at the bottom, so you check all n items
This is why stacks and queues are NOT good for searching! If you need fast search, use a different data structure (like a hash table or binary search tree).

Summary

Stacks (LIFO)

  • Last In, First Out - like a stack of plates
  • Operations: push, pop, peek, isEmpty, isFull
  • Array implementation: Use top index, check for overflow/underflow
  • Linked-list implementation: Insert/delete at head, no overflow
  • Use for: Undo, function calls, balanced parentheses, DFS
  • All operations are O(1)

Queues (FIFO)

  • First In, First Out - like a line at the bank
  • Operations: enqueue, dequeue, front, isEmpty, isFull
  • Linear array: Simple but wastes space
  • Circular array: Uses modulo to wrap around, efficient
  • Linked-list implementation: Use head (front) and tail (rear), no overflow
  • Use for: Print queue, BFS, task scheduling, buffering
  • All operations are O(1)

Key Differences

  • Stack: One access point (top), LIFO, process newest first
  • Queue: Two access points (front and rear), FIFO, process oldest first

Common Mistakes to Avoid

  • Off-by-one errors in array indices
  • Forgetting to update tail when dequeuing last element
  • Not using modulo in circular queue
  • Confusing front and rear in queue operations
  • Memory leaks from incomplete destructors
