Which of the following is the correct syntax for declaring a function template?
A
template<class T> void myFunc(T param);
B
template<T> void myFunc(T param);
C
void template<class T> myFunc(T param);
D
template<type T> void myFunc(T param);
Correct Answer: A
Option A is correct because it follows the proper template syntax: template<class T> (or template<typename T>) must come before the function declaration. The keyword class or typename tells the compiler that T is a type parameter.
Why the other options are wrong:
Option B is wrong:
Missing the class or typename keyword. The compiler needs to know that T is a type parameter, not a value. template<T> is invalid syntax and will cause a compilation error.
Option C is wrong:
The template keyword must come BEFORE the function signature, not after the return type. Putting template<class T> in the middle of the function declaration is syntactically incorrect.
Option D is wrong:
type is not a valid keyword in C++. Only class or typename can be used to declare type parameters in templates. Using type will result in a compilation error.

True/False
True or False: The keywords class and typename can be used interchangeably when declaring template parameters.
A
True
B
False
Correct Answer: A (True)
In C++, class and typename are completely interchangeable when declaring template type parameters. Both of these are valid and identical in meaning:
template<class T> // Valid template<typename T> // Also valid, means exactly the same thing
The keyword typename was added later to the C++ standard because class was considered confusing - it made people think the template parameter had to be a class type, when in fact it can be ANY type (including built-in types like int, double, etc.).
Additional context:
Many modern C++ programmers prefer typename because it's more clear about what the parameter represents - a type name, not necessarily a class. However, in older codebases and in many teaching contexts, you'll still see class being used. Both are correct, and the compiler treats them identically.
Why False is wrong:
They are not different or restricted to different contexts when declaring template parameters. In template parameter declarations, they have identical meaning and behavior. There is one specific context where typename MUST be used (accessing dependent type names in templates), but that's not what this question is asking about.

Multiple Choice
When should you implement template functions in header files (.h) rather than source files (.cpp)?
A
Only when the template has multiple type parameters
B
Always - template definitions must be in header files
C
Never - templates should always be in .cpp files
D
Only when the template is used in multiple files
Correct Answer: B
Template definitions MUST be in header files (or in the same file where they're used) because of how templates work. The compiler needs to see the complete template definition at the point where it's instantiated with a specific type. Here's why:
How templates work:
1. Templates are NOT regular functions/classes - they're blueprints
2. When you use maximum<int>(5, 10), the compiler generates a brand new function
3. To generate this code, the compiler needs to see the template definition
4. If the definition is in a .cpp file, the compiler can't access it when compiling other files
5. This would cause linker errors: "undefined reference to template function"
The correct pattern:
// Array.h template<class T> class Array { public: void print() { // Implementation HERE in .h file } };
Why the other options are wrong:
Option A is wrong:
The number of type parameters doesn't matter. Whether you have template<class T> or template<class T, class U>, the definition still needs to be in the header file.
Option C is wrong:
Putting template definitions in .cpp files will cause linker errors. The compiler won't be able to generate the template instances when you try to use them from other files.
Option D is wrong:
Even if you only use the template in one file, it's still best practice to keep the definition in the header. This makes your code more reusable and avoids confusion. The rule is consistent: templates go in headers, period.

Find the Bug
This code has a bug. What's wrong with it?
template<class T> void swap(T a, T b) { T temp = a; a = b; b = temp; } int main() { int x = 5, y = 10; swap(x, y); cout << x << " " << y; // Expecting: 10 5 return 0; }
A
Parameters should be passed by reference: void swap(T& a, T& b)
B
Missing template specification: should call swap<int>(x, y)
C
The temp variable should be int, not T
D
No bug - the code is correct
Correct Answer: A
The bug is that parameters are passed by value instead of by reference. When you pass by value, the function gets COPIES of x and y, not the originals. Let me trace what actually happens:
Current (buggy) behavior:
Before swap: x = 5, y = 10
Function call: swap(x, y) creates copies: a = 5, b = 10
Inside swap:
  • temp = a (temp = 5)
  • a = b (a = 10)
  • b = temp (b = 5)
Function ends: Local variables a, b, and temp are destroyed
After swap: x is STILL 5, y is STILL 10 (originals unchanged!)
Output: 5 10 instead of expected 10 5
Correct implementation:
template<class T> void swap(T& a, T& b) { // Pass by REFERENCE T temp = a; a = b; b = temp; }
Now a and b are references (aliases) to the original x and y, so modifying them modifies the originals.
Why the other options are wrong:
Option B is wrong:
You don't need to explicitly specify <int> because the compiler can deduce the type from the arguments. swap(x, y) where x and y are ints allows the compiler to infer T = int automatically. Template type deduction works here.
Option C is wrong:
Using T for the temp variable is correct and preferred! This keeps the function generic. If you hardcoded int temp, the function wouldn't work for other types like double or string. Using T maintains the template's flexibility.
Option D is wrong:
The code definitely has a bug - it swaps the copies, not the originals. The output would be 5 10, not the expected 10 5.

Multiple Choice
What happens when you call a template function without explicitly specifying the type parameter?
template<class T> T add(T a, T b) { return a + b; } int result = add(5, 10); // What happens here?
A
Compilation error - must specify type as add<int>(5, 10)
B
Compiler automatically deduces T = int from the arguments
C
T defaults to double for all numeric types
D
Runtime error occurs when the function executes
Correct Answer: B
The compiler uses template argument deduction to automatically determine that T should be int. Here's exactly how it works:
Deduction process:
1. Function call: add(5, 10)
2. Template signature: T add(T a, T b)
3. First argument: 5 is an int, so compiler tries T = int
4. Second argument: 10 is also an int, confirming T = int
5. Result: Compiler generates int add(int a, int b)
6. Compilation: Function is created and called successfully
When deduction works vs. when it doesn't:
// ✓ WORKS - both args are int add(5, 10); // T deduced as int // ✓ WORKS - both args are double add(3.5, 2.1); // T deduced as double // ✗ ERROR - mismatched types! add(5, 3.5); // T = int or double? Compiler can't decide! // ✓ WORKS - explicit type resolves ambiguity add<double>(5, 3.5); // 5 converts to 5.0
Why the other options are wrong:
Option A is wrong:
You CAN specify the type explicitly (add<int>(5, 10)), but you don't HAVE to. Template argument deduction is a core feature of C++ templates that makes them convenient to use. Explicit specification is only needed when the compiler can't deduce the type or when you want to override the deduction.
Option C is wrong:
There's no default type for templates. The compiler deduces the EXACT type from the arguments. If you pass ints, you get int. If you pass doubles, you get double. No automatic conversion to double happens.
Option D is wrong:
This is a compile-time feature, not a runtime one. Template instantiation and type deduction happen during compilation, before the program even runs. If there's a problem, you'll get a compilation error, never a runtime error from the template mechanism itself.

True/False
True or False: You can create a template with multiple type parameters, like template<class T, class U>.
A
True
B
False
Correct Answer: A (True)
Absolutely! Templates can have multiple type parameters. This is really useful when you need to work with different types in the same function or class. Here's how it works:
Example with function template:
template<class T, class U> void printPair(T first, U second) { cout << "First: " << first << ", Second: " << second; } // Can call with different type combinations: printPair(42, "hello"); // T=int, U=const char* printPair(3.14, 100); // T=double, U=int printPair("hi", 2.5); // T=const char*, U=double
Example with class template:
template<class T, class U> class Pair { private: T first; U second; public: Pair(T f, U s) : first(f), second(s) {} T getFirst() { return first; } U getSecond() { return second; } }; // Create pairs with different type combinations: Pair<int, string> p1(1, "one"); Pair<double, int> p2(3.14, 100);
Real-world usage:
Multiple type parameters are used everywhere in C++! The STL (Standard Template Library) uses this extensively:
• std::map<KeyType, ValueType> - maps need two types
• std::pair<T1, T2> - pairs of different types
• You can even have 3+ type parameters if needed!
Why False is wrong:
Templates are not limited to a single type parameter. C++ allows you to have as many type parameters as you need, separated by commas: template<class T, class U, class V> and so on. This is a fundamental feature of C++ templates.

True/False
True or False: Template functions are compiled when you write them, just like regular functions.
A
True
B
False
Correct Answer: B (False)
Template functions are NOT compiled when you write them. They're only compiled when you actually USE them with a specific type. This is a fundamental difference between templates and regular functions!
How regular functions work:
int add(int a, int b) { // Compiler compiles this NOW return a + b; } // Function is fully compiled and ready to use
How template functions work:
template<class T> T add(T a, T b) { // Compiler does NOT compile this yet! return a + b; // This is just a BLUEPRINT } // Later in your code: int x = add(5, 10); // NOW compiler generates int add(int, int) double y = add(2.5, 3.5); // NOW compiler generates double add(double, double)
The compilation process:
Step 1: Write template (just stores the blueprint, no compilation yet)
Step 2: Use template with int → Compiler generates and compiles int version
Step 3: Use template with double → Compiler generates and compiles double version
Step 4: Use template with string → Compiler generates and compiles string version
Why this matters:
1. Errors appear late: If there's a bug in your template, you won't see it until you use the template with a type that triggers the bug

2. Code generation: If you use a template with 5 different types, the compiler creates 5 different functions

3. Header files: This is why template definitions MUST be in header files - the compiler needs to see the blueprint when generating the code
Example of late error detection:
template<class T> void printDouble(T val) { cout << val * 2; // Looks fine, compiles without errors at first! } printDouble(10); // ✓ Works! Compiler generates int version printDouble("Hi"); // ✗ ERROR! Can't multiply string by 2 // Error happens HERE, when used!
Why True is wrong:
Templates are explicitly NOT compiled when you write them. They use a lazy compilation model: compilation happens on-demand when you instantiate the template with a concrete type. This is called "template instantiation" and it's a compile-time feature, but it doesn't happen when the template is defined - only when it's used.

Naledi is working on her anime tracker. This code has a subtle bug - what is it?
template<class T> class Stack { private: T items[100]; int top; public: Stack() { top = -1; } void push(T item) { items[++top] = item; } T pop() { return items[top--]; } };
A
No bounds checking - could overflow or underflow the array
B
Should use typename instead of class
C
The array size should be a template parameter
D
No bug - the code is correct
Correct Answer: A
The bug is missing bounds checking! This stack can easily overflow (push too many items) or underflow (pop from an empty stack), causing undefined behavior.
Overflow scenario:
Stack<int> s; for (int i = 0; i < 101; i++) { // Push 101 items! s.push(i); // ⚠ DANGER when i >= 100 } // What happens: // push #0: top becomes 0, items[0] = 0 ✓ OK // push #99: top becomes 99, items[99] = 99 ✓ OK // push #100: top becomes 100, items[100] = 100 ✗ OUT OF BOUNDS! // push #101: top becomes 101, items[101] = 101 ✗ UNDEFINED BEHAVIOR!
Underflow scenario:
Stack<string> s; // Empty stack, top = -1 string anime = s.pop(); // ⚠ DANGER - popping from empty stack! // What happens: // top is -1 // return items[top--] → return items[-1] ✗ NEGATIVE INDEX! // Then top becomes -2, making it worse // UNDEFINED BEHAVIOR - could crash, return garbage, or corrupt memory
Correct implementation with bounds checking:
template<class T> class Stack { private: T items[100]; int top; public: Stack() { top = -1; } void push(T item) { if (top >= 99) { // Check for overflow! cout << "Error: Stack overflow!"; return; } items[++top] = item; } T pop() { if (top < 0) { // Check for underflow! cout << "Error: Stack underflow!"; return T(); // Return default value } return items[top--]; } };
Why the other options are wrong:
Option B is wrong:
class and typename are completely interchangeable in template parameters. Either one is valid. Using class doesn't cause any bugs - it's purely a stylistic choice.
Option C is wrong:
While making the array size a template parameter would be a nice IMPROVEMENT (allowing Stack<int, 50>), it's not a BUG. The current implementation with a fixed size of 100 works fine - the bug is the lack of bounds checking, not the hardcoded size.
Option D is wrong:
There's definitely a bug. Without bounds checking, this stack is unsafe and can cause memory corruption, crashes, or other undefined behavior when used incorrectly.

Multiple Choice
When working with template inheritance, why do you sometimes need to use this-> to access inherited members?
template<class T> class Base { protected: T value; }; template<class T> class Derived : public Base<T> { public: void print() { cout << this->value; // Why this-> ? } };
A
Because templates don't support regular inheritance
B
Because the base class is a template - compiler can't see its members until instantiation
C
It's just a style preference - not actually required
D
To avoid naming conflicts between base and derived classes
Correct Answer: B
When you inherit from a template base class, the compiler doesn't know what members exist in the base until the template is instantiated with a specific type. Using this-> tells the compiler to delay looking up the name until instantiation time.
The problem - dependent base classes:
In the code above, Base<T> is called a "dependent base class" because its contents depend on the template parameter T. The compiler doesn't know what's inside Base<T> until you specify what T is.
What happens without this->:
template<class T> class Derived : public Base<T> { public: void print() { cout << value; // ✗ COMPILATION ERROR! // Error: "identifier value is undefined" } };
The compiler looks for value in the current scope, doesn't find it, and gives up. It doesn't look in Base<T> because it doesn't know what's in there yet.
Three solutions:
// Solution 1: Use this-> (recommended) void print() { cout << this->value; // ✓ Tells compiler to look in base class } // Solution 2: Use Base<T>:: prefix void print() { cout << Base<T>::value; // ✓ Explicitly qualify the name } // Solution 3: Using declaration using Base<T>::value; void print() { cout << value; // ✓ Now compiler knows where to find it }
Why this happens - two-phase lookup:
C++ uses "two-phase name lookup" for templates:
Phase 1: When template is defined, non-dependent names are looked up
Phase 2: When template is instantiated, dependent names are looked up

Without this->, value is treated as non-dependent, so it's looked up in Phase 1 (too early!). With this->, value becomes dependent, so it's looked up in Phase 2 (when the compiler knows what Base<T> contains).
Why the other options are wrong:
Option A is wrong:
Templates fully support inheritance! You can inherit from template classes, create template derived classes, and use all the normal OOP features. Template inheritance works the same as regular inheritance, just with the added complexity of dependent names.
Option C is wrong:
It's NOT just style - it's actually REQUIRED for the code to compile! Without this-> (or one of the other solutions), the compiler will give an error saying it can't find the member. This is a real technical requirement due to how template name lookup works.
Option D is wrong:
While this-> CAN help with naming conflicts in general programming, that's not why it's needed here. Even if there are no naming conflicts at all, you still need this-> when accessing dependent base class members from a template derived class.

True/False
True or False: You can create a template function that works with arrays of any type and any size.
A
True
B
False
Correct Answer: A (True)
Absolutely! You can create template functions that handle arrays of any type AND any size. C++ supports non-type template parameters (like integers) in addition to type parameters.
Template with type parameter only:
template<class T> void printArray(T arr[], int size) { for (int i = 0; i < size; i++) { cout << arr[i] << " "; } } // Works with any type, but you need to pass the size: int nums[] = {1, 2, 3}; printArray(nums, 3); // T = int double scores[] = {8.5, 9.0, 7.5}; printArray(scores, 3); // T = double
Template with type AND size parameters:
template<class T, int N> // N is a non-type parameter! void printArray(T (&arr)[N]) { // Reference to array of size N for (int i = 0; i < N; i++) { cout << arr[i] << " "; } } // Compiler deduces BOTH type AND size! int nums[] = {1, 2, 3, 4, 5}; printArray(nums); // T = int, N = 5 (automatically!) double scores[] = {8.5, 9.0, 7.5}; printArray(scores); // T = double, N = 3 (automatically!) string names[] = {"Alice", "Bob"}; printArray(names); // T = string, N = 2 (automatically!)
Real-world example - finding minimum in any array:
template<class T, int SIZE> T findMin(T (&arr)[SIZE]) { T minimum = arr[0]; for (int i = 1; i < SIZE; i++) { if (arr[i] < minimum) { minimum = arr[i]; } } return minimum; } int nums[] = {5, 2, 8, 1, 9}; cout << findMin(nums); // Outputs: 1 double temps[] = {36.5, 37.2, 35.8}; cout << findMin(temps); // Outputs: 35.8
Key advantages:
1. Type safety: Works with any type that supports the required operations
2. Size safety: Compiler knows the exact array size, preventing out-of-bounds errors
3. No extra parameters: Don't need to manually pass the size
4. Compile-time checking: Everything is checked at compile time
Why False is wrong:
C++ definitely supports this through non-type template parameters. You can parameterize templates not just by type (class/typename), but also by integer values. This allows creating truly generic array-handling functions that work with any type and any size.

This code will NOT compile because the compiler cannot deduce a single type for T. Let me explain why:
Type deduction attempt:
Function signature: T add(T a, T b)
Function call: add(5, 3.5)

First argument: 5 is int → Compiler thinks T = int
Second argument: 3.5 is double → Compiler thinks T = double
Conflict! T cannot be both int AND double

Compiler error: "no matching function for call to 'add(int, double)'"
Full message: "template argument deduction/substitution failed: deduced conflicting types for parameter 'T'"
Why this is a problem:
The template requires BOTH parameters to be the same type T. Since you passed an int and a double, the compiler cannot instantiate this template. The function signature says "take two values of THE SAME type T", but you're providing two DIFFERENT types.
Solutions:
// Solution 1: Make both arguments the same type int result1 = add(5, 3); // ✓ Both int double result2 = add(5.0, 3.5); // ✓ Both double // Solution 2: Explicitly specify the type double result3 = add<double>(5, 3.5); // ✓ 5 converts to 5.0 // Solution 3: Use two template parameters template<class T, class U> ??? add(T a, U b) { // What's the return type? Tricky! return a + b; }

Option A is wrong:
The code never gets to run because it fails to compile. Even if it could run, 5 + 3.5 = 8.5, not 8. You can't get output from code that doesn't compile.
Option B is wrong:
While 8.5 would be the mathematically correct result of 5 + 3.5, the code never compiles. The template type deduction fails before any calculation can happen.
Option D is wrong:
This is a compile-time error, not a runtime error. Template type deduction happens during compilation, so the compiler catches this problem before the program can run. Runtime errors only occur in running programs.

Find the Bug
This template class has a memory issue. What's the bug?
template<class T> class DynamicArray { private: T* data; int size; public: DynamicArray(int s) { size = s; data = new T[size]; } };
A
Missing destructor - memory leak!
B
Should use malloc instead of new
C
Templates can't have dynamic memory
D
The size variable should be static
Correct Answer: A
The bug is a classic memory leak! The class allocates memory with new in the constructor, but never deallocates it with delete. Every time a DynamicArray object goes out of scope or is destroyed, the memory stays allocated.
The memory leak in action:
void leakyFunction() { DynamicArray<int> arr(1000); // Allocates 1000 ints on heap } // ⚠ arr goes out of scope, but memory NOT freed! // 1000 ints still taking up memory // No way to access or free this memory now! // Call this 100 times = 100,000 leaked ints! for (int i = 0; i < 100; i++) { leakyFunction(); // Each call leaks more memory }
What happens:
Object created: DynamicArray<int> arr(1000);
  • Constructor runs
  • new T[1000] allocates memory on the heap
  • data points to this memory

Object destroyed: Function ends, arr goes out of scope
  • Default destructor runs (does nothing useful)
  • Local variables data and size are destroyed
  • BUT the heap memory they pointed to is NOT freed
  • Memory is now inaccessible but still allocated = LEAK!
Correct implementation:
template<class T> class DynamicArray { private: T* data; int size; public: DynamicArray(int s) { size = s; data = new T[size]; } // ✓ Add destructor to free memory! ~DynamicArray() { delete[] data; // Free the array } // Also should add copy constructor and assignment operator // (Rule of Three!) but destructor is the critical missing piece };
The Rule of Three:
If a class needs ANY of these three, it probably needs ALL three:
1. Destructor - to free resources
2. Copy constructor - to handle deep copies
3. Copy assignment operator - to handle deep copies in assignment

This class has dynamic memory, so it needs all three to be safe!
Why the other options are wrong:
Option B is wrong:
new is the correct way to allocate memory in C++, especially for objects. malloc is from C and doesn't call constructors. For templates working with any type T, you MUST use new because T might be a class that needs its constructor called. Using malloc would be wrong.
Option C is wrong:
Templates absolutely CAN use dynamic memory! In fact, most STL containers (vector, list, map) are templates that use dynamic memory internally. Templates work with any code that regular classes can use.
Option D is wrong:
Making size static would be completely wrong! Static members are shared across ALL instances of the class. If size were static, ALL DynamicArray objects would share the same size value, which makes no sense. Each array needs its own size.

Option D is wrong:
Templates are optional. You can write C++ programs without using templates at all. They're a tool, not a requirement.
