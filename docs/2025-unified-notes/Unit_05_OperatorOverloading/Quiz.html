Question 1

Operator Function Syntax (Adapted from EO1 2025 Q3)

Given the expression: result = (a + b) * c;

Where a, b, c, and result are objects of class Number, rewrite this using explicit operator function calls.

Answer:

result.operator=(operator*(operator+(a, b), c));

Detailed Explanation:

Working from innermost to outermost operations:

  1. a + b becomes operator+(a, b) - calls the + operator with a and b as arguments
  2. The result is then multiplied by c: operator*(result_of_add, c)
  3. Finally, assignment: result.operator=(result_of_mult)

Key Insight: Binary operators like + and * are typically implemented as non-member functions taking two parameters. Assignment (=) is typically a member function, so it's called as result.operator=(...).

Question 2

Friend vs Member Functions

Which of the following statements is TRUE about friend functions in operator overloading?

  1. Friend functions are always more efficient than member functions
  2. Friend functions allow symmetric type conversion for both operands
  3. Friend functions must be declared inside the class but defined with the friend keyword
  4. Friend functions cannot access private members of the class

Answer: B - Friend functions allow symmetric type conversion for both operands

Why B is correct:

Friend functions are non-member functions, so both operands are parameters. The compiler can apply automatic type conversion to either operand. This means both obj + 5 and 5 + obj can work (if there's an appropriate constructor). With member functions, only the right operand can be converted.

Why other options are wrong:

  • A: Incorrect - Friend and member functions have the same efficiency when accessing private members. Both can access private data directly. The choice between them is about interface design, not performance.
  • C: Incorrect - Friend functions are declared with the friend keyword inside the class, but defined WITHOUT the friend keyword outside the class. The definition is just a regular function.
  • D: Incorrect - This is backwards. The whole point of friend functions is that they CAN access private and protected members. That's what makes them "friends".
Question 3

Stream Operator Requirements

Which of the following is a requirement for overloading the << operator for output?

  1. It must be implemented as a member function
  2. It must return void
  3. It must return ostream&
  4. The object parameter must be non-const

Answer: C - It must return ostream&

Why C is correct:

The operator<< must return ostream& (a reference to the output stream) to enable chaining. When you write cout << obj1 << obj2, the expression (cout << obj1) must evaluate to cout so it can be used for the next << obj2 operation. Returning by reference avoids copying the stream object.

Why other options are wrong:

  • A: Incorrect - operator<< must be a NON-member function (usually a friend). The left operand is ostream, not your class. You can't add member functions to ostream (it's in the standard library).
  • B: Incorrect - Returning void breaks chaining. You couldn't write cout << obj << endl because (cout << obj) would be void, and void << endl is nonsense.
  • D: Incorrect - The object parameter should be const because we're only reading it for output, not modifying it. ostream& operator<<(ostream& os, const MyClass& obj) is the correct signature.
Question 4

Code Tracing with Operators

What is the output of the following code?

class Counter {
public:
    Counter(int v = 0) : value(v) {}

    Counter& operator++() {
        value++;
        return *this;
    }

    const Counter operator++(int) {
        Counter old = *this;
        value++;
        return old;
    }

    void print() { cout << value; }

private:
    int value;
};

int main() {
    Counter c(5);
    (c++).print();
    cout << " ";
    (++c).print();
    return 0;
}

Output:

5 7

Line-by-Line Trace:

  1. Line 20: Create Counter c(5) → c.value = 5
  2. Line 21: (c++).print():
    • Postfix ++ is called
    • Saves old value: old.value = 5
    • Increments: c.value = 6
    • Returns old (5)
    • Calls print() on temporary (old) → prints 5
  3. After line 21: c.value = 6 (the increment happened, but we printed the old value)
  4. Line 22: Prints " " (space)
  5. Line 23: (++c).print():
    • Prefix ++ is called
    • Increments: c.value = 7
    • Returns reference to c
    • Calls print() on c → prints 7

Key Difference:

  • Postfix (c++): Returns OLD value (5), but c still gets incremented to 6
  • Prefix (++c): Increments FIRST (6→7), then returns reference to modified c
Question 5

Return Types

For the operator+= member function, what should the return type be and why?

  1. void - Because it modifies the object directly
  2. ClassName - To return a new modified object
  3. ClassName& - To enable chaining and avoid copying
  4. const ClassName& - To prevent modification of the result

Answer: C - ClassName& (non-const reference)

Why C is correct:

Compound assignment operators like += should return *this by reference. This enables two things:

  1. Chaining: a += b += c works because each += returns the modified object
  2. Efficiency: Returning by reference avoids making a copy of the object
  3. Consistency: Matches the behavior of built-in types (int also returns reference from +=)

Why other options are wrong:

  • A (void): Breaks chaining. a += b += c wouldn't work because (b += c) returns void, and you can't do a += void. Also doesn't match how built-in += works.
  • B (ClassName): Returns a copy, not a reference. Inefficient and incorrect - you'd be returning a copy of the modified object, not the object itself. Also breaks chaining properly because you'd modify the copy, not the original.
  • D (const ClassName&): The const is wrong. You should be able to further modify the result. For example, (a += b)++ or (a += b) = c should be possible (though rarely used). Making it const prevents these operations unnecessarily.

Implementation Example:

ClassName& operator+=(const ClassName& other) {
    // Modify *this
    this->data += other.data;
    return *this;  // Return reference to modified object
}
Question 6

True or False: Operator Overloading Rules

True or False: You can overload the operator[] for a class as a non-member function.

Justify your answer.

Answer: False

Detailed Justification:

The C++ standard requires that certain operators MUST be implemented as non-static member functions. The subscript operator [] is one of them.

Operators that MUST be members:

  • = (assignment)
  • [] (subscript)
  • () (function call)
  • -> (member access)

Why this restriction exists:

These operators are fundamentally tied to the object they operate on. The subscript operator [] is providing direct access to the object's internal data structure. It only makes sense as a member because:

  1. The left operand MUST be an object of the class
  2. It operates on the object's internal state
  3. There's no case where you'd want symmetric conversion (you can't subscript an int: 5[obj] is nonsense)

Correct Implementation:

class MyArray {
public:
    int& operator[](int index) {  // MUST be a member
        return data[index];
    }
private:
    int* data;
};
Question 7

Implementing Comparison Operators

Which implementation of operator!= is most efficient if you've already implemented operator==?

  1. bool operator!=(const MyClass& a, const MyClass& b) {
    return (a.data1 != b.data1 || a.data2 != b.data2);
}
  2. bool operator!=(const MyClass& a, const MyClass& b) {
    return !(a == b);
}
  3. bool operator!=(const MyClass& a, const MyClass& b) {
    if (a.data1 == b.data1 && a.data2 == b.data2)
        return false;
    return true;
}
  4. bool MyClass::operator!=(const MyClass& other) const {
    return !(*this).operator==(other);
}

Answer: B

Why B is correct:

Option B is the best because it:

  • Reuses existing logic: Delegates to operator== which you've already implemented and tested
  • Avoids duplication: No duplicate comparison logic to maintain
  • Prevents bugs: If you update how equality works, inequality automatically updates too
  • Clear and concise: The intent is obvious - "not equal" is literally "not (equal)"

Why other options are worse:

  • A: Duplicates the comparison logic from operator==. If you have 10 member variables, you have to update both functions when you add an 11th. Violates DRY (Don't Repeat Yourself) principle.
  • C: Also duplicates logic, just written differently. Same maintenance problem as A.
  • D: Unnecessarily verbose. (*this).operator==(other) is the same as *this == other, which the compiler handles. While technically correct, it's harder to read than option B.

Best Practice Pattern:

Implement the "primitive" operators (==, <) with full logic. Derive all others from them:

bool operator!=(const MyClass& a, const MyClass& b) { return !(a == b); }
bool operator>(const MyClass& a, const MyClass& b) { return b < a; }
bool operator<=(const MyClass& a, const MyClass& b) { return !(b < a); }
bool operator>=(const MyClass& a, const MyClass& b) { return !(a < b); }
Question 8

Prefix vs Postfix Increment (Adapted from EO1 2024)

What distinguishes the prefix ++ operator from the postfix ++ operator in their function signatures?

  1. Different return types: prefix returns reference, postfix returns value
  2. Postfix has a dummy int parameter, prefix has no parameters
  3. Prefix is always a member function, postfix is always a friend
  4. Prefix takes the object by reference, postfix by value

Answer: B - Postfix has a dummy int parameter, prefix has no parameters

Why B is correct:

The C++ standard uses a clever trick to distinguish prefix from postfix: the postfix version has an unused int parameter. This parameter has no name and is never used - it exists solely to make the signature different.

Signatures:

// Prefix (no parameters if member, one if friend)
Counter& operator++();  // member version

// Postfix (dummy int parameter)
const Counter operator++(int);  // member version
//                        ^^^--- unused dummy parameter

Why other options are wrong:

  • A: While true that return types differ, this is NOT what distinguishes them in the signature. C++ doesn't allow overloading based solely on return type. The signatures must differ in their parameters.
  • C: Both can be implemented as either member or friend functions. Neither is required to be one or the other.
  • D: Incorrect - both typically work with the same object. The calling object (for members) or parameter (for friends) is the same. The difference is the dummy int parameter.

Usage:

Counter c(5);
++c;   // Calls operator++()    - prefix
c++;   // Calls operator++(int) - postfix (compiler passes 0)
Question 9

Find the Bug

The following code has a bug. Identify the bug and explain how to fix it.

class Money {
public:
    Money(int d, int c) : dollars(d), cents(c) {}

    friend Money operator+(const Money& m1, const Money& m2);

private:
    int dollars, cents;
};

friend Money operator+(const Money& m1, const Money& m2) {
    int totalCents = (m1.dollars * 100 + m1.cents) +
                     (m2.dollars * 100 + m2.cents);
    return Money(totalCents / 100, totalCents % 100);
}

Bug Location: Line 11

What's Wrong: The friend keyword appears in the function definition (line 11), but it should only be in the declaration (line 5).

Why It's Wrong:

The friend keyword is a class permission - it goes in the class declaration to grant access. The function definition is written as a regular free function (no friend keyword, no class scope). Using friend in the definition causes a compilation error.

How to Fix:

// Correct version - NO 'friend' keyword in definition
Money operator+(const Money& m1, const Money& m2) {
    int totalCents = (m1.dollars * 100 + m1.cents) +
                     (m2.dollars * 100 + m2.cents);
    return Money(totalCents / 100, totalCents % 100);
}

Key Rule:

  • Declaration (inside class): Use friend keyword
  • Definition (outside class): NO friend keyword, NO ClassName:: scope

Why this confuses students: Member function definitions use ClassName:: scope. Friend functions look like member declarations but are defined as free functions. This asymmetry is deliberate - friend functions are not members, they're external functions with special access.

Question 10

Implementing Multiplication Operator (Similar to EO1 2025 Q10)

Given this incomplete Box class:

class Box {
public:
    Box(int w, int h, int d) : width(w), height(h), depth(d) {}
    int getVolume() const { return width * height * depth; }
private:
    int width, height, depth;
};

Write the implementation for operator* that multiplies all dimensions by a factor. After Box b2 = b1 * 2;, b2 should have dimensions twice as large as b1.

Answer:

class Box {
public:
    Box(int w, int h, int d) : width(w), height(h), depth(d) {}
    int getVolume() const { return width * height * depth; }

    // Friend declaration
    friend Box operator*(const Box& box, int factor);

private:
    int width, height, depth;
};

// Friend function definition
Box operator*(const Box& box, int factor) {
    return Box(box.width * factor,
               box.height * factor,
               box.depth * factor);
}

Explanation:

  1. Friend function: Allows symmetric conversion. Both box * 2 and 2 * box can work if you also implement operator*(int, const Box&).
  2. Returns new Box: Arithmetic operators create and return new objects, they don't modify operands.
  3. Const parameters: Neither operand is modified - we read from both and create a new result.
  4. Direct member access: As a friend, we can access box.width, box.height, box.depth directly.

For symmetric conversion, add:

Box operator*(int factor, const Box& box) {
    return box * factor;  // Reuse the existing operator
}

Usage:

Box b1(2, 3, 4);          // 2x3x4 box
Box b2 = b1 * 2;           // 4x6x8 box
Box b3 = 3 * b1;           // 6x9x12 box (needs second operator)
cout << b2.getVolume();    // 192 (4*6*8)
Question 11

Operator Overloading Restrictions

Which of the following operators CANNOT be overloaded in C++?

  1. operator[] (subscript)
  2. operator-> (member access)
  3. operator. (dot operator)
  4. operator() (function call)

Answer: C - operator. (dot operator) cannot be overloaded

Why C is correct:

The dot operator . is one of a few operators that C++ explicitly forbids overloading. Others include:

  • . (dot / member selection)
  • :: (scope resolution)
  • ?: (ternary conditional)
  • sizeof
  • .* (pointer-to-member)

Why these can't be overloaded: These operators are fundamental to the language's semantics. Allowing them to be overloaded would make code unpredictable and potentially break the type system.

Why other options can be overloaded:

  • A ([]): Can be overloaded to provide array-like access to class objects
  • B (->): Can be overloaded to create smart pointers
  • D (()): Can be overloaded to make objects callable like functions (function objects / functors)

What does this code print?

class Value {

    Value(int v) : val(v) {}

    Value operator+(const Value& other) const {

    int val;

int main() {
    Value a(5), b(3), c(2);

    • First: b += c → b.val = 3+2 = 5, returns reference to b

  • operator+ creates new objects without modifying operands
  • operator+= modifies the left operand and returns it by reference
  • Compound assignment has right-to-left associativity
Question 13

Const Correctness in Operators

Given a Point class, which operator signature is correct for checking equality?

  1. bool operator==(Point& other)
  2. bool operator==(const Point& other) const
  3. bool operator==(Point& other) const
  4. const bool operator==(const Point& other) const

Answer: B - bool operator==(const Point& other) const

Why B is correct:

  • First const: The parameter is const Point& because we're only reading it, not modifying it
  • Second const: The member function is const because comparing doesn't modify the calling object either
  • Return type: Plain bool - there's no reason to return const bool for a fundamental type

Why others are wrong:

  • A: No const anywhere - prevents comparing const objects: const Point p1(1,2); const Point p2(1,2); p1 == p2 won't compile
  • C: Parameter isn't const - prevents using with const arguments or temporaries
  • D: const bool return is pointless - you can't modify a bool anyway, and it prevents certain optimizations

Example:

class Point {
public:
    bool operator==(const Point& other) const {
        return (x == other.x && y == other.y);
    }
private:
    int x, y;
};
Question 14

Assignment Operator Special Case

Why should the assignment operator check for self-assignment?

  1. To improve performance by avoiding unnecessary work
  2. To prevent crashes when deallocating and reallocating the same memory
  3. Both A and B
  4. Self-assignment check is not necessary in C++

Answer: C - Both A and B

Why C is correct:

Self-assignment checking serves two critical purposes:

Reason A - Performance:

If someone writes obj = obj;, without checking you'd unnecessarily copy all data to itself. Checking if (this != &other) skips this wasted work.

Reason B - Correctness (MORE IMPORTANT):

With dynamic memory, self-assignment can cause crashes:

// WITHOUT self-assignment check
MyClass& operator=(const MyClass& other) {
    delete[] data;              // Delete our data
    data = new int[other.size]; // Allocate new
    // Copy from other...
}

// If self-assignment (obj = obj):
// 1. delete[] data    → Deletes our data
// 2. other.data is ALSO deleted (it's the same object!)
// 3. new int[other.size] → other.size is garbage!
// CRASH!

Correct Implementation:

MyClass& operator=(const MyClass& other) {
    if (this != &other) {  // Check for self-assignment!
        delete[] data;
        size = other.size;
        data = new int[size];
        for (int i = 0; i < size; i++)
            data[i] = other.data[i];
    }
    return *this;
}

Why other options are wrong:

  • D: Completely wrong - self-assignment check is critical for classes with dynamic memory
Question 15

Conversion and Operators

If a class has a constructor MyClass(int), which expression will work with a member operator+?

  1. obj + 5 only
  2. 5 + obj only
  3. Both obj + 5 and 5 + obj
  4. Neither will work

Answer: A - obj + 5 only

Why A is correct:

With a member function operator+:

  • obj + 5 translates to obj.operator+(5)
  • The compiler can convert 5 to MyClass(5) using the constructor
  • This works: obj.operator+(MyClass(5))

Why 5 + obj doesn't work:

  • 5 + obj translates to 5.operator+(obj)
  • int doesn't have an operator+ that takes MyClass
  • The compiler can't add member functions to built-in types
  • Result: compilation error

To make both work, use friend function:

class MyClass {
public:
    MyClass(int v) : value(v) {}  // Allows int → MyClass conversion

    // Friend allows conversion on BOTH sides
    friend MyClass operator+(const MyClass& a, const MyClass& b) {
        return MyClass(a.value + b.value);
    }

private:
    int value;
};

// Now BOTH work:
MyClass result1 = obj + 5;  // Works: obj.operator+(MyClass(5))
MyClass result2 = 5 + obj;  // Works: operator+(MyClass(5), obj)

Key Principle: Automatic conversion only works for parameters, not for the calling object (left side of member function call).

Question 16

Subscript Operator with Const Overloading

Why do we need two versions of operator[]?

class IntArray {
public:
    int& operator[](int index);             // Version 1
    const int& operator[](int index) const; // Version 2
private:
    int* data;
};
  1. To allow subscripting with different index types
  2. One for reading, one for writing to array elements
  3. To work with both const and non-const objects
  4. This is a compiler error - you can't overload based only on const

Answer: C - To work with both const and non-const objects

Why C is correct:

We need TWO versions to handle const and non-const objects properly:

Version 1 (non-const):

  • Returns int& - allows modification
  • Called on non-const objects
  • Enables: arr[0] = 42; (writing)

Version 2 (const):

  • Returns const int& - prevents modification
  • Called on const objects
  • Enables: int x = arr[0]; (reading from const array)

Example Usage:

IntArray arr;
arr[0] = 10;        // Calls non-const version, returns int&

const IntArray cArr;
int x = cArr[0];    // Calls const version, returns const int&
cArr[0] = 10;       // ERROR! Can't modify const reference

Why other options are wrong:

  • A: Both versions take the same parameter type (int index). Different index types would require different parameter types, not const overloading.
  • B: Close but not quite right. BOTH versions can be used for reading. The difference is whether the object itself is const, not whether you're reading or writing. The const version prevents writing, but the choice of which is called depends on the object's constness.
  • D: Incorrect - you CAN overload member functions based on const. The const keyword is part of the function signature for member functions.

Full Implementation:

class IntArray {
public:
    // Non-const version: for modifiable arrays
    int& operator[](int index) {
        return data[index];  // Returns reference - can modify
    }

    // Const version: for const arrays
    const int& operator[](int index) const {
        return data[index];  // Returns const ref - can't modify
    }

private:
    int* data;
};
Question 17

Function Call Operator (Functor)

What is the output?

class Multiplier {
public:
    Multiplier(int f) : factor(f) {}

    int operator()(int value) const {
        return value * factor;
    }

private:
    int factor;
};

int main() {
    Multiplier triple(3);
    Multiplier doubleIt(2);

    cout << triple(5) << " ";
    cout << doubleIt(triple(4));
    return 0;
}

Output:

15 24

Line-by-Line Trace:

  1. Line 13: Create Multiplier triple(3) → triple.factor = 3
  2. Line 14: Create Multiplier doubleIt(2) → doubleIt.factor = 2
  3. Line 16: triple(5):
    • Calls triple.operator()(5)
    • Returns 5 * triple.factor = 5 * 3 = 15
    • Prints: 15 and space
  4. Line 17: doubleIt(triple(4)):
    • Inner: triple(4) → 4 * 3 = 12
    • Outer: doubleIt(12) → 12 * 2 = 24
    • Prints: 24

What's Happening:

The function call operator operator() makes objects callable like functions. These are called functors or function objects.

Key Benefits of Functors:

  • State: Unlike regular functions, functors can hold state (the factor member variable)
  • Customizable: Each functor object can have different state
  • Syntax: Used just like functions: obj(args)

Real-World Use:

Functors are used extensively with STL algorithms:

vector nums = {1, 2, 3, 4, 5};
Multiplier triple(3);
transform(nums.begin(), nums.end(), nums.begin(), triple);
// nums is now {3, 6, 9, 12, 15}

Question 19

Find the Bug: Stream Insertion

The following code has a bug. Identify and fix it.

class Fraction {
public:
    Fraction(int n, int d) : numerator(n), denominator(d) {}

    friend ostream& operator<<(ostream& os, Fraction& frac);

private:
    int numerator, denominator;
};

ostream& operator<<(ostream& os, Fraction& frac) {
    os << frac.numerator << "/" << frac.denominator;
    return os;
}

Bug Location: Lines 5 and 11 (parameter should be const)

What's Wrong:

The Fraction parameter is passed by non-const reference (Fraction& frac), but it should be const Fraction& frac.

Why It's Wrong:

This causes problems with:

  1. Const objects: 
    const Fraction f(3, 4);
cout << f;  // ERROR! Can't bind const to non-const reference
  2. Temporary objects: 
    cout << Fraction(1, 2);  // ERROR! Temporary is const
  3. Chaining: 
    cout << Fraction(1, 2) << " " << Fraction(3, 4);
// First Fraction(1,2) fails - it's a temporary

How to Fix:

class Fraction {
public:
    Fraction(int n, int d) : numerator(n), denominator(d) {}

    // FIX: Add const to parameter
    friend ostream& operator<<(ostream& os, const Fraction& frac);

private:
    int numerator, denominator;
};

// FIX: Add const to parameter
ostream& operator<<(ostream& os, const Fraction& frac) {
    os << frac.numerator << "/" << frac.denominator;
    return os;
}

Why This Works:

  • Output operation doesn't modify the object - we're only reading it
  • const reference accepts const objects, non-const objects, AND temporaries
  • Matches the pattern of standard library stream operators

General Rule: Input/output operators should take the object parameter as const& (for output) or non-const & (for input, because reading modifies state).

Question 20

Operator Precedence and Associativity

Given proper operator overloading for class Expr, how is the expression a = b + c * d evaluated?

  1. a.operator=(operator+(b, operator*(c, d)))
  2. operator=(a, operator*(operator+(b, c), d))
  3. a.operator=(operator*(operator+(b, c), d))
  4. operator+(b, operator*(c, d)).operator=(a)

Answer: A - a.operator=(operator+(b, operator*(c, d)))

Why A is correct:

Operator overloading preserves precedence and associativity from built-in operators.

Evaluation Order:

  1. Step 1: * has higher precedence than +, so c * d is evaluated first
    • operator*(c, d) → returns temporary result1
  2. Step 2: + is evaluated next with b and result1
    • operator+(b, result1) → returns temporary result2
  3. Step 3: = has lowest precedence, evaluated last
    • a.operator=(result2)

Precedence Table (Highest to Lowest):

Higher  *  /  %           (multiplicative)
        +  -              (additive)
        << >>             (shift)
        <  >  <= >=       (relational)
        == !=             (equality)
        =  += -= etc.     (assignment)
Lower

Why other options are wrong:

  • B: Wrong on two counts:
    1. Assignment is member function, not free function: can't be operator=(a, ...)
    2. Order is wrong: evaluates b + c first (ignores precedence)
  • C: Order is wrong - evaluates b + c before * d, violating precedence rules
  • D: Completely backwards - tries to assign a to the temporary result, which doesn't make sense

Key Principle: You CANNOT change precedence or associativity when overloading operators. They're built into the language.

Question 21

Return Type Justification

Why does the prefix increment operator++ return by reference, but postfix returns by value?

  1. Postfix needs to return the old value before incrementing
  2. Prefix is faster, so it can afford to return a reference
  3. It's arbitrary - both could return the same type
  4. Postfix can't return by reference for syntax reasons

Answer: A - Postfix needs to return the old value before incrementing

Why A is correct:

Prefix (++x) - Returns reference:

Counter& operator++() {
    value++;           // Increment first
    return *this;      // Return reference to modified object
}
// int x = 5; ++x → x is now 6, expression value is 6 (reference to x)

Postfix (x++) - Returns by value:

const Counter operator++(int) {
    Counter old = *this;  // Save old value
    value++;              // Increment
    return old;           // Return COPY of old value
}
// int x = 5; x++ → x is now 6, but expression value is 5 (temporary copy)

Detailed Explanation:

  • Prefix: Increments THEN returns the modified object. Since the object still exists and has been modified, we can safely return a reference to it.
  • Postfix: Must return the OLD value (before increment), but we've already incremented the object. The old value only exists as a local variable (old) which will be destroyed when the function ends. We MUST return a copy, not a reference to local variable.

Why other options are wrong:

  • B: While prefix IS faster (no copy), that's a consequence, not the reason. The reason is semantic - prefix returns the modified object (can be reference), postfix returns old value (must be copy).
  • C: Not arbitrary at all. Postfix MUST return by value because it's returning a local variable. Returning reference to local = undefined behavior.
  • D: Postfix could theoretically return by reference if it didn't need to return the old value, but it DOES need to (that's the definition of postfix increment).

Visual Example:

Counter c(5);
Counter& ref1 = ++c;    // OK: c is now 6, ref1 refers to c (also 6)
Counter val = c++;      // c is now 7, val is a copy holding old value (6)

ref1.print();  // 7 (ref1 refers to c, which is 7)
val.print();   // 6 (val is copy of old value)
c.print();     // 7

Why postfix returns const value: To prevent nonsense like (x++)++. The temporary copy shouldn't be modified.

Question 22

Implementation Comparison (Adapted from Tutorial 3)

Which implementation of operator- (subtraction) is better?

Option A:

Complex operator-(const Complex& a, const Complex& b) {
    Complex result;
    result.real = a.real - b.real;
    result.imag = a.imag - b.imag;
    return result;
}

Option B:

Complex operator-(const Complex& a, const Complex& b) {
    return Complex(a.real - b.real, a.imag - b.imag);
}

Answer: B is better

Why B is better:

  1. Clearer intent: Directly expresses "create and return a new Complex with these values"
  2. Potentially more efficient: Enables compiler optimizations like Return Value Optimization (RVO) or copy elision. The compiler can construct the result directly in the caller's memory.
  3. Fewer lines: More concise without sacrificing readability
  4. Initialization vs Assignment: Uses constructor (initialization) rather than default construction followed by assignment

What's wrong with A:

  • Creates default Complex object first, then assigns values
  • Two steps where one would suffice
  • Harder for compiler to optimize
  • More verbose

Performance Comparison:

Option A:
1. Call default constructor for result (real=0, imag=0)
2. Assign real = a.real - b.real
3. Assign imag = a.imag - b.imag
4. Return result (potentially copy)

Option B:
1. Call parameterized constructor directly with computed values
2. Return result (compiler can optimize away copy with RVO)

Best Practice Pattern:

For binary arithmetic operators that create new objects:

// ✅ GOOD: Direct construction
Type operator+(const Type& a, const Type& b) {
    return Type(a.data + b.data);
}

// ❌ AVOID: Default construct then modify
Type operator+(const Type& a, const Type& b) {
    Type result;
    result.data = a.data + b.data;
    return result;
}

Exception: If computation is complex, Option A style might be clearer:

Matrix operator*(const Matrix& a, const Matrix& b) {
    Matrix result(a.rows, b.cols);
    // Complex nested loop calculation...
    return result;
}
Question 23

Memory Management in Assignment Operator

What is the correct order of operations in an assignment operator with dynamic memory?

  1. Check self-assignment → Delete old memory → Copy new data → Allocate new memory
  2. Delete old memory → Allocate new memory → Check self-assignment → Copy new data
  3. Check self-assignment → Allocate new memory → Delete old memory → Copy new data
  4. Check self-assignment → Delete old memory → Allocate new memory → Copy new data

Answer: D - Check self-assignment → Delete old memory → Allocate new memory → Copy new data

Why D is correct:

This is the correct sequence for the classic copy-and-swap idiom:

MyClass& operator=(const MyClass& other) {
    // 1. Check self-assignment (FIRST!)
    if (this != &other) {

        // 2. Delete old memory
        delete[] data;

        // 3. Allocate new memory
        size = other.size;
        data = new int[size];

        // 4. Copy new data
        for (int i = 0; i < size; i++) {
            data[i] = other.data[i];
        }
    }
    return *this;
}

Step-by-Step Reasoning:

  1. Step 1 - Self-assignment check MUST be first:
    • If obj = obj, and we delete our memory, we also delete other's memory (they're the same!)
    • Must check before doing ANYTHING destructive
  2. Step 2 - Delete old memory:
    • Prevents memory leak
    • Safe because we've ruled out self-assignment
  3. Step 3 - Allocate new memory:
    • Create space for the new data
    • Size based on other.size
  4. Step 4 - Copy data:
    • Deep copy from other to this

Why other options are wrong:

  • A: Can't copy new data before allocating memory - where would you copy it to?
  • B: Deleting before self-assignment check is DISASTER - you delete the source data!
  • C: Allocating before deleting causes memory leak (old memory never freed) and wastes memory (briefly have both old and new allocated)

What happens with wrong order B:

// WRONG ORDER B
MyClass& operator=(const MyClass& other) {
    delete[] data;     // Delete our memory
    // If self-assignment (obj = obj):
    // other.data is NOW DELETED! (same object)

    data = new int[other.size];  // other.size is GARBAGE!
    // CRASH or random behavior
}

Advanced: Copy-and-Swap Idiom (Exception-Safe):

MyClass& operator=(const MyClass& other) {
    if (this != &other) {
        MyClass temp(other);  // Copy construct
        swap(temp);           // Swap with temp
    }  // temp destroyed (deletes old data)
    return *this;
}

// Return *this by reference to enable chaining

Tutorial Question - Input Stream Operator (Adapted from Tutorial 4)

Implement operator>> for reading a Time object in format HH:MM (e.g., "14:30").

class Time {
public:
    Time() : hours(0), minutes(0) {}

    // TODO: Declare friend operator>>

    void print() {
        cout << hours << ":" << minutes;
    }

private:
    int hours, minutes;
};

Answer:

class Time {
public:
    Time() : hours(0), minutes(0) {}

    // Friend declaration
    friend istream& operator>>(istream& is, Time& t);

    void print() {
        cout << hours << ":" << minutes;
    }

private:
    int hours, minutes;
};

// Friend function definition
istream& operator>>(istream& is, Time& t) {
    char colon;  // To read the ':' separator
    is >> t.hours >> colon >> t.minutes;
    return is;
}

Detailed Explanation:

  1. Signature:
    • istream& - reference to input stream (cin, file stream, etc.)
    • Time& - non-const reference (we're modifying it with input)
    • Returns istream& to enable chaining
  2. Must be friend: Input operator CANNOT be a member because the left operand is istream, not Time
  3. Implementation:
    • Read hours (integer)
    • Read colon character (discarded)
    • Read minutes (integer)
    • Return stream reference for chaining

Usage Example:

Time t1, t2;
cout << "Enter time 1 (HH:MM): ";
cin >> t1;        // User enters: 14:30

cout << "Enter time 2 (HH:MM): ";
cin >> t2;        // User enters: 09:15

// Chaining works:
cin >> t1 >> t2;  // Read both in one line

Important Notes:

  • Parameter must be non-const: We're MODIFYING the object with input data
  • Return type must be istream&: Enables chaining: cin >> t1 >> t2
  • Error handling: In production code, check is.fail() to handle bad input

With Error Handling:

istream& operator>>(istream& is, Time& t) {
    char colon;
    is >> t.hours >> colon >> t.minutes;

    // Validate input
    if (colon != ':' || t.hours < 0 || t.hours > 23 ||
        t.minutes < 0 || t.minutes > 59) {
        is.setstate(ios::failbit);  // Mark stream as failed
    }

    return is;
}

Why friend, not member?

If member:  cin.operator>>(t)  ❌ Can't add members to istream
If friend:  operator>>(cin, t)  ✅ Free function with access

EO1-Style Implementation Question

Complete the implementation of the operator+ for a Matrix class that adds two matrices. Assume matrices have the same dimensions.

class Matrix {
public:
    Matrix(int r, int c) : rows(r), cols(c) {
        data = new int*[rows];
        for (int i = 0; i < rows; i++) {
            data[i] = new int[cols];
            for (int j = 0; j < cols; j++)
                data[i][j] = 0;
        }
    }

    // TODO: Implement operator+

    ~Matrix() {
        for (int i = 0; i < rows; i++)
            delete[] data[i];
        delete[] data;
    }

private:
    int** data;
    int rows, cols;

    friend Matrix operator+(const Matrix& a, const Matrix& b);
};

Answer:

Matrix operator+(const Matrix& a, const Matrix& b) {
    // Create result matrix with same dimensions
    Matrix result(a.rows, a.cols);

    // Add corresponding elements
    for (int i = 0; i < a.rows; i++) {
        for (int j = 0; j < a.cols; j++) {
            result.data[i][j] = a.data[i][j] + b.data[i][j];
        }
    }

    return result;
}

Detailed Explanation:

  1. Signature:
    • Returns Matrix by value (new object)
    • Takes both operands as const references (not modifying them)
    • Friend function to access private members
  2. Create result: Matrix result(a.rows, a.cols) allocates 2D array via constructor
  3. Add elements: Nested loop adds corresponding elements from a and b
  4. Return: Return new matrix (copy or move)

Why Friend Function:

  • Needs access to private data, rows, cols
  • Non-member allows symmetric conversion (if there were implicit constructors)
  • More natural syntax: operator+(a, b) rather than a.operator+(b)

Usage Example:

Matrix m1(2, 2), m2(2, 2);

// Fill m1
m1.data[0][0] = 1; m1.data[0][1] = 2;
m1.data[1][0] = 3; m1.data[1][1] = 4;

// Fill m2
m2.data[0][0] = 5; m2.data[0][1] = 6;
m2.data[1][0] = 7; m2.data[1][1] = 8;

Matrix m3 = m1 + m2;

// Result:
// m3.data[0][0] = 6  m3.data[0][1] = 8
// m3.data[1][0] = 10 m3.data[1][1] = 12

Important Considerations:

  • Memory management: The result's constructor allocates memory, destructor deallocates it
  • Assumption: We assume dimensions match. Production code should check: if (a.rows != b.rows || a.cols != b.cols) throw exception;
  • Deep copy on return: The result matrix is properly deep-copied when returned (via copy constructor)

Common Mistakes to Avoid:

    Matrix result;  // Calls default constructor (doesn't exist!)
    // ...
}

// ❌ WRONG - returns reference to local variable

    Matrix result(a.rows, a.cols);

    return result;  // DANGER! result destroyed after return
