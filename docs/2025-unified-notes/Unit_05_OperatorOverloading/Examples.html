Example 1: Money Class with Arithmetic Operators

This example implements a Money class that represents dollar amounts. We'll overload +, -, and == operators as friend functions to enable symmetric type conversion.

Problem Statement

Create a class to represent money amounts with dollars and cents. The class should support:

  • Adding two money amounts together
  • Subtracting one amount from another
  • Comparing two amounts for equality

Solution Strategy

Step 1: Design the Class

We need two private members: dollars and cents. We'll use friend functions so both m1 + m2 and m1 + 100 work (symmetric conversion).

Step 2: Handle Cents Overflow

When adding or subtracting, cents might exceed 99 or go negative. We convert everything to total cents, perform the operation, then convert back to dollars and cents.

Step 3: Return Appropriate Types

Arithmetic operators (+, -) return a new Money object by value. The equality operator (==) returns bool.

Experiments to Try

🔬 Experiment 1: Change the operators from friend functions to member functions. What breaks?

What changes: You'd need to rewrite as: Money operator+(const Money& other) const inside the class.

What breaks: Symmetric conversion. m1 + 5 might work (if there's a Money(int) constructor), but 5 + m1 won't compile because the compiler tries to call 5.operator+(m1), which doesn't make sense.

Why friend is better: Friend functions treat both operands equally, enabling conversion on either side.

🔬 Experiment 2: What if you forget to handle negative amounts in the operators?

What happens: Subtracting a larger amount from smaller (like Money(5, 0) - Money(10, 0)) gives incorrect results.

Why: Without the abs() and sign handling, negative total cents would produce wrong dollar/cent separation. For example, -500 cents would become -5 dollars and 0 cents instead of -5 dollars and 0 cents properly.

Fix: Always use abs() for division/modulo, then restore the sign afterward.

🔬 Experiment 3: Try adding Money(int totalDollars) constructor and use m1 + 100. Does it work?

What happens: Both m1 + 100 and 100 + m1 work!

Why: The compiler can convert 100 to Money(100) automatically. Since we used friend functions, conversion works on both sides.

Add this constructor:

Money(int totalDollars) : dollars(totalDollars), cents(0) {}

🔬 Experiment 4: What if operator== was a member function instead?

What happens: It still works fine for most cases.

Why: Comparison doesn't usually need symmetric conversion. You rarely write 100 == m1. Member function bool operator==(const Money& other) const would work perfectly for m1 == m2.

Best practice: Friend is still preferred for consistency, but member works here.

🔬 Experiment 5: Remove the const from operator+ parameters. Does it still compile?

What happens: It compiles, but you can't pass temporary objects or const objects.

Example that breaks: Money total = Money(10, 0) + Money(5, 0); - temporaries can't bind to non-const references in some contexts.

Best practice: Always use const& for parameters you're not modifying. It's more efficient and flexible.

In One Punch Man (an anime where heroes are ranked by class and strength), heroes are categorized from C-Class (weakest) to S-Class (strongest). Let's create a Hero class with comparison operators to rank heroes properly.

Problem Statement

Solution Strategy

Step 1: Rank Hierarchy

S-Class beats A-Class regardless of power level. Within the same class, higher power level wins.

Step 2: Comparison Logic

First compare ranks. If ranks are equal, compare power levels. This creates a hierarchical ordering.

Step 3: Implement All Comparisons

Once we have < and ==, we can derive >, <=, >=, and != from them.

Experiments to Try

🔬 Experiment 1: Implement operator!= and operator<=. How can you derive them from existing operators?

Implementation:

bool operator!=(const Hero& h1, const Hero& h2) {
    return !(h1 == h2);  // NOT equal
}

bool operator<=(const Hero& h1, const Hero& h2) {
    return (h1 < h2) || (h1 == h2);  // Less than OR equal
}

Why this works: You only need to implement < and ==. All other comparisons can be built from these two primitives.

🔬 Experiment 2: What happens if you forget to check rank first and only compare power levels?

What breaks: A C-Class hero with power 1000 would rank higher than an S-Class hero with power 50.

Example: Mumen Rider (C-Class, 1000 power) would be stronger than Genos (S-Class, 85 power), which is wrong!

Fix: Always compare primary criterion first (rank), then secondary (power level) only if primary is equal.

🔬 Experiment 3: Why is operator> implemented as return h2 < h1?

Logic: If h1 > h2, then h2 < h1. It's the reverse relationship!

Why do this: Avoids duplicating logic. We've already written the comparison logic in operator<. Reusing it prevents bugs and inconsistencies.

Best practice: Implement < and == with full logic. Derive all others from these two.

Example 3: Tutoring Session Tracker with Stream Operators

Let's create a Session class for Swift Tuition that tracks tutoring sessions. We'll implement stream operators (<< and >>) and the += operator to add minutes to a session.

Problem Statement

Create a class to track tutoring sessions with student name, subject, and duration. Support:

  • Reading session data from input (cin >> session)
  • Writing session data to output (cout << session)
  • Adding extra time to a session (session += 30 for 30 more minutes)

Solution Strategy

Step 1: Stream Input (>>)

Must be a friend function. Takes istream& and Session& (non-const). Returns istream& for chaining.

Step 2: Stream Output (<<)

Also friend. Takes ostream& and const Session&. Returns ostream&.

Step 3: Compound Assignment (+=)

Member function. Modifies the calling object, returns *this by reference.

Experiments to Try

🔬 Experiment 1: What happens if operator<< returns void instead of ostream&?

What breaks: Chaining stops working. cout << s1 << endl won't compile.

Why: (cout << s1) would return void, and you can't apply << endl to void.

Error message: "no match for operator<< (operand types are 'void' and ...)"

🔬 Experiment 2: Why is the Session& parameter const in operator<< but NOT in operator>>?

Output (<<): We're only reading the session to print it. The session doesn't change, so it's const.

Input (>>): We're modifying the session by reading into it. Can't be const because we change its values.

Rule: Reading = const, Writing/Modifying = non-const.

🔬 Experiment 3: Why does operator+= return Session& instead of void?

Enables chaining: s1 += 10 += 20 works because each += returns the modified object.

Mimics built-in behavior: For int x = 5; x += 3 += 2;, the result is 10 (x = 5 + 3 + 2). Our operator should behave the same way.

Standard practice: All compound assignment operators (+=, -=, *=) return *this by reference.

🔬 Experiment 4: Implement operator+ using operator+=. How would you do it?

Implementation:

// Friend function
Session operator+(const Session& s, int minutes) {
    Session result = s;  // Copy the session
    result += minutes;   // Use += to add minutes
    return result;       // Return new session
}

Why this pattern: We implement += first (modifies object), then build + on top of it (creates new object). Avoids duplicating logic.

Common pattern: Implement +=, -=, etc. as members. Implement +, - as friends using the compound operators.

🔬 Experiment 5: Why must stream operators be friend functions and not member functions?

The problem with member functions: For cout << session, the left operand is cout (an ostream), not session.

If it were a member: We'd need ostream::operator<<(Session), which means modifying the ostream class. We can't do that - it's in the standard library!

Friend solution: operator<<(ostream&, Session&) is a free function we control, but it has access to Session's private members.

Bug #1: operator+ has wrong denominator calculation

Location: Line 23

What's wrong: result.denominator = f1.denominator; should be result.denominator = f1.denominator * f2.denominator;

Why it's wrong: When adding fractions, the denominator should be the product of both denominators. The code only uses one denominator.

Impact: 1/2 + 1/3 = 5/2 (wrong!) instead of 5/6 (correct)

Bug #2: operator+= doesn't return anything

Location: Line 14

What's wrong: Function should return *this but has no return statement (and no return type!)

Why it's wrong: Compound assignment operators should return a reference to the modified object for chaining.

Fix: Change signature to Fraction& operator+=(const Fraction& other) and add return *this;

Bug #3: operator== modifies its parameter

Location: Line 28-29

What's wrong: The function modifies f2 during comparison, and f2 is not const

Why it's wrong: Comparison should never modify operands! Also, the parameter should be const Fraction& f2.

Fix: Use cross-multiplication without modifying: return (f1.numerator * f2.denominator == f2.numerator * f1.denominator);

Bug #4: operator<< returns void

Location: Line 33

What's wrong: Returns void instead of ostream&

Why it's wrong: Breaks chaining. Can't write cout << f1 << endl;

Fix: Change to ostream& operator<<(ostream& os, const Fraction& f) and add return os;

Fraction operator+(const Fraction& f1, const Fraction& f2) {
    Fraction result;
    result.numerator = f1.numerator * f2.denominator + f2.numerator * f1.denominator;
    result.denominator = f1.denominator * f2.denominator;  // FIX
    return result;
}

bool operator==(const Fraction& f1, const Fraction& f2) {  // FIX: const
    // FIX: Don't modify, use cross-multiplication
    return (f1.numerator * f2.denominator == f2.numerator * f1.denominator);
}

ostream& operator<<(ostream& os, const Fraction& f) {  // FIX: return type
    os << f.numerator << "/" << f.denominator;
    return os;  // FIX: return statement
}
