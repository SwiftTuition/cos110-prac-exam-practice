Question 1

Inline Member Functions

True or False: Inline member functions work against the principle of separating interface and implementation.

Justify your answer.

Answer: True

Detailed Justification:

When you define a member function as inline (either explicitly with the inline keyword or implicitly by defining it inside the class declaration), the function body must appear in the header file. This means the implementation details are exposed to anyone who includes the header.

The principle of separation: Good software design separates the interface (what the class can do) from the implementation (how it does it). Typically:

  • Header file (.h): Contains class declaration with function prototypes (interface)
  • Implementation file (.cpp): Contains function definitions (implementation)

Why inline violates this: Inline functions require their implementation to be visible at compile time (in the header), so the compiler can substitute the function code directly. This exposes implementation details that should be hidden.

Example:

class Student {
private:
    int id;
public:
    int getID() const { return id; }  // Inline - implementation in header
};

Trade-off: Inline functions can improve performance for small functions by avoiding function call overhead, but they sacrifice encapsulation and increase header file dependencies.

Question 2

Multiple Choice: Default Constructor

Which statement about default constructors is correct?

  1. C++ always provides a default constructor, even if you define other constructors
  2. A default constructor must initialize all member variables to zero
  3. If you define any constructor, C++ will not provide a default constructor automatically
  4. Default constructors cannot use initialization lists

Answer: C - If you define any constructor, C++ will not provide a default constructor automatically

Why C is correct:

C++ provides a default constructor (one that takes no parameters) automatically only if you haven't defined any constructors. Once you define even a single parameterized constructor, C++ assumes you want control over object construction and stops generating a default constructor. If you want both, you must write both explicitly.

Example:

class Student {
public:
    Student(int id) { }  // Parameterized constructor defined
};

int main() {
    Student s1(100);  // OK
    Student s2;       // ERROR - no default constructor
}

Why other options are wrong:

  • A: Incorrect. C++ only provides a default constructor if you define NO constructors. Once you define any constructor (even a parameterized one), the automatic default constructor is not generated.
  • B: Incorrect. A default constructor doesn't have to initialize anything to zero. The compiler-generated default constructor calls default constructors of member objects but leaves primitive types (int, double) uninitialized (garbage values). You can write a default constructor that initializes members to any values you want.
  • D: Incorrect. Default constructors CAN and SHOULD use initialization lists. Example: Student() : id(0), gpa(0.0) { }
Question 3

Code Tracing: Constructor Execution

What is the output of the following code?

#include 
using namespace std;

class Test {
private:
    int value;
public:
    Test() : value(0) {
        cout << "A";
    }

    Test(int v) : value(v) {
        cout << "B";
    }

    ~Test() {
        cout << "C";
    }
};

int main() {
    Test t1;
    Test t2(5);
    return 0;
}

Output:

ABCC

Line-by-Line Trace:

  1. Line: Test t1; → Calls default constructor Test() → Outputs: "A" → Variables: value = 0
  2. Line: Test t2(5); → Calls parameterized constructor Test(int v) with v=5 → Outputs: "B" → Variables: value = 5
  3. Line: return 0; → main() ends, local objects destroyed in reverse order (LIFO)
  4. Destruction of t2: → Calls ~Test() for t2 → Outputs: "C"
  5. Destruction of t1: → Calls ~Test() for t1 → Outputs: "C"

Why this output?

  • Constructors run in the order objects are created: t1 first ("A"), then t2 ("B")
  • Destructors run in reverse order (LIFO - Last In, First Out): t2 destroyed first ("C"), then t1 ("C")
  • Total output: "A" + "B" + "C" + "C" = "ABCC"

Key Concept: Local objects are destroyed in reverse order of their construction. This is important for managing dependencies between objects.

Question 4

Find the Bug: Private Member Access

The following code has a compilation error. Identify the line number and explain the error.

class Person {
    string name;
    int age;
public:
    Person(string n, int a) : name(n), age(a) { }
    void display() const {
        cout << name << ", " << age << endl;
    }
};

int main() {
    Person p("Alice", 25);
    p.age = 30;
    p.display();
    return 0;
}

Bug Location: Line 13 - p.age = 30;

What's Wrong:

The code attempts to access the private member variable age from outside the class (in main()). This violates encapsulation.

Why It's Wrong:

In the Person class, name and age are declared without an access specifier. In a class (as opposed to a struct), members are private by default. Private members can only be accessed by member functions of the class, not from outside code.

Compiler Error Message:

"'int Person::age' is private within this context"

How to Fix:

Option 1: Make age public (bad practice - breaks encapsulation):

class Person {
    string name;
public:
    int age;  // Now public
    // ...
};

Option 2 (Better): Add a public setter method:

class Person {
    string name;
    int age;
public:
    Person(string n, int a) : name(n), age(a) { }

    void setAge(int a) {
        if (a > 0 && a < 150) {  // Validation
            age = a;
        }
    }

    void display() const {
        cout << name << ", " << age << endl;
    }
};

int main() {
    Person p("Alice", 25);
    p.setAge(30);  // Use setter
    p.display();
    return 0;
}

Why the fix works: By using a setter function, we maintain encapsulation (age is still private) and can add validation to ensure age is reasonable. This is the correct object-oriented approach.

Question 5

Multiple Choice: Copy Constructor

When is a copy constructor called?

  1. Only when you use the assignment operator (=)
  2. When passing an object by reference to a function
  3. When initializing a new object from an existing object
  4. When deleting an object with the delete keyword

Answer: C - When initializing a new object from an existing object

Why C is correct:

The copy constructor is called in three situations:

  1. When initializing a new object from an existing object: Student s2 = s1; or Student s2(s1);
  2. When passing an object by value to a function
  3. When returning an object by value from a function

Examples:

Student s1("Alice", 123);
Student s2 = s1;        // Copy constructor called
Student s3(s1);         // Copy constructor called

void func(Student s) { } // Copy constructor when calling func(s1)
func(s1);

Why other options are wrong:

  • A: Incorrect. The assignment operator (=) is different from initialization. When you write Student s2 = s1; during declaration, it's initialization (copy constructor). But s2 = s1; after both objects exist is assignment (assignment operator, covered in Unit 4). The copy constructor is for creating a new object from an existing one, not for assigning to an already-existing object.
  • B: Incorrect. When passing by reference (const Student&), NO copy is made. The function receives a reference to the original object. The copy constructor is only called when passing by VALUE.
  • D: Incorrect. The delete keyword calls the destructor, not the copy constructor. Destructors clean up resources when an object is destroyed.

Key Distinction: Copy constructor creates a NEW object. Assignment operator modifies an EXISTING object.

Question 6

const Member Functions

What happens if you try to modify a member variable inside a const member function?

  1. The code compiles but gives a runtime warning
  2. The code compiles fine with no issues
  3. Compilation error: cannot modify member in const function
  4. The member variable becomes const permanently

Answer: C - Compilation error: cannot modify member in const function

Why C is correct:

A const member function promises not to modify the object. If you try to modify any member variable inside a const function, the compiler will reject the code with an error like "assignment of member 'Class::member' in read-only object".

Example:

class Counter {
private:
    int count;
public:
    void increment() const {
        count++;  // COMPILATION ERROR
    }
};

Why other options are wrong:

  • A: Incorrect. This is a compilation error, not a runtime warning. The compiler catches this violation immediately.
  • B: Incorrect. The code will NOT compile. The const qualifier is enforced at compile time.
  • D: Incorrect. The member variable doesn't become permanently const. The const on the function only applies within that function's scope. Other non-const functions can still modify the member.

Exception - mutable keyword:

If you need to modify a member in a const function (e.g., for caching or counting), you can declare it mutable:

class Counter {
private:
    mutable int callCount;  // Can be modified even in const functions
public:
    int getValue() const {
        callCount++;  // OK now
        return value;
    }
};

Question 7

Deep vs Shallow Copy

True or False: The default copy constructor provided by C++ performs a deep copy of all member variables, including dynamically allocated memory.

Justify your answer.

Answer: False

Detailed Justification:

The default copy constructor provided by C++ performs a shallow copy, not a deep copy. This means it copies member variables directly, bit-by-bit. For pointer members, it copies the pointer value (the memory address), not the data the pointer points to.

What happens with shallow copy:

class IntArray {
private:
    int* data;
    int size;
public:
    IntArray(int s) : size(s) {
        data = new int[size];
    }
    // No custom copy constructor - uses default shallow copy
};

int main() {
    IntArray arr1(5);
    IntArray arr2 = arr1;  // Shallow copy!
    // Both arr1.data and arr2.data point to SAME array
}

The problem:

  • Both arr1 and arr2 have their own size variable (value copied correctly)
  • But both data pointers point to the SAME dynamically allocated array
  • When arr2 is destroyed, it calls delete[] data
  • When arr1 is destroyed, it tries to delete[] the same memory again → crash!

The solution - Deep copy:

Write a custom copy constructor that allocates new memory and copies the values:

IntArray(const IntArray& other) : size(other.size) {
    data = new int[size];  // Allocate NEW memory
    for (int i = 0; i < size; i++) {
        data[i] = other.data[i];  // Copy VALUES
    }
}

Key Concept: If your class has ANY pointer members allocated with new, you MUST write a custom copy constructor to perform deep copying. The default shallow copy will cause crashes and undefined behavior.

Question 8

Static Member Initialization

Which of the following correctly initializes a static member variable?

  1. class Student { static int count = 0; };
  2. class Student { static int count; }; in header, then Student::count = 0; in main()
  3. class Student { static int count; }; in header, then int Student::count = 0; in .cpp file
  4. Static members don't need initialization

Answer: C - Declare in header, initialize in .cpp with int Student::count = 0;

Why C is correct:

Static member variables must be initialized outside the class definition. The proper approach is:

  1. Declare in the class (header file): static int count;
  2. Initialize outside the class (in .cpp file or before main()): int Student::count = 0;

Example:

// Student.h
class Student {
private:
    static int count;  // Declaration
public:
    Student() { count++; }
};

// Student.cpp
int Student::count = 0;  // Initialization (note: includes type)

Why other options are wrong:

  • A: Incorrect. You cannot initialize static members inside the class definition (except for static const integral types). This will cause a compilation error: "ISO C++ forbids in-class initialization of non-const static member".
  • B: Incorrect. You cannot initialize static members in main(). By the time main() runs, the static member must already be initialized. Also, trying to do Student::count = 0; in main() would be assignment, not initialization, and would fail if count is private.
  • D: Incorrect. Static members DO need initialization. If you don't initialize them, you'll get a linker error: "undefined reference to Student::count". The linker expects to find exactly one definition of the static member across all translation units.

Special case - static const integral types:

You CAN initialize these in-class:

class Student {
    static const int MAX_STUDENTS = 100;  // OK for const integral types
};

Code Tracing: Initialization List

What is the output?

#include 
using namespace std;

class Point {
private:
    int x;
    int y;
public:
    Point(int a, int b) : x(a), y(a + b) {
        cout << x << "," << y << " ";
    }
};

int main() {
    Point p1(2, 3);
    Point p2(5, 5);
    return 0;
}

Output:

2,5 5,10

Line-by-Line Trace:

  1. Line: Point p1(2, 3);
    • Calls Point(int a, int b) with a=2, b=3
    • Initialization list executes: x(a) sets x = 2
    • Then: y(a + b) sets y = 2 + 3 = 5
    • Constructor body executes: cout << x << "," << y << " ";
    • Outputs: "2,5 "
    • Variables after construction: p1.x = 2, p1.y = 5
  2. Line: Point p2(5, 5);
    • Calls Point(int a, int b) with a=5, b=5
    • Initialization list: x = 5, y = 5 + 5 = 10
    • Outputs: "5,10 "
    • Variables after construction: p2.x = 5, p2.y = 10
  3. Total output: "2,5 " + "5,10 " = "2,5 5,10 "

Key Concepts:

  • Initialization lists execute BEFORE the constructor body
  • You can use expressions in initialization lists: y(a + b) evaluates to y(2 + 3)
  • Each object construction prints its x and y values during construction
Question 10

Destructor Behavior

In what order are destructors called for local objects?

  1. In the order the objects were created (FIFO)
  2. In reverse order of creation (LIFO)
  3. In random order determined by the compiler
  4. All destructors are called simultaneously

Answer: B - In reverse order of creation (LIFO - Last In, First Out)

Why B is correct:

Local objects are destroyed in reverse order of their construction when they go out of scope. This is a stack-based (LIFO) destruction order. The last object created is the first to be destroyed.

Example:

class Test {
    int id;
public:
    Test(int i) : id(i) {
        cout << "Construct " << id << endl;
    }
    ~Test() {
        cout << "Destruct " << id << endl;
    }
};

int main() {
    Test t1(1);
    Test t2(2);
    Test t3(3);
    return 0;
}

// Output:
// Construct 1
// Construct 2
// Construct 3
// Destruct 3    <- t3 destroyed first
// Destruct 2    <- t2 destroyed second
// Destruct 1    <- t1 destroyed last

Why this matters:

  • If object A depends on object B, you should create B first, then A. This ensures A is destroyed before B.
  • Example: If a Database object and a Connection object exist, and Connection uses Database, create Database first. When scope ends, Connection is destroyed before Database, preventing use-after-free errors.

Why other options are wrong:

  • A: Incorrect. FIFO (First In, First Out) would mean the first object created is destroyed first. This is NOT how C++ works. C++ uses LIFO.
  • C: Incorrect. The order is deterministic, not random. It's always reverse order of construction.
  • D: Incorrect. Destructors are called one at a time in a specific order, not simultaneously.

Technical reason: Local objects are allocated on the stack. The stack is a LIFO data structure. When a scope ends, the stack unwinds in reverse order, calling destructors as objects are popped off.

Question 11

this Pointer

What does the this pointer represent inside a member function?

  1. A reference to the class itself
  2. A pointer to the current object
  3. A pointer to the base class
  4. The address of the member function

Answer: B - A pointer to the current object

Why B is correct:

The this pointer is an implicit pointer available in all non-static member functions. It points to the object that called the function. Type: ClassName* const this (a constant pointer to the object).

Common uses:

  1. Disambiguating parameters from members:
    2. class Student {
    int id;
public:
    void setID(int id) {
        this->id = id;  // this->id is member, id is parameter
    }
};
  2. Returning the current object (for chaining):
    3. class Student {
public:
    Student& setName(string n) {
        name = n;
        return *this;  // Return object itself (not pointer)
    }
};

// Allows chaining:
student.setName("Alice").setAge(20).setGPA(3.8);
  3. Passing current object to another function:
    4. void register(Student* s);

class Student {
public:
    void enroll() {
        registerStudent(this);  // Pass pointer to current object
    }
};

Why other options are wrong:

  • A: Incorrect. this is a POINTER, not a reference. It points to a specific object instance, not the class itself. The class is a blueprint; this points to a concrete object created from that blueprint.
  • C: Incorrect. this points to the current object of the current class, not the base class. In inheritance, this points to the derived class object.
  • D: Incorrect. this points to the object (data), not to the function (code). Member functions are shared across all objects; this tells the function which object's data to operate on.

Important distinction:

  • this → pointer to the object (type: ClassName*)
  • *this → the object itself (type: ClassName)
  • this->member → access member via pointer
Question 12

Find the Bug: Static Function Error

The following code has a compilation error. Identify what's wrong and explain how to fix it.

class Book {
private:
    static int totalBooks;
    string title;
public:
    Book(string t) : title(t) {
        totalBooks++;
    }

    static int getTotalBooks() {
        return totalBooks + title.length();
    }
};

int Book::totalBooks = 0;

Bug Location: Line 10 - return totalBooks + title.length();

What's Wrong:

The static function getTotalBooks() attempts to access the non-static member title. This is illegal.

Why It's Wrong:

Static member functions don't have a this pointer because they're not associated with any specific object. They belong to the class itself. Since title is a non-static member (each object has its own title), a static function can't access it without knowing which object's title to use.

Compiler Error:

"invalid use of member 'Book::title' in static member function"

What static functions CAN access:

  • Other static members (variables and functions)
  • Local variables within the function
  • Global variables

What static functions CANNOT access:

  • Non-static member variables (title)
  • Non-static member functions
  • The this pointer (they don't have one)

How to Fix:

Option 1: Remove the problematic code (just return totalBooks):

static int getTotalBooks() {
    return totalBooks;  // OK - totalBooks is static
}

Option 2: Make the function non-static if you need to access title:

int getTitleLength() {  // Not static
    return title.length();  // OK now
}

Option 3: Pass an object as a parameter:

static int getBookInfo(const Book& book) {
    return totalBooks + book.title.length();  // Access via parameter
}

Why the fix works: By removing access to non-static members, the static function only uses data available to it (static members that belong to the class, not to specific objects).

Question 13

Memory Management: What's the Output?

What is the output of this code?

#include 
using namespace std;

class Array {
private:
    int* data;
public:
    Array(int size) {
        data = new int[size];
        cout << "A";
    }

    Array(const Array& other) {
        data = other.data;
        cout << "B";
    }

    ~Array() {
        delete[] data;
        cout << "C";
    }
};

int main() {
    Array arr1(5);
    Array arr2 = arr1;
    return 0;
}

Output (before crash):

ABC

Then: Runtime error (crash or undefined behavior)

Line-by-Line Trace:

  1. Line: Array arr1(5); → Calls constructor → Allocates memory → Outputs: "A" → arr1.data points to new array
  2. Line: Array arr2 = arr1; → Calls copy constructor → Shallow copy: arr2.data = arr1.data → Outputs: "B" → Both point to SAME array
  3. Line: return 0; → Destructors called in reverse order
  4. Destruction of arr2: → Calls destructor → delete[] data; frees the array → Outputs: "C"
  5. Destruction of arr1: → Calls destructor → delete[] data; tries to free SAME array again → CRASH!

The Problem - Double Delete:

The copy constructor performs a shallow copy (data = other.data;), so both arr1 and arr2 point to the same dynamically allocated array. When arr2 is destroyed, it frees the memory. When arr1 is destroyed, it tries to free the same memory again, causing undefined behavior (usually a crash).

Visual Representation:

After arr2 = arr1 (shallow copy):
arr1.data ----\
               \
                v
          [Memory Block]
                ^
               /
arr2.data ----/

Both point to same memory!

When arr2 destructor runs:
arr2.data ----> [FREED MEMORY]

When arr1 destructor runs:
arr1.data ----> [FREED MEMORY]  <- Double delete!

The Fix - Deep Copy:

Array(const Array& other) {
    // Allocate NEW memory
    data = new int[other.size];  // (need to store size member)
    // Copy VALUES
    for (int i = 0; i < size; i++) {
        data[i] = other.data[i];
    }
    cout << "B";
}

Key Lesson: This demonstrates why shallow copies are dangerous with dynamic memory. You MUST implement deep copying for classes with pointer members.

Question 14

Initialization List vs Assignment

Which of the following is a valid reason to use an initialization list instead of assignment in the constructor body?

  1. Initialization lists are required for const members and references
  2. Initialization lists make the code longer and more readable
  3. Initialization lists allow you to call non-const functions
  4. Assignment is more efficient than initialization lists

Answer: A - Initialization lists are required for const members and references

Why A is correct:

Initialization lists are REQUIRED (not optional) in these cases:

  1. const members: Must be initialized when created, cannot be assigned later
  2. Reference members: Must be bound to an object when created
  3. Members without default constructors: If a member class has no default constructor, you must use initialization list to pass arguments
  4. Base class initialization (Unit 7): Must use initialization list to pass arguments to base constructor

Example showing requirement:

class Student {
private:
    const int id;          // const member
    string& nameRef;       // reference member
public:
    // WRONG - Won't compile:
    Student(int i, string& n) {
        id = i;           // ERROR: can't assign to const
        nameRef = n;      // ERROR: reference not initialized
    }

    // CORRECT - Must use initialization list:
    Student(int i, string& n) : id(i), nameRef(n) {
        // Now both are properly initialized
    }
};

Why other options are wrong:

  • B: Incorrect. Initialization lists are typically SHORTER, not longer. Compare: 
    // Initialization list (concise):
Student(int i) : id(i), gpa(0.0) { }

// Assignment (more code):
Student(int i) {
    id = i;
    gpa = 0.0;
}
  • C: Incorrect. This has nothing to do with initialization lists. You can call non-const functions in either approach.
  • D: Incorrect. This is backwards. Initialization lists are MORE efficient, not less. With initialization lists, members are constructed directly with the correct values. With assignment, members are first default-constructed, then assigned (two operations instead of one).

Efficiency example:

class Student {
    string name;
public:
    // Initialization list: Direct construction
    Student(string n) : name(n) { }
    // 1. Constructs name with value n

    // Assignment: Default construct then assign
    Student(string n) {
        name = n;
    }
    // 1. Default constructs name ("")
    // 2. Assigns n to name
    // (Two operations instead of one!)
};

Best Practice: Always use initialization lists for ALL members, even when not required. It's more efficient and consistent.

Question 15

Class vs Struct Default Access

What is the default access specifier for members in a class and in a struct?

  1. class: public, struct: public
  2. class: private, struct: private
  3. class: private, struct: public
  4. class: public, struct: private

Answer: C - class: private, struct: public

Why C is correct:

  • In a class, members are private by default
  • In a struct, members are public by default

This is the ONLY difference between class and struct in C++.

Example:

class MyClass {
    int x;      // private by default
    int y;      // private by default
};

struct MyStruct {
    int x;      // public by default
    int y;      // public by default
};

int main() {
    MyClass c;
    c.x = 5;    // ERROR - x is private

    MyStruct s;
    s.x = 5;    // OK - x is public
}

You can override defaults:

class MyClass {
public:        // Explicitly make public
    int x;
    int y;
};

struct MyStruct {
private:       // Explicitly make private
    int x;
    int y;
};

Why other options are wrong:

  • A: Incorrect. If class members were public by default, there would be no point in having classes (they'd be identical to structs).
  • B: Incorrect. Structs have public default access. This is inherited from C, where structs are used for simple data grouping with public access.
  • D: Incorrect. This is backwards (class and struct defaults are swapped).

When to use each:

  • class: Use when you want encapsulation (private data with public methods)
  • struct: Use for simple data containers where all members should be public (like a Point with x, y coordinates)

C++ convention: Most C++ code uses class for OOP types with methods, and reserves struct for plain data structures (POD types).

Question 16

Code Output: Constructor Chaining

What is the output?

#include 
using namespace std;

class Box {
private:
    int width;
    int height;
public:
    Box() : width(0), height(0) {
        cout << "Default ";
    }

    Box(int w) : Box() {
        width = w;
        cout << "Width ";
    }

    Box(int w, int h) : Box(w) {
        height = h;
        cout << "Height ";
    }
};

int main() {
    Box b(5, 10);
    return 0;
}

Output:

Default Width Height

Execution Trace:

  1. Box b(5, 10); calls Box(int w, int h) with w=5, h=10
  2. Initialization list: Box(w) calls Box(int w) with w=5
  3. Initialization list: Box() calls default constructor
  4. Default constructor executes: Sets width=0, height=0, outputs "Default "
  5. Back to Box(int w): Sets width=5, outputs "Width "
  6. Back to Box(int w, int h): Sets height=10, outputs "Height "

This demonstrates constructor delegation (C++11 feature). Constructors can call other constructors in the initialization list, creating a chain.

Final state: b.width = 5, b.height = 10

Note: Constructor delegation is a C++11 feature. In C++98 (which COS 110 uses), you would typically use a private helper function instead.

Question 17

Encapsulation Violation

Which of the following violates the principle of encapsulation?

  1. Declaring all member variables as private
  2. Providing public getter and setter functions
  3. Making member variables public so they can be accessed directly
  4. Using const member functions for accessors

Answer: C - Making member variables public so they can be accessed directly

Why C is correct (violates encapsulation):

Encapsulation means hiding internal data and providing controlled access through methods. Making member variables public breaks encapsulation because:

  • External code can modify data without validation
  • You can't change internal representation later without breaking existing code
  • No way to track or log when data changes
  • Violates the "information hiding" principle

Bad example (public members):

class BankAccount {
public:
    double balance;  // Public - anyone can modify!
};

int main() {
    BankAccount acc;
    acc.balance = -5000.0;  // No validation - negative balance!
}

Good example (encapsulation):

class BankAccount {
private:
    double balance;  // Hidden
public:
    void deposit(double amount) {
        if (amount > 0) {  // Validation
            balance += amount;
        }
    }

    double getBalance() const {
        return balance;
    }
};

Why other options are wrong (they support encapsulation):

  • A: Correct practice. Private members hide implementation details.
  • B: Correct practice. Getters/setters provide controlled access with validation.
  • D: Correct practice. Const functions promise not to modify, supporting safe access.

Benefits of encapsulation:

  • Data validation and error checking
  • Can change internal representation without affecting users
  • Can add logging, debugging, or monitoring
  • Prevents accidental corruption of data

Question 18

Rule of Three

True or False: If a class needs a custom destructor to free dynamic memory, it probably also needs a custom copy constructor and assignment operator.

Justify your answer.

Answer: True

Detailed Justification:

This principle is called the "Rule of Three". If a class manages resources (especially dynamic memory), you need all three:

  1. Destructor: To free the resource
  2. Copy constructor: To properly copy the resource (deep copy)
  3. Assignment operator: To properly assign/replace the resource

Why all three are needed:

If you need a custom destructor, it means you're managing a resource that needs cleanup (like dynamically allocated memory). The default copy constructor and assignment operator do shallow copies, which causes problems:

  • Without custom copy constructor: Two objects share the same resource. When one is destroyed, it frees the resource, leaving the other with a dangling pointer.
  • Without custom assignment operator: Same problem as above, plus memory leaks (old resource not freed before assignment).

Example showing all three:

class IntArray {
private:
    int* data;
    int size;
public:
    // Constructor
    IntArray(int s) : size(s) {
        data = new int[size];
    }

    // 1. Destructor (frees memory)
    ~IntArray() {
        delete[] data;
    }

    // 2. Copy constructor (deep copy)
    IntArray(const IntArray& other) : size(other.size) {
        data = new int[size];
        for (int i = 0; i < size; i++) {
            data[i] = other.data[i];
        }
    }

    // 3. Assignment operator (Unit 4)
    IntArray& operator=(const IntArray& other) {
        if (this != &other) {  // Self-assignment check
            delete[] data;     // Free old memory
            size = other.size;
            data = new int[size];  // Allocate new
            for (int i = 0; i < size; i++) {
                data[i] = other.data[i];  // Copy
            }
        }
        return *this;
    }
};

What happens without all three:

// Only has destructor, missing copy constructor:
IntArray arr1(5);
IntArray arr2 = arr1;  // Shallow copy (both point to same array)
// When arr2 destroyed: delete[] data
// When arr1 destroyed: delete[] data (SAME DATA) -> CRASH!

Modern C++ note: In C++11 and later, this becomes the "Rule of Five" (adds move constructor and move assignment operator).

Question 19

Constructor Parameter Ambiguity

What is the problem with this constructor?

class Student {
private:
    int id;
    double gpa;
public:
    Student(int id, double gpa) {
        id = id;
        gpa = gpa;
    }
};

Problem: Parameter names shadow member variable names, causing self-assignment.

What happens:

Inside the constructor, id refers to the parameter (not the member variable). The line id = id; assigns the parameter to itself, which does nothing. The member variables remain uninitialized (garbage values).

Why this happens:

C++ name resolution rules: When there's a local variable/parameter with the same name as a member, the local name takes precedence. The member is "shadowed" and inaccessible without qualification.

Fix 1: Use this pointer

Student(int id, double gpa) {
    this->id = id;      // this->id is member, id is parameter
    this->gpa = gpa;    // this->gpa is member, gpa is parameter
}

Fix 2: Use initialization list (best practice)

Student(int id, double gpa) : id(id), gpa(gpa) {
    // Initialization list handles the ambiguity correctly
    // Empty body - all work done in initialization list
}

Fix 3: Use different parameter names

Student(int studentID, double studentGPA) {
    id = studentID;
    gpa = studentGPA;
}

Why initialization list is best:

  • More efficient (direct initialization vs default + assignment)
  • Required for const/reference members
  • Handles name ambiguity automatically
  • Shorter, cleaner code

Common mistake indicator: If you see name = name; in a constructor, it's almost always wrong.

Source: This appears in EO1 2025, Question 4 (ambiguity between local and member variables)
Question 20

Static vs Non-Static

How many copies of a static member variable exist if you create 100 objects of a class?

  1. 100 copies (one per object)
  2. 1 copy (shared by all objects)
  3. 0 copies (static members don't exist)
  4. Depends on the compiler

Answer: B - 1 copy (shared by all objects)

Why B is correct:

Static member variables belong to the CLASS, not to individual objects. No matter how many objects you create (0, 1, 100, or 1000), there is exactly ONE copy of each static member, shared by all instances.

Visual representation:

Non-static members (regular):
Object 1: [name="Alice", id=1]
Object 2: [name="Bob", id=2]
Object 3: [name="Carol", id=3]
→ Each object has its own copy

Static member:
Class Student: [static count=3]
                      ↑
                      |
All objects share this ONE variable

Example:

class Student {
private:
    static int totalStudents;  // ONE copy for entire class
    string name;               // Each object has its own
public:
    Student(string n) : name(n) {
        totalStudents++;  // All objects modify SAME variable
    }

    static int getTotal() {
        return totalStudents;  // Returns the shared count
    }
};

int Student::totalStudents = 0;  // Single initialization

int main() {
    // Create 100 students
    Student* students[100];
    for (int i = 0; i < 100; i++) {
        students[i] = new Student("Student" + to_string(i));
    }

    cout << Student::getTotal();  // Outputs: 100
    // Only ONE totalStudents variable, incremented 100 times
}

Why other options are wrong:

  • A: Incorrect. This describes non-static members. Each object has its own copy of non-static members, but static members are shared.
  • C: Incorrect. Static members DO exist - they're allocated in static storage (like global variables), not on the heap or stack with objects.
  • D: Incorrect. This is specified by the C++ standard. ALL compilers must implement static members as shared class-level variables.

Memory location: Static members are stored in the data segment (like global variables), not with each object's memory.

Access: Can be accessed via class name (Student::totalStudents) or via any object (s1.totalStudents), but there's still only one copy.

Question 21

const Correctness with Objects

Given:

class Point {
private:
    int x, y;
public:
    void setX(int val) { x = val; }
    int getX() const { return x; }
    void display() { cout << x << "," << y; }
};

void printPoint(const Point& p) {
    p.display();
}

Will this code compile?

Answer: No, compilation error

Error location: p.display(); in printPoint()

Why it fails:

The parameter p is a const Point&, meaning you cannot call non-const member functions on it. display() is not marked const, so the compiler rejects the call.

Compiler error:

"passing 'const Point' as 'this' argument discards qualifiers"

The fix: Mark display() as const:

void display() const {  // Add const
    cout << x << "," << y;
}

Why this works: display() doesn't modify the object, so it's safe to call on const objects. Adding const tells the compiler this guarantee.

Rule: Any member function that doesn't modify the object should be marked const. This allows it to be called on const objects and const references.

Question 22

Constructor Overloading

How many constructors can a class have?

  1. Exactly one
  2. At most two (default and parameterized)
  3. As many as needed, as long as they have different parameter lists
  4. Only one of each type (default, copy, parameterized)

Answer: C - As many as needed, as long as they have different parameter lists

Why C is correct:

Constructors can be overloaded just like any function. You can have as many constructors as needed, provided each has a unique signature (different number or types of parameters).

Example with 4 constructors:

class Rectangle {
private:
    int width, height;
public:
    // 1. Default constructor
    Rectangle() : width(0), height(0) { }

    // 2. Square constructor (one parameter)
    Rectangle(int side) : width(side), height(side) { }

    // 3. Rectangle constructor (two parameters)
    Rectangle(int w, int h) : width(w), height(h) { }

    // 4. Copy constructor
    Rectangle(const Rectangle& other)
        : width(other.width), height(other.height) { }
};

Usage:

Rectangle r1;           // Calls default
Rectangle r2(5);        // Calls single-parameter (square)
Rectangle r3(4, 6);     // Calls two-parameter
Rectangle r4 = r3;      // Calls copy constructor

Why other options are wrong:

  • A: Incorrect. You can have multiple constructors through overloading.
  • B: Incorrect. You can have more than two. There's no limit.
  • D: Incorrect. You can have multiple parameterized constructors with different parameters.

Overloading rules: Each constructor must have a unique signature. The signature includes the number and types of parameters, but NOT the return type (constructors have no return type anyway).

Question 23

Memory Leak Detection

Which class has a memory leak?

// Class A
class A {
    int* data;
public:
    A() { data = new int[10]; }
    ~A() { delete[] data; }
};

// Class B
class B {
    int* data;
public:
    B() { data = new int[10]; }
    // No destructor
};

// Class C
class C {
    int data[10];
public:
    C() { }
    // No destructor
};

Answer: Class B has a memory leak

Analysis of each class:

Class A - NO memory leak:

  • Allocates memory with new int[10] in constructor
  • Frees memory with delete[] data in destructor
  • Every new has a matching delete - correct!

Class B - MEMORY LEAK:

  • Allocates memory with new int[10] in constructor
  • No destructor, so memory is never freed
  • When B object is destroyed, the pointer is lost but the memory remains allocated
  • Memory leak: 10 integers (40 bytes) leaked per object

Class C - NO memory leak:

  • Uses a static array (int data[10]), not dynamic allocation
  • Static arrays are automatically cleaned up when the object is destroyed
  • No new, so no need for delete
  • Compiler-generated destructor handles cleanup automatically

The Rule:

For every new, there must be a matching delete. For every new[], there must be a matching delete[]. If you allocate memory in a constructor, you MUST free it in the destructor.

How to detect:

  • Use Valgrind (Linux): valgrind ./program
  • Look for "definitely lost: X bytes in Y blocks"

Fix for Class B:

class B {
    int* data;
public:
    B() { data = new int[10]; }
    ~B() { delete[] data; }  // Add destructor!
};
Question 24

Default Parameter Placement

Which function declaration is valid?

  1. void func(int a = 5, int b, int c);
  2. void func(int a, int b = 5, int c);
  3. void func(int a, int b, int c = 5);
  4. All are valid

Answer: C - void func(int a, int b, int c = 5);

Why C is correct:

Default parameters must appear at the END of the parameter list. Once you have a default parameter, all parameters after it must also have defaults.

Rule: Default parameters must be rightmost and contiguous.

Valid examples:

void func1(int a, int b, int c = 5);              // OK: last param
void func2(int a, int b = 3, int c = 5);          // OK: last two params
void func3(int a = 1, int b = 3, int c = 5);      // OK: all three params

Invalid examples:

void func4(int a = 5, int b, int c);              // ERROR (A)
void func5(int a, int b = 5, int c);              // ERROR (B)
void func6(int a = 5, int b, int c = 7);          // ERROR

Why other options are wrong:

  • A: Incorrect. Default parameter a=5 is followed by non-default parameters b and c. This creates ambiguity.
  • B: Incorrect. Default parameter b=5 is followed by non-default parameter c. Not allowed.
  • D: Incorrect. Only C is valid.

Why the rule exists:

Consider: void func(int a = 5, int b, int c);

If you call func(10, 20);, which parameter gets which value?

  • Is it func(10, 20, ???) using default for a?
  • Or func(???, 10, 20) using default for c?
  • Ambiguous! The compiler can't determine intent.

By requiring defaults to be rightmost, the rule is simple: Arguments fill parameters left-to-right. Missing arguments use defaults from right-to-left.

Question 25

Shallow Copy Problem

What happens when you use the default copy constructor with a class containing a pointer member?

  1. A deep copy is automatically performed
  2. Both objects point to the same dynamically allocated memory
  3. The pointer is set to NULL in the copy
  4. A compilation error occurs

Answer: B - Both objects point to the same dynamically allocated memory

Why B is correct:

The default copy constructor performs a shallow (member-wise) copy. For pointer members, it copies the pointer VALUE (the memory address), not the data the pointer points to. Result: both objects' pointers contain the same address.

Visual representation:

Original object:           Copy (shallow):
obj1.ptr ----\             obj2.ptr ----\
              \                          |
               v                         |
          [Data Block] <-----------------/

Both pointers point to SAME memory block!

The danger:

class Array {
    int* data;
    int size;
public:
    Array(int s) : size(s) {
        data = new int[size];
    }
    ~Array() {
        delete[] data;  // Frees the memory
    }
    // No custom copy constructor - uses default shallow copy
};

void func() {
    Array arr1(10);
    Array arr2 = arr1;  // Shallow copy - both point to same array

    // arr2 goes out of scope first
    // ~Array() called for arr2: deletes the array

    // arr1 goes out of scope
    // ~Array() called for arr1: tries to delete SAME array
    // CRASH! Double delete!
}

Why other options are wrong:

  • A: Incorrect. The default copy constructor does NOT perform deep copy. You must write a custom copy constructor for deep copying.
  • C: Incorrect. The pointer is not set to NULL. It's copied as-is (same address as original).
  • D: Incorrect. The code compiles fine. The problem appears at runtime (crash when destructors run).

The solution - Custom deep copy constructor:

Array(const Array& other) : size(other.size) {
    data = new int[size];  // Allocate NEW memory
    for (int i = 0; i < size; i++) {
        data[i] = other.data[i];  // Copy VALUES
    }
}

After deep copy:

obj1.ptr ----> [Data Block 1]
obj2.ptr ----> [Data Block 2] (independent copy)
Question 26

Constructor Execution Order

In what order are member variables initialized when using an initialization list?

  1. Left to right as they appear in the initialization list
  2. In the order they are declared in the class
  3. Alphabetically by variable name
  4. Random order determined by the compiler

Answer: B - In the order they are declared in the class

Why B is correct:

Member variables are ALWAYS initialized in the order they appear in the class declaration, regardless of the order in the initialization list.

Example:

class Example {
private:
    int a;
    int b;
    int c;
public:
    // Initialization list order: c, a, b
    Example() : c(3), a(1), b(2) { }
    // But ACTUAL initialization order: a, b, c (declaration order)
};

Why this matters - Dependency trap:

class Trap {
private:
    int size;        // Declared FIRST
    int* data;       // Declared SECOND
public:
    // WRONG order in initialization list:
    Trap(int s) : data(new int[size]), size(s) { }
    // Problem: data initialized first (using uninitialized size!)
    // Then size initialized
};

// CORRECT:
class Fixed {
private:
    int size;        // Declared FIRST
    int* data;       // Declared SECOND
public:
    // Match declaration order:
    Fixed(int s) : size(s), data(new int[size]) { }
    // Now: size initialized first, then data uses size
};

Best practice: List members in initialization list in the same order as declaration to avoid confusion.

Why other options are wrong:

  • A: Incorrect. The initialization list order is ignored. Declaration order matters.
  • C: Incorrect. Alphabetical ordering is not used.
  • D: Incorrect. The order is deterministic (declaration order), not random.

Compiler warning: Some compilers warn if initialization list order doesn't match declaration order.

Question 27

const Object Restrictions

Given: const Student s("Alice", 3.8);
Which operations are allowed on s?

  1. Calling any member function
  2. Only calling const member functions
  3. Modifying public member variables
  4. No operations allowed at all

Answer: B - Only calling const member functions

Why B is correct:

A const object is immutable - it cannot be modified. The compiler enforces this by only allowing calls to const member functions, which promise not to modify the object.

Example:

class Student {
private:
    string name;
    double gpa;
public:
    string getName() const { return name; }      // const - OK
    void setName(string n) { name = n; }         // non-const - NOT OK
    void display() const {                       // const - OK
        cout << name << ", " << gpa << endl;
    }
};

const Student s("Alice", 3.8);
s.getName();     // OK - const function
s.display();     // OK - const function
s.setName("Bob"); // ERROR - non-const function

Why other options are wrong:

  • A: Incorrect. Only const member functions can be called, not all functions.
  • C: Incorrect. const objects cannot have members modified, even public ones. The entire object is immutable.
  • D: Incorrect. const member functions CAN be called. The object can still be used for reading data.

Practical use:

void printStudent(const Student& s) {
    // s is const, so we can only call const functions
    cout << s.getName() << endl;  // OK if getName() is const
    s.display();                  // OK if display() is const
    // s.setName("X");            // ERROR
}

Why this is useful: Passing by const& avoids copying (efficient) while preventing accidental modification (safe).

Question 28

Destructor Syntax

Which is the correct destructor declaration for a class named Matrix?

  1. void ~Matrix() { }
  2. ~Matrix() { }
  3. Matrix::~Matrix() { }
  4. delete Matrix() { }

Answer: B - ~Matrix() { } (in class declaration) or C - Matrix::~Matrix() { } (in .cpp file)

Why B and C are correct:

  • B: Correct syntax for destructor declaration inside the class
  • C: Correct syntax for destructor definition outside the class (in .cpp file)

Destructor syntax rules:

  1. Name: Tilde (~) followed by class name
  2. No return type (not even void)
  3. No parameters
  4. Cannot be overloaded (only ONE destructor per class)
  5. Called automatically when object is destroyed

Complete example:

// Matrix.h
class Matrix {
private:
    int** data;
    int rows, cols;
public:
    Matrix(int r, int c);
    ~Matrix();  // Declaration (Option B)
};

// Matrix.cpp
Matrix::~Matrix() {  // Definition (Option C)
    for (int i = 0; i < rows; i++) {
        delete[] data[i];
    }
    delete[] data;
}

Why other options are wrong:

  • A: Incorrect. Destructors have NO return type, not even void. Writing void ~Matrix() is a syntax error.
  • D: Incorrect. delete is used to destroy objects, not to declare destructors. The destructor is what gets called when you use delete on an object.

When destructor is called:

  • Local object goes out of scope
  • delete called on dynamically allocated object
  • Program terminates (for global/static objects)
Question 29

Copy Constructor Parameter

Why must the copy constructor parameter be a reference (const ClassName&)?

  1. For efficiency (avoid copying)
  2. To prevent infinite recursion
  3. To allow modification of the parameter
  4. It's a C++ convention, not required

Answer: B - To prevent infinite recursion

Why B is correct:

If the copy constructor took the parameter by value instead of by reference, it would create infinite recursion:

// WRONG - would cause infinite recursion:
class Student {
public:
    Student(Student other) {  // Pass by VALUE
        // To pass 'other' by value, we need to COPY it
        // To copy it, we call the copy constructor
        // To call copy constructor, we pass by value
        // To pass by value, we need to copy...
        // INFINITE RECURSION!
    }
};

The problem step-by-step:

  1. You write: Student s2 = s1;
  2. Compiler calls: Student(s1) (copy constructor)
  3. To pass s1 by value, compiler must create a copy
  4. To create a copy, compiler calls copy constructor
  5. Back to step 2 → infinite loop!

CORRECT - uses reference:

class Student {
public:
    Student(const Student& other) {  // Pass by REFERENCE
        // No copying needed - just refers to original
        // No recursion!
    }
};

Why const?

The const is for safety - the copy constructor shouldn't modify the source object. It only needs to read from it.

Why other options are wrong:

  • A: While efficiency is a benefit of using references, it's not the PRIMARY reason. The main reason is to avoid infinite recursion. Even if copying were cheap, we'd still need a reference.
  • C: Incorrect. We use const specifically to PREVENT modification. The copy constructor should not change the source object.
  • D: Incorrect. Using a reference is REQUIRED, not just convention. A copy constructor without a reference parameter would cause infinite recursion and is invalid.

C++ standard requirement: A copy constructor must have a parameter of type const ClassName& or ClassName& (reference). Any other type is not a valid copy constructor.

Question 30

Access Specifier Inheritance

True or False: If a class uses private inheritance from a base class, the public members of the base class become private in the derived class.

Justify your answer.

Answer: True

Detailed Justification:

When you use private inheritance, ALL members of the base class (public and protected) become private in the derived class. This means they're accessible within the derived class but not from outside.

Example:

class Base {
public:
    int publicVar;
protected:
    int protectedVar;
private:
    int privateVar;
};

class Derived : private Base {  // PRIVATE inheritance
    // publicVar is now private in Derived
    // protectedVar is now private in Derived
    // privateVar is inaccessible (was already private in Base)
};

int main() {
    Derived d;
    d.publicVar = 5;  // ERROR - publicVar is private in Derived!
}

Inheritance access levels:

Base Member public Inheritance protected Inheritance private Inheritance
public public protected private
protected protected protected private
private inaccessible inaccessible inaccessible

When to use private inheritance:

  • Implementation hiding: You want to reuse base class functionality internally but not expose it as part of the derived class's interface
  • Rare in practice - composition (has-a) is usually preferred over private inheritance

Note: This topic is covered in detail in Unit 7 (Inheritance). For Unit 3, you only need to know that access specifiers (public, protected, private) control member visibility.
