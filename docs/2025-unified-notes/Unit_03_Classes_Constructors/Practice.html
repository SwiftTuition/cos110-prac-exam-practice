Problem 2: Fix the Shallow Copy Bug (Intermediate)

Scenario: Nkosinathi is building a class to store exam scores for his students. He wrote the code below, but when he copies a ScoreList object, weird things happen. The program sometimes crashes, and modifying one object affects the other.

Task: Identify the problem and fix it by implementing a proper copy constructor.

Buggy Code Provided:

class ScoreList {
private:
    int* scores;
    int count;

public:
    ScoreList(int n) : count(n) {
        scores = new int[count];
        for (int i = 0; i < count; i++) {
            scores[i] = 0;
        }
    }

    ~ScoreList() {
        delete[] scores;
    }

    void setScore(int index, int value) {
        if (index >= 0 && index < count) {
            scores[index] = value;
        }
    }

    void display() const {
        for (int i = 0; i < count; i++) {
            cout << scores[i] << " ";
        }
        cout << endl;
    }
};

Problem: When you copy a ScoreList object, both the original and copy point to the same array. Modifying one affects the other, and when one is destroyed, the other has a dangling pointer.

Explanation:

  1. The Problem: Without a custom copy constructor, C++ uses the default shallow copy. This copies the pointer scores directly, so both objects point to the same array.
  2. The Fix: We implement a copy constructor that allocates a new array (scores = new int[count];) and copies each element individually.
  3. Initialization List: We initialize count from other.count in the initialization list.
  4. Independent Memory: After deep copying, list1 and list2 have separate arrays. Modifying one doesn't affect the other.
  5. Safe Destruction: When list2 is destroyed, it deletes its own array. When list1 is destroyed, it deletes its own separate array (no double-free crash).

Time Complexity: O(n) for the copy constructor, where n is the number of scores (must copy each element).

Rule of Three: If your class has dynamic memory (uses new), you need: (1) Destructor, (2) Copy constructor, (3) Assignment operator. This class has 1 and 2; in Unit 4, we'll add the assignment operator.

Problem 3: What's Wrong with This Code? (Debugging)

Scenario: The following Counter class is supposed to track how many Counter objects have been created and destroyed. The code compiles but doesn't work correctly.

Task: Find and fix ALL the bugs. There are 3 bugs to identify.

class Counter {
private:
    static int totalCreated;
    static int totalDestroyed;
    int id;

public:
    Counter() {
        id = totalCreated;
        totalCreated++;
        cout << "Counter " << id << " created" << endl;
    }

    ~Counter() {
        totalDestroyed++;
        cout << "Counter " << id << " destroyed" << endl;
    }

    static void displayStats() {
        cout << "Created: " << totalCreated << endl;
        cout << "Destroyed: " << totalDestroyed << endl;
        cout << "Currently active: " << (totalCreated - totalDestroyed) << endl;
    }
};

int main() {
    Counter::displayStats();

    Counter c1;
    Counter c2;

    Counter::displayStats();

    return 0;
}

Bug #1: Missing Static Member Initialization

Problem: The static members totalCreated and totalDestroyed are declared but never initialized outside the class.

Error: Linker error: "undefined reference to Counter::totalCreated"

Fix: Add initialization before main():

int Counter::totalCreated = 0;
int Counter::totalDestroyed = 0;

Bug #2: Wrong Initial ID Assignment

Problem: In the constructor, id = totalCreated; happens before incrementing totalCreated.

Result: First counter gets ID 0, second gets ID 1. This might be intentional, but it's more intuitive to start from 1.

Better approach:

Counter() {
    totalCreated++;
    id = totalCreated;  // Now first object gets ID 1
    cout << "Counter " << id << " created" << endl;
}

Note: This isn't technically a bug if IDs starting from 0 were intended, but it's a common mistake.

Bug #3: Trying to Access Non-Static Members from Static Function

Problem: This code doesn't have this bug explicitly shown, but it's a common mistake. If you tried to add cout << id; in displayStats(), you'd get an error.

Why: Static functions can't access non-static members (like id) because they don't have a this pointer.

Problem 4: Card Deck Manager (Challenge)

Task: Create a Card class and a Deck class that manages a collection of cards. This problem combines multiple concepts: classes, constructors, copy constructors, const correctness, and dynamic memory.

Requirements:

Card Class:

  • Private members: string rank (e.g., "Ace", "2", "King"), string suit (e.g., "Hearts", "Spades")
  • Constructor: Card(string r, string s) using initialization list
  • Getter: string toString() const returns "Rank of Suit" (e.g., "Ace of Spades")

Deck Class:

  • Private members: Card* cards (dynamic array), int size
  • Constructor: Deck(int s) allocates array of s cards
  • Copy constructor: Deep copy the card array
  • Destructor: Free the dynamic array
  • void setCard(int index, const Card& c): Sets card at index (with bounds checking)
  • void display() const: Prints all cards

Test Case:

Deck myDeck(3);
myDeck.setCard(0, Card("Hog Rider", "Troops"));
myDeck.setCard(1, Card("Fireball", "Spells"));
myDeck.setCard(2, Card("Cannon", "Buildings"));

Deck copiedDeck = myDeck;
copiedDeck.setCard(1, Card("Lightning", "Spells"));

// Both decks should have different cards at index 1

Explanation:

  1. Card Class: Simple class with two strings. The toString() method is const because it doesn't modify the card.
  2. Default Card Constructor: We added Card() with empty strings so we can create an array of Cards (arrays need default-constructible elements).
  3. Deck Constructor: Allocates an array of size cards using new Card[size]. This calls the default constructor for each card.
  4. Deep Copy Constructor: Allocates a new array and copies each Card object from the original deck to the new deck.
  5. Destructor: Frees the dynamically allocated array with delete[] cards.
  6. setCard(): Validates the index before setting. The parameter is const Card& to avoid unnecessary copying.
  7. display(): Marked const because it only reads data.

Time Complexity:

  • Constructor: O(n) where n = size (must initialize n card objects)
  • Copy constructor: O(n) (must copy n cards)
  • setCard(): O(1) (constant time)
  • display(): O(n) (must print n cards)
Advanced Concept: This problem demonstrates composition (Deck contains Cards). The Deck manages the memory for its Cards, so the copy constructor must handle deep copying properly.
Clash Royale Connection: In Clash Royale, your 8-card deck cycles through as you play cards. This Deck class is a simplified version of that system. In a real implementation, you'd add methods like playCard(), shuffle(), and draw().
