Question 1 2 marks
Which of the following best describes exception handling in C++?
a) A mechanism to prevent compilation errors
b) A way to handle runtime errors by transferring control to error-handling code
c) A technique to optimize program performance
d) A method to validate user input at compile time

✓ Correct Answer

b) A way to handle runtime errors by transferring control to error-handling code

Explanation:

Exception handling is a runtime mechanism that allows a program to respond to exceptional circumstances (like runtime errors) by transferring control from one part of the program to another.

When an exception is thrown, the normal flow of execution stops and control is transferred to the nearest matching catch block.

Why other options are wrong:

  • a) Exceptions handle runtime errors, not compilation errors. The compiler doesn't execute exception handling.
  • c) Exception handling is for error management, not performance optimization. In fact, it can slightly decrease performance.
  • d) Input validation can use exceptions, but they're evaluated at runtime, not compile time.
Question 2 2 marks
What happens when an exception is thrown but there is no matching catch block?
a) The exception is silently ignored
b) The program terminates (calls std::terminate)
c) The exception is automatically converted to a return value
d) The program continues execution from where the exception was thrown

✓ Correct Answer

b) The program terminates (calls std::terminate)

Explanation:

If an exception is thrown and there is no matching catch block in the entire call stack, C++ will call std::terminate(), which by default calls std::abort() to end the program abnormally.

This is why it's critical to have appropriate catch blocks for exceptions you might throw, or use a catch-all catch (...) block to prevent unexpected termination.

Why other options are wrong:

  • a) Exceptions are never silently ignored - that would defeat their purpose
  • c) There is no automatic conversion to return values
  • d) Execution does NOT continue from the throw point - control is transferred away permanently
Question 3 1 mark
True or False: A catch block can catch exceptions of the specified type AND any types derived from it.

✓ Correct Answer

True

Explanation:

This statement is true. When you catch by reference (e.g., catch (BaseException& e)), the catch block will match exceptions of type BaseException and any classes derived from it.

This is polymorphism in action - a base class reference can refer to derived class objects.

Example:

class BaseException { };
class DerivedException : public BaseException { };

try {
    throw DerivedException();
}
catch (BaseException& e) {
    // This WILL catch DerivedException
}

This is why you should order catch blocks from most specific to most general - the first matching catch block is executed.

Question 4 2 marks
What is the purpose of catching exceptions by reference (e.g., catch (Exception& e)) rather than by value?
a) It's required by C++ syntax
b) To avoid object slicing and enable polymorphism
c) To make the program run faster
d) To prevent the exception from being caught

✓ Correct Answer

b) To avoid object slicing and enable polymorphism

Explanation:

Catching by reference is important for two reasons:

  1. Avoid object slicing: If you catch by value and throw a derived exception, only the base class part is copied - you lose the derived class data.
  2. Enable polymorphism: With references, virtual functions work correctly, so calling a virtual method on the caught exception will invoke the correct derived class version.

Example of the problem with catching by value:

class Base {
public:
    virtual void show() { cout << "Base"; }
};

class Derived : public Base {
public:
    void show() { cout << "Derived"; }
};

try {
    throw Derived();
}
catch (Base e) {  // BY VALUE - BAD!
    e.show();     // Prints "Base" due to slicing
}

catch (Base& e) {  // BY REFERENCE - GOOD!
    e.show();      // Prints "Derived" - polymorphism works
}
Question 5 2 marks
In the following code, which catch block will execute when divide(10, 0) is called? 
class MathException { };
class DivisionException : public MathException { };

int divide(int a, int b) {
    if (b == 0) {
        throw DivisionException();
    }
    return a / b;
}

try {
    divide(10, 0);
}
catch (DivisionException& e) {
    cout << "Caught DivisionException";
}
catch (MathException& e) {
    cout << "Caught MathException";
}
a) The DivisionException catch block
b) The MathException catch block
c) Both catch blocks
d) Neither - the program terminates

✓ Correct Answer

a) The DivisionException catch block

Explanation:

When an exception is thrown, C++ searches for a matching catch block from top to bottom. The first matching catch block is executed, then control exits the try-catch structure.

In this case:

  1. DivisionException() is thrown
  2. First catch block checks: Is it DivisionException? YES - exact match!
  3. Execute this catch block and print "Caught DivisionException"
  4. Exit the try-catch structure (the second catch is never evaluated)

Important: Even though DivisionException inherits from MathException (so the second catch would also match), only the FIRST matching catch is executed.

Best practice: Order catch blocks from most specific to most general:

catch (DivisionException& e) { }  // Most specific first
catch (MathException& e) { }      // More general second
catch (...) { }                   // Catch-all last

If you reverse the order (general first), the specific catch blocks will never execute because the general one catches everything.

Question 6 3 marks
What will the following code output? 
class FileException {
private:
    int errorCode;
public:
    FileException(int code) : errorCode(code) {}
    int getCode() const { return errorCode; }
};

void openFile(bool success) {
    if (!success) {
        throw FileException(404);
    }
    cout << "File opened" << endl;
}

int main() {
    try {
        openFile(false);
        cout << "After openFile" << endl;
    }
    catch (FileException& e) {
        cout << "Error code: " << e.getCode() << endl;
    }
    cout << "Program continues" << endl;
    return 0;
}
a) File opened
After openFile
Program continues
b) Error code: 404
Program continues
c) File opened
Error code: 404
Program continues
d) Error code: 404
After openFile
Program continues

✓ Correct Answer

b) Error code: 404
Program continues

Explanation - Line by line trace:

  1. Enter main(), start try block
  2. Call openFile(false)
  3. In openFile(): success is false, so !success is true
  4. Throw FileException(404)
  5. Control immediately jumps to catch block - the rest of openFile() is skipped
  6. "File opened" is NEVER printed because we threw before reaching that line
  7. Back in main(), the line cout << "After openFile" is SKIPPED because we jumped to the catch block
  8. Catch block executes: prints "Error code: 404"

Question 7 1 mark
True or False: The catch (...) block catches ALL types of exceptions, including built-in types and custom exception classes.

✓ Correct Answer

True

Explanation:

This statement is true. The catch-all syntax catch (...) (three dots, called an ellipsis) will catch ANY exception thrown, regardless of its type.

This includes:

  • Custom exception classes
  • Built-in types thrown as exceptions (int, string, etc.)
  • Standard library exceptions (std::exception and derived)
  • Anything else thrown with throw

Example:

try {
    throw 42;  // Throwing an int
    // or throw "error";  // Throwing a string
    // or throw MyException();  // Custom class
}
catch (int e) {
    cout << "Caught int: " << e;
}
catch (...) {
    cout << "Caught something else!";
    // This catches ALL other types
}

Important: The catch-all should always be LAST, because it matches everything - any catch blocks after it would be unreachable.

Question 8 2 marks
Which of the following is the BEST practice for resource cleanup with exceptions?
a) Always use catch (...) and manually clean up resources
b) Validate all inputs to prevent exceptions from being thrown
c) Acquire resources after validation, use try-catch for cleanup, and rethrow if needed
d) Disable exception handling to avoid cleanup issues

✓ Correct Answer

c) Acquire resources after validation, use try-catch for cleanup, and rethrow if needed

Explanation:

The best practice for exception-safe resource management follows this pattern:

  1. Validate BEFORE allocating: Check inputs before acquiring resources (memory, files, etc.)
  2. Acquire resources: Only allocate after validation passes
  3. Use try-catch for cleanup: Wrap risky operations in try, catch exceptions, clean up resources in catch, then rethrow
  4. Rethrow if needed: Use throw; to propagate the exception after cleanup

Example:

void processFile(int size) {
    if (size <= 0) {
        throw InvalidSizeException();  // Validate FIRST
    }

    int* buffer = new int[size];  // Allocate AFTER validation

    try {
        riskyOperation(buffer, size);
    }
    catch (...) {
        delete[] buffer;  // Cleanup
        throw;            // Rethrow to caller
    }

    delete[] buffer;  // Normal cleanup
}

Why other options are wrong:

  • a) Relying only on catch-all is risky - you might not know what exception occurred
  • b) While validation is good, you can't prevent ALL exceptions (e.g., out of memory, hardware failures)
  • d) Disabling exceptions removes a powerful error-handling mechanism
Question 9 2 marks
What is the purpose of rethrowing an exception using throw; (with no argument)?
a) To throw a new exception of the same type
b) To propagate the current exception to the next outer catch block
c) To reset the exception state
d) To convert the exception to a return value

✓ Correct Answer

b) To propagate the current exception to the next outer catch block

Explanation:

The syntax throw; (with no argument) can only be used inside a catch block. It rethrows the EXACT SAME exception object that was caught, propagating it to the next outer exception handler.

This is useful when you want to:

  • Perform partial error handling (like logging or cleanup)
  • Let outer code also handle the exception
  • Preserve the original exception object (including derived class info)

Example:

void innerFunction() {
    int* ptr = new int[100];
    try {
        riskyOperation(ptr);
    }
    catch (...) {
        delete[] ptr;  // Cleanup locally
        throw;         // Rethrow to caller
    }
}

void outerFunction() {
    try {
        innerFunction();
    }
    catch (MyException& e) {
        cout << "Outer caught: " << e.getMessage();
    }
}

The inner function cleans up its resources, then rethrows. The outer function catches and handles the exception.

Important difference:

  • throw; - Rethrows the SAME exception object (preserves type, polymorphism)
  • throw e; - Throws a COPY of e (may cause object slicing if e is a base reference to derived object)
Question 10 3 marks
Given the following exception hierarchy, what will be the output? 
class Exception {
public:
    virtual void display() { cout << "Exception"; }
};

class NetworkError : public Exception {
public:
    void display() { cout << "NetworkError"; }
};

class TimeoutError : public NetworkError {
public:
    void display() { cout << "TimeoutError"; }
};

int main() {
    try {
        throw TimeoutError();
    }
    catch (Exception& e) {
        e.display();
    }
    return 0;
}
a) Exception
b) NetworkError
c) TimeoutError
d) Compilation error

✓ Correct Answer

c) TimeoutError

Explanation:

This question tests your understanding of polymorphism with exceptions.

Here's what happens:

  1. We throw a TimeoutError object
  2. We catch it with Exception& e (base class reference)
  3. Because display() is declared virtual in the base class, C++ uses dynamic binding
  4. When we call e.display(), it invokes the DERIVED class version (TimeoutError::display())
  5. Output: "TimeoutError"

Inheritance chain:

Exception (base)
    ↑
NetworkError (derived from Exception)
    ↑
TimeoutError (derived from NetworkError)

Why polymorphism works here:

  • We catch by REFERENCE: Exception& e
  • display() is VIRTUAL in the base class
  • Therefore, the actual type (TimeoutError) determines which display() is called

If we caught by VALUE instead:

catch (Exception e) {  // BY VALUE - slicing occurs
    e.display();       // Would print "Exception"
}

Catching by value would cause object slicing - only the Exception part would be copied, and we'd lose the derived class information.

Question 11 2 marks
When should you use exception handling instead of return codes?
a) Always - exceptions are better in every case
b) When errors are rare and exceptional, not part of normal flow
c) Only for file I/O operations
d) Never - return codes are always more efficient

✓ Correct Answer

b) When errors are rare and exceptional, not part of normal flow

Explanation:

Exception handling is best used for truly exceptional conditions - situations that are:

  • Rare: Don't happen during normal execution
  • Unexpected: Invalid inputs, resource failures, programming errors
  • Require special handling: Can't be handled locally

Use exceptions for:

  • Out of memory errors
  • File not found
  • Network connection failures
  • Invalid array indices
  • Division by zero

Use return codes for:

  • Expected failures (e.g., user enters wrong password - this is normal, not exceptional)
  • Frequent checks (e.g., checking if a value is in a list)
  • Performance-critical code paths

Why other options are wrong:

  • a) Exceptions have overhead - using them for normal control flow (like "end of file") is inefficient
  • c) Exceptions are useful for many types of errors, not just file I/O
  • d) Sometimes exceptions are clearer and lead to cleaner code separation

Rule of thumb: If something happens frequently and is part of normal operation, use return codes. If it's rare and exceptional, use exceptions.

Question 13 3 marks
What is wrong with the following code? 
int* allocateArray(int size) {
    int* arr = new int[size];

    if (size <= 0) {
        throw "Invalid size";
    }

    for (int i = 0; i < size; i++) {
        arr[i] = 0;
    }

    return arr;
}
a) You cannot throw string literals
b) Memory is allocated before validation, causing a leak when exception is thrown
c) The array should be allocated with malloc, not new
d) Nothing is wrong with this code

✓ Correct Answer

b) Memory is allocated before validation, causing a leak when exception is thrown

Explanation:

This code has a critical memory leak bug. Here's the problem sequence:

  1. Line 2: Allocate memory with new int[size]
  2. Line 4-6: Check if size is invalid
  3. If size is invalid (≤ 0), throw an exception
  4. Problem: When we throw, we jump to the catch block, skipping the rest of the function
  5. The delete[] is never called, so the allocated memory leaks

Let's trace what happens with allocateArray(-5):

  1. Allocate memory for -5 elements (undefined behavior, but let's assume it allocates something)
  2. Check: is -5 ≤ 0? YES
  3. Throw exception
  4. The pointer arr is lost when we throw - we can NEVER free this memory
  5. Memory leak!

The fix: Validate BEFORE allocating

int* allocateArray(int size) {
    if (size <= 0) {
        throw "Invalid size";  // Throw BEFORE allocating
    }

    int* arr = new int[size];  // Only allocate if valid

    for (int i = 0; i < size; i++) {
        arr[i] = 0;
    }

    return arr;
}

Now if validation fails, we throw BEFORE allocating memory - no leak!

Why other options are wrong:

  • a) You CAN throw string literals in C++ (though it's not best practice)
  • c) new is the correct C++ way to allocate (malloc is C-style)
  • d) There is definitely a bug - the memory leak
Question 14 2 marks
What is the correct order for catch blocks when you have an exception hierarchy?
a) Base class first, then derived classes
b) Derived classes first, then base class
c) Order doesn't matter
d) Alphabetically by class name

✓ Correct Answer

b) Derived classes first, then base class

Explanation:

When catching exceptions from a hierarchy, you MUST order catch blocks from most specific (derived) to most general (base). This is because C++ checks catch blocks from top to bottom and uses the FIRST match.

Correct order:

try {
    // ...
}
catch (VerySpecificException& e) {
    // Most specific first
}
catch (SpecificException& e) {
    // Less specific
}
catch (GeneralException& e) {
    // More general (base class)
}
catch (...) {
    // Catch-all ALWAYS last
}

Why this order matters:

If you put the base class first, it will catch ALL derived exceptions too (because derived IS-A base), so the derived catch blocks would NEVER execute.

Wrong order example:

class Base { };
class Derived : public Base { };

try {
    throw Derived();
}
catch (Base& e) {          // BAD - Base first
    cout << "Caught Base";
}
catch (Derived& e) {       // This will NEVER execute!
    cout << "Caught Derived";
}

// Output: "Caught Base"
// The Derived catch is unreachable!

The compiler may warn you about unreachable catch blocks, but it's legal C++ (just useless).

Best practice summary:

  1. Most specific (most derived) exceptions first
  2. Less specific in the middle
  3. Most general (base class) near the end
  4. catch (...) absolutely last
Question 15 3 marks
Identify all the problems with this exception class design: 
class FileException {
    string message;
    int errorCode;

public:
    FileException(string msg, int code) {
        message = msg;
        errorCode = code;
    }

    string getMessage() {
        return message;
    }
};
a) No problems - this is well-designed
b) getMessage() should be const, and initialization should use initializer list
c) The class should inherit from std::exception
d) Exception classes cannot have multiple data members

✓ Correct Answer

b) getMessage() should be const, and initialization should use initializer list

Explanation:

This exception class has two design issues:

Problem 1: getMessage() should be const

When we catch exceptions by const reference (which is common), we can only call const member functions. getMessage() doesn't modify the object, so it should be marked const:

string getMessage() const {  // Add const
    return message;
}

Without const, this would fail:

catch (const FileException& e) {
    cout << e.getMessage();  // ERROR: can't call non-const method on const object
}

Problem 2: Should use initializer list instead of assignment

The constructor uses assignment in the body instead of an initializer list. Initializer lists are more efficient (especially for strings) and allow initialization of const/reference members:

// Current (less efficient):
FileException(string msg, int code) {
    message = msg;      // Default construct, then assign
    errorCode = code;
}

// Better (more efficient):
FileException(string msg, int code)
    : message(msg), errorCode(code) {
    // Direct initialization
}

Fixed version:

class FileException {
    string message;
    int errorCode;

public:
    FileException(string msg, int code)
        : message(msg), errorCode(code) { }

    string getMessage() const {
        return message;
    }

    int getCode() const {
        return errorCode;
    }
};

Why other options are wrong:

  • a) There ARE problems as explained above
  • c) Inheriting from std::exception is GOOD practice but not required - custom exceptions can stand alone
  • d) Exception classes can have as many data members as needed
Question 16 2 marks
What happens if a destructor throws an exception?
a) Nothing unusual - exceptions can be thrown anywhere
b) The program terminates if the destructor is called during stack unwinding
c) The exception is automatically caught and ignored
d) Compilation error - destructors cannot throw

✓ Correct Answer

b) The program terminates if the destructor is called during stack unwinding

Explanation:

Throwing from a destructor is dangerous and should be avoided. Here's why:

When an exception is thrown, C++ performs "stack unwinding" - it destroys all local objects in the current scope and calling scopes until it finds a catch block.

If a destructor throws an exception WHILE stack unwinding is already happening (because another exception was thrown), you have TWO active exceptions. C++ cannot handle this and calls std::terminate(), ending the program immediately.

Example of the problem:

class BadClass {
public:
    ~BadClass() {
        throw runtime_error("Oops!");  // BAD!
    }
};

void dangerous() {
    BadClass obj;
    throw logic_error("First exception");
    // Stack unwinding starts
    // obj's destructor is called
    // Destructor throws - TWO exceptions active
    // std::terminate() called - program ends
}

Best practice: Never throw from destructors

Mark destructors as noexcept and handle errors internally:

class GoodClass {
public:
    ~GoodClass() noexcept {
        try {
            riskyCleanup();
        }
        catch (...) {
            // Log error but don't throw
        }
    }
};
Question 17 1 mark
True or False: You can have multiple catch blocks for the same try block.

✓ Correct Answer

True

Explanation:

This statement is true. A single try block can have multiple catch blocks to handle different types of exceptions.

Example:

try {
    riskyOperation();
}
catch (FileNotFoundException& e) {
    cout << "File error: " << e.getMessage();
}
catch (NetworkException& e) {
    cout << "Network error: " << e.getCode();
}
catch (InvalidInputException& e) {
    cout << "Input error: " << e.getField();

}

This allows you to handle different error types in different ways, providing specific error handling for each case.

Question 18 2 marks
What is "stack unwinding" in the context of exception handling?
a) The process of removing items from a stack data structure
b) The process of destroying local objects when an exception is thrown
c) A compiler optimization technique
d) The process of reversing a function call

✓ Correct Answer

b) The process of destroying local objects when an exception is thrown

Explanation:

Stack unwinding is the automatic process that happens when an exception is thrown. C++ destroys all local objects in the current scope and calling scopes (in reverse order of construction) until it finds a matching catch block.

Step by step:

  1. Exception is thrown in a function
  2. C++ looks for a matching catch block in the current function
  3. If not found, destroy all local objects in current function (call their destructors)
  4. Exit the function and search the calling function
  5. Repeat until a catch block is found or main() is exited

Example:

class Resource {
public:
    Resource() { cout << "Acquired\n"; }
    ~Resource() { cout << "Released\n"; }
};

void inner() {
    Resource r1;
    throw runtime_error("Error!");
    // r1's destructor is automatically called
    // (stack unwinding)
}

void outer() {
    Resource r2;
    inner();
    // When inner() throws, r2's destructor
    // is also called during unwinding
}

// Output:
// Acquired (r2)
// Acquired (r1)
// Released (r1)  <- unwinding from inner()
// Released (r2)  <- unwinding from outer()

Why this matters: Stack unwinding ensures that destructors are called, which is crucial for RAII (Resource Acquisition Is Initialization). Even when exceptions occur, resources are properly cleaned up.

Question 20 2 marks
Which of the following is a disadvantage of using exceptions?
a) They make error handling more complex
b) They have runtime overhead and can make control flow less obvious
c) They cannot carry error information
d) They are not supported in modern C++

✓ Correct Answer

b) They have runtime overhead and can make control flow less obvious

Explanation:

While exceptions are powerful, they do have some disadvantages:

1. Runtime overhead:

  • Exception handling mechanisms add some performance cost
  • Stack unwinding, destructor calls, and exception matching take time
  • For performance-critical code paths, this can be significant

2. Less obvious control flow:

  • Functions can exit at any throw point, not just at return statements
  • Code between throw and catch is skipped - not always obvious when reading
  • Harder to trace execution path compared to explicit return codes

Example of non-obvious flow:

void process() {
    setup();
    riskyOperation();  // Might throw - jumps to catch
    cleanup();         // This might never run!
}

// Better - guarantee cleanup:
void process() {
    setup();
    try {
        riskyOperation();
    }
    catch (...) {
        cleanup();
        throw;
    }
    cleanup();
}

Why other options are wrong:

  • a) Exceptions actually simplify error handling by separating error handling from normal code
  • c) Exceptions CAN carry detailed error information in exception objects
  • d) Exceptions are fully supported in all modern C++ standards

When to avoid exceptions:

  • Performance-critical inner loops
  • Embedded systems with limited resources
  • Real-time systems with strict timing requirements
Question 21 2 marks
What is the purpose of declaring member functions as const in exception classes (e.g., string getMessage() const)?
a) To prevent the function from being called
b) To allow the function to be called on const exception objects
c) To make the function run faster
d) It's required by the C++ standard for all exception classes

✓ Correct Answer

b) To allow the function to be called on const exception objects

Explanation:

When you catch an exception by const reference (which is common practice), the exception object becomes const. You can only call const member functions on const objects.

Example of the problem:

class MyException {
    string message;
public:
    MyException(string msg) : message(msg) {}

    // Non-const version - PROBLEM!
    string getMessage() {
        return message;
    }
};

try {
    throw MyException("Error!");
}
catch (const MyException& e) {  // Caught by const ref
    cout << e.getMessage();     // ERROR! Can't call non-const
                                // method on const object
}

The fix - add const:

class MyException {
    string message;
public:
    MyException(string msg) : message(msg) {}

    // Const version - WORKS!
    string getMessage() const {
        return message;
    }
};

try {
    throw MyException("Error!");
}
catch (const MyException& e) {  // Caught by const ref
    cout << e.getMessage();     // ✓ Works! Can call const method
}

Why catch by const reference?

  • Prevents accidental modification of the exception object
  • Communicates intent - you're just reading the error info
  • Matches the pattern used by standard library exceptions

Rule of thumb: Any member function in an exception class that reads data (getters, display functions, etc.) should be marked const.

Question 22 1 mark
True or False: An exception thrown in a constructor will cause the destructor to be called.

✓ Correct Answer

False

Explanation:

This statement is false. If an exception is thrown during construction, the destructor for that object is NOT called because the object was never fully constructed.

The rule: Destructors are only called for fully constructed objects. If construction fails (exception thrown), the object doesn't exist, so its destructor doesn't run.

Example:

class Resource {
public:
    Resource() {
        cout << "Constructor" << endl;
        throw runtime_error("Construction failed!");
        cout << "After throw" << endl;  // Never executed
    }

    ~Resource() {
        cout << "Destructor" << endl;  // NEVER CALLED
    }
};

int main() {
    try {
        Resource r;
    }
    catch (...) {
        cout << "Caught exception" << endl;
    }
}

// Output:
// Constructor
// Caught exception
// (No "Destructor" - it's not called!)

Why this matters for resource management:

If your constructor allocates resources (memory, files, etc.), you MUST clean them up before throwing an exception, because the destructor won't run.

Example with resource leak:

class BadClass {
    int* data;
public:
    BadClass(int size) {
        data = new int[size];  // Allocate

        if (size < 0) {
            throw invalid_argument("Bad size");
            // LEAK! data is never deleted because
            // destructor won't be called
        }
    }

    ~BadClass() {
        delete[] data;  // This won't run if construction fails
    }
};

The fix:

class GoodClass {
    int* data;
public:
    GoodClass(int size) {
        if (size < 0) {
            throw invalid_argument("Bad size");
            // Good - throw BEFORE allocating
        }

        data = new int[size];  // Only allocate if valid
    }

    ~BadClass() {
        delete[] data;
    }
};

Important note: Even though the constructor's destructor isn't called, destructors of any FULLY CONSTRUCTED member objects ARE called during stack unwinding.

Question 23 2 marks
What is the difference between throw e; and throw; when rethrowing?
a) No difference - they do the same thing
b) throw; rethrows the original exception, throw e; throws a copy
c) throw e; is faster
d) throw; can only be used in catch blocks

✓ Correct Answer

b) throw; rethrows the original exception, throw e; throws a copy

Explanation:

This is a subtle but important distinction:

throw; (no argument):

  • Rethrows the EXACT SAME exception object that was caught
  • Preserves the dynamic type (important for polymorphism)
  • More efficient (no copying)
  • Can ONLY be used inside a catch block

throw e; (with argument):

  • Throws a COPY of the exception variable e
  • Can cause object slicing if e is a base reference to a derived object
  • Less efficient (requires copying)
  • Can be used anywhere, not just in catch blocks

Example showing the difference:

class Base {
public:
    virtual void show() { cout << "Base"; }
};

class Derived : public Base {
public:
    void show() { cout << "Derived"; }
};

void test1() {
    try {
        throw Derived();
    }
    catch (Base& e) {
        throw;  // Rethrows original Derived object
    }
}

void test2() {
    try {
        throw Derived();
    }
    catch (Base& e) {
        throw e;  // Throws a COPY of Base (slicing!)
    }
}

// Using test1():
try {
    test1();
}
catch (Base& e) {
    e.show();  // Prints "Derived" - preserved!
}

// Using test2():
try {
    test2();
}
catch (Base& e) {
    e.show();  // Prints "Base" - lost derived info!
}

Why option d is partially true but not the answer: Yes, throw; can only be used in catch blocks, but that's not the main difference - the key difference is what gets thrown (original vs copy).

Best practice: Always use throw; (no argument) when rethrowing to preserve the exception's type and avoid copying.

Question 24 3 marks
Design an exception class ArrayException that stores an error message and the invalid index. What members and methods should it have? Choose the BEST design:
a) Public data members: message, index
b) Private data members: message, index. Public methods: getMessage() const, getIndex() const
c) Only a message member, no index needed
d) No data members, just a display() method that prints a hardcoded message

✓ Correct Answer

b) Private data members: message, index. Public methods: getMessage() const, getIndex() const

Explanation:

Option b follows proper object-oriented design principles for exception classes:

Good design (option b):

class ArrayException {
private:
    string message;
    int index;

public:
    ArrayException(string msg, int idx)
        : message(msg), index(idx) { }

    string getMessage() const {
        return message;
    }

    int getIndex() const {
        return index;
    }
};

Why this design is good:

  • Encapsulation: Data members are private, accessed through public methods
  • Const correctness: Getters are const because they don't modify the object
  • Complete information: Stores both message AND the problematic index
  • Flexible usage: Caller can format the error message however they want

Usage example:

int getValue(int* arr, int size, int index) {
    if (index < 0 || index >= size) {
        throw ArrayException("Invalid array index", index);
    }
    return arr[index];
}

try {
    int* data = new int[10];
    int val = getValue(data, 10, 15);
}
catch (ArrayException& e) {
    cout << "Error: " << e.getMessage()
         << " at position " << e.getIndex() << endl;
    // Output: Error: Invalid array index at position 15
}

Why other options are wrong:

  • a) Public data members: Breaks encapsulation. Users could modify the exception object after it's thrown, which is bad design.
  • c) Only message: Loses important information. Knowing WHICH index failed is valuable for debugging.
  • d) Hardcoded message: Not reusable. Every different error would need a different exception class.

Optional enhancement - display() method:

class ArrayException {
    // ... (same as before)

public:
    void display() const {
        cout << message << " (index: " << index << ")" << endl;
    }
};

// Usage:
catch (ArrayException& e) {
    e.display();  // Prints: Invalid array index (index: 15)
}
Question 25 4 marks
You are building a file processing system. Design a complete exception hierarchy for file errors with the following requirements:
  • Base class: FileException
  • Derived class 1: FileNotFoundException (stores filename)
  • Derived class 2: PermissionDeniedException (stores filename and permission type)
  • All exceptions should have a virtual display() method
Which implementation is correct?
a) All classes store their own filename independently
b) Base class stores filename in protected, derived classes add specific data and override display()
c) Each class is independent with no inheritance
d) Use a single class with flags to indicate exception type

✓ Correct Answer

b) Base class stores filename in protected, derived classes add specific data and override display()

Explanation:

This is the proper way to design an exception hierarchy using inheritance and polymorphism:

Correct implementation (option b):

class FileException {
protected:
    string filename;  // Protected - accessible to derived

public:
    FileException(string file) : filename(file) { }

    virtual void display() const {
        cout << "File error: " << filename << endl;
    }

    virtual ~FileException() { }  // Virtual destructor
};

class FileNotFoundException : public FileException {
public:
    FileNotFoundException(string file)
        : FileException(file) { }

    void display() const {
        cout << "File not found: " << filename << endl;
    }
};

class PermissionDeniedException : public FileException {
private:
    string permissionType;

public:
    PermissionDeniedException(string file, string perm)
        : FileException(file), permissionType(perm) { }

    void display() const {
        cout << "Permission denied (" << permissionType
             << "): " << filename << endl;
    }
};

Why this design is good:

  1. DRY principle: Filename is stored in base class, not duplicated in derived classes
  2. Protected access: Derived classes can access filename directly for display
  3. Polymorphism: display() is virtual, so calling it on a base reference invokes the correct version
  4. Extensibility: Easy to add new file exception types
  5. Virtual destructor: Proper cleanup when deleting through base pointer

Usage example showing polymorphism:

void processFile(string filename) {
    if (!fileExists(filename)) {
        throw FileNotFoundException(filename);
    }
    if (!hasPermission(filename, "read")) {
        throw PermissionDeniedException(filename, "read");
    }
    // ... process file
}

int main() {
    try {
        processFile("data.txt");
    }
    catch (FileException& e) {  // Catches ALL file exceptions
        e.display();  // Polymorphism - calls correct version
    }
}

Output scenarios:

  • If file doesn't exist: "File not found: data.txt"
  • If permission denied: "Permission denied (read): data.txt"

Why other options are wrong:

  • a) Duplicate filename storage: Violates DRY (Don't Repeat Yourself). Wastes memory and makes updates harder.
  • c) No inheritance: Can't catch all file errors with a single catch block. No code reuse.
  • d) Single class with flags: Not object-oriented. Requires if-else logic to check flags. Hard to extend.

Advanced: Catching specific vs general:

try {
    processFile("secret.txt");
}
catch (PermissionDeniedException& e) {
    // Specific handling for permission errors
    requestPermission(e.getFilename());
}
catch (FileNotFoundException& e) {
    // Specific handling for missing files
    createDefaultFile(e.getFilename());
}
catch (FileException& e) {
    // General handling for other file errors
    logError(e);
}

The inheritance hierarchy allows you to catch broadly (base class) or specifically (derived classes) depending on your needs.
