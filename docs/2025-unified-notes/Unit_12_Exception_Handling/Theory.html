1. Why Exception Handling?

Before exception handling existed, programmers handled errors using return codes. Here's how that looked:

int divide(int a, int b) {
    if (b == 0) {
        cout << "Error: Division by zero!" << endl;
        return -1;  // Magic error code
    }
    return a / b;
}

int main() {
    int result = divide(10, 0);
    if (result == -1) {
        // Handle error
    }
    return 0;
}

What's happening here? The function divide checks if b is zero. If it is, we print an error and return -1 as a "magic number" to signal an error. The caller (in this case, main) has to check if the result is -1 to know if an error occurred.

This approach has serious problems:

  • Magic numbers: What if -1 is actually a valid result? For example, divide(-10, 10) should return -1, but now we can't tell if that's an error or a real answer.
  • Easy to ignore: The caller might forget to check the error code. If they just use result without checking, they're using an invalid value.
  • Limited information: An error code is just a number. It doesn't tell you why the error happened, where it happened, or what to do about it.
  • Code gets messy: You need error checking after every function call, which makes your code hard to read.

Exception handling solves all of these problems. It lets you separate normal code from error-handling code. Your main logic stays clean, and error handling happens in dedicated places.

Swift Note: Think of exceptions like smoke alarms. They don't prevent fires, but they alert you when one happens so you can respond. Your program's exception handlers are the emergency exits.

2. The try-catch-throw Mechanism

Exception handling in C++ uses three keywords that work together:

  • throw - Signals that an error has occurred. Think of it as "raising an alarm."
  • try - Wraps code that might throw exceptions. Think of it as "this zone might have problems."
  • catch - Handles specific types of exceptions. Think of it as "if this specific problem happens, do this."

Flow of Control:
  1. Code inside try block starts running
  2. If throw executes, control immediately jumps to the matching catch
  3. The catch block handles the error
  4. Program continues after the catch block

Swift Quiz 1

What happens if an exception is thrown but there's no matching catch block?

Answer: The program terminates abnormally and calls std::terminate(), which typically calls abort(). Your program crashes. This is why it's important to either catch exceptions or let them propagate to a handler that can catch them.

3. Custom Exception Classes

So far, we've been throwing primitive types like string and int. This works, but it's limited. A string can only hold a message. An int can only hold a number. What if you want to store multiple pieces of information about an error?

That's where custom exception classes come in. We can create our own classes specifically for representing errors. These classes can have multiple data members, methods to display error information, and anything else we need.

Swift Quiz 2

Why do we catch exceptions by reference (catch (Exception& e)) instead of by value (catch (Exception e))?

Answer: Catching by reference avoids "slicing." When you have exception hierarchies (derived exceptions), catching by value copies only the base class part and loses the derived class information. Catching by reference preserves the full object and supports polymorphism. It's also more efficient since no copying occurs.

4. Exception Hierarchies

Just like regular classes, exception classes can use inheritance. This lets you create families of related exceptions and catch them at different levels of specificity.

Why is this useful? Imagine you're writing a math library. You might have different types of math errors: division by zero, square root of negative number, logarithm of zero, etc. You could create a separate exception class for each one, but then you'd need a separate catch block for each. That's a lot of repetition.

With exception hierarchies, you can create a base class MathException and derive specific exceptions from it. Then you can catch all math errors with one catch (MathException& e) block, or catch specific ones individually.

  • Line 8: We use protected instead of private so derived classes can access message.

Why is what() virtual? Because we're catching by reference to the base class. When we call e.what(), polymorphism ensures we call the correct version. If a derived class overrides what(), that version runs. If not, the base version runs.

Catch Order Matters

When you have multiple catch blocks for a hierarchy, the order matters. C++ checks catch blocks from top to bottom and uses the first match.

Here's the right way to do it:

try {
    divide(10, 0);
}
catch (DivisionByZeroException& e) {
    // Specific handler - catches ONLY DivisionByZeroException
    cout << "Division error: " << e.what() << endl;
}
catch (NegativeSquareRootException& e) {
    // Specific handler - catches ONLY NegativeSquareRootException
    cout << "Square root error: " << e.what() << endl;
}
catch (MathException& e) {
    // General handler - catches all OTHER MathException types
    cout << "Math error: " << e.what() << endl;
}

Rule: Most specific (derived) exceptions first, most general (base) exceptions last.

⚠️ Wrong Order: If you put the base class catch first, it catches everything and the derived catches never run! 
// WRONG! This won't work as expected
try {
    divide(10, 0);
}
catch (MathException& e) {
    // This catches EVERYTHING - base and derived
    cout << "Math error: " << e.what() << endl;
}
catch (DivisionByZeroException& e) {
    // This NEVER runs - unreachable code!
    cout << "Division error: " << e.what() << endl;
}
Swift Note: Make your error methods virtual in the base class. This enables polymorphism, so calling the method on a base class reference actually calls the derived class version if it's overridden.

Swift Quiz 3

In an exception hierarchy with BaseException and DerivedException : public BaseException, if you write catch (BaseException e) (without &), what problem occurs?

Answer: Object slicing occurs. When you catch by value, the exception object is copied. If a DerivedException is thrown, only the BaseException part gets copied. All the derived class data and behavior is "sliced off." This means if you call a virtual function, it calls the base version, not the derived version. Always catch by reference to avoid this!

5. Rethrowing Exceptions

Sometimes you want to catch an exception, do some cleanup or logging, and then pass it to a higher-level handler. This is called rethrowing.

Why would you do this? Imagine a function that opens a file. If an error occurs, you want to close the file before the exception propagates. But you also want the caller to know that an error happened. The solution: catch the exception, close the file, then rethrow the exception.

When to Rethrow

Rethrowing is useful when you need to:

  • Log errors: Record what went wrong at a low level
  • Clean up resources: Close files, free memory, release locks
  • Add context: Wrap the exception in a higher-level exception with more information
  • Delegate decisions: Let a higher-level function decide what to do

Swift Quiz 4

What's the difference between throw; and throw e; inside a catch block?

Answer: throw; rethrows the original exception object (preserves type and data perfectly). throw e; creates a NEW exception by copying e. If e is a base class reference pointing to a derived object, throw e; will slice it and throw only the base part. Always use throw; for rethrowing!

6. Exception Safety

Exception-safe code is code that works correctly even when exceptions are thrown. This is important because when an exception occurs, you need to make sure your program doesn't leak resources or leave data in a broken state.

The Problem: Resource Leaks

Look at this code. Can you spot the problem?

#include 
using namespace std;

void riskyFunction() {
    int* data = new int[100];  // Allocate memory

    // What if this throws an exception?
    if (someCondition) {
        throw string("Error!");
    }

    delete[] data;  // This line never executes if exception thrown!
}

The problem: When the exception is thrown on line 9, the function immediately stops. Line 12 (delete[] data;) never executes. We've leaked 100 integers worth of memory.

Every time this function is called and throws an exception, we leak more memory. Eventually, the program runs out of memory and crashes.

Solution: Cleanup in Catch Blocks

We need to make sure cleanup happens whether an exception is thrown or not. Here's how:

🎮 Playground 8: Fix the Resource Leak

Challenge:
  • Add a try-catch block inside enrollStudent → Expected: Wrap the age check in try, add catch(...) that deletes s and rethrows
  • In the catch block, delete s; before rethrowing → Expected: Student destructor runs before exception propagates upward
  • Watch the output - you should see "Destroyed student" even when exception is thrown → Expected: Prints "Created student: Johan Pretorius", then "Destroyed student: Johan Pretorius", then "Error: Student too young!"

The fix:

void enrollStudent(string name, int age) {
    Student* s = new Student(name);

    try {
        if (age < 18) {
            throw string("Student too young!");
        }
        cout << s->name << " enrolled successfully" << endl;
    }
    catch (...) {
        // Cleanup before rethrowing
        delete s;
        throw;  // Rethrow the exception
    }

    delete s;  // Normal cleanup if no exception
}

How it works:

  • If no exception: code runs normally, reaches line 16, deletes s
  • If exception thrown: catch block runs, deletes s, then rethrows
  • Either way, s gets deleted - no leak!
Swift Note: In modern C++, you'd use RAII (Resource Acquisition Is Initialization) and smart pointers to handle this automatically. But in COS 110 with C++98, you need to be careful with manual cleanup in exception handlers.

Three Levels of Exception Safety

  1. No guarantee: Code might leak resources or corrupt data if exception thrown (bad!)
  2. Basic guarantee: No resource leaks, but data might be in a modified state (acceptable)
  3. Strong guarantee: Operation either completes fully or leaves everything unchanged (ideal)

For COS 110, aim for at least the basic guarantee: always clean up resources, even when exceptions occur.

Swift Quiz 5

What does catch (...) (three dots) do?

Answer: catch (...) is a catch-all handler that catches any exception of any type. It's useful as a last resort to prevent program termination, but you can't access the exception object or get any information about it. Use it carefully and typically as the very last catch block.

7. Common Mistakes to Avoid

Let's look at the most frequent mistakes students make with exception handling, and how to fix them.

Mistake 1: Catching by Value (Slicing)

This is one of the most dangerous mistakes:

#include 
using namespace std;

class BaseException {
public:
    virtual void show() { cout << "Base" << endl; }
};

class DerivedException : public BaseException {
public:
    void show() { cout << "Derived" << endl; }
};

int main() {
    try {
        throw DerivedException();
    }
    catch (BaseException e) {  // Caught by VALUE - wrong!
        e.show();  // Prints "Base" even though we threw Derived!
    }
    return 0;
}

What happens: When you catch by value, C++ copies the exception. If you throw a DerivedException but catch a BaseException, only the base part gets copied. The derived part is "sliced off." When you call e.show(), it calls the base version, not the derived version.

The fix: Always catch by reference!

catch (BaseException& e) {  // Catch by reference - correct!
    e.show();  // Now this calls the Derived version
}

Mistake 2: Wrong Catch Order

try {
    // code that might throw
}
catch (BaseException& e) {
    // This catches EVERYTHING - base and derived
}
catch (DerivedException& e) {
    // This NEVER runs - unreachable code!
}

What happens: C++ checks catch blocks from top to bottom. The first match wins. Since DerivedException is derived from BaseException, the first catch block matches and runs. The second catch is never reached.

The fix: Put most specific (derived) exceptions first, most general (base) exceptions last.

try {
    // code
}
catch (DerivedException& e) {
    // Specific - checked first
}
catch (BaseException& e) {
    // General - checked last
}

Mistake 3: Not Cleaning Up Resources

void processFile() {
    int* data = new int[1000];

    readFile();  // Might throw exception

    delete[] data;  // Never reached if exception thrown!
}

What happens: If readFile() throws an exception, delete[] data never executes. Memory leak.

The fix: Use try-catch with cleanup in the catch block, or avoid manual new/delete when possible.

void processFile() {
    int* data = new int[1000];

    try {
        readFile();
    }
    catch (...) {
        delete[] data;  // Cleanup before rethrowing
        throw;
    }

    delete[] data;  // Normal cleanup
}

Mistake 4: Empty Catch Blocks

try {
    riskyOperation();
}
catch (...) {
    // Silent failure - error is hidden!
}

What happens: The error is completely hidden. The program continues as if nothing went wrong. This makes debugging nearly impossible.

The fix: At minimum, log the error. Never silently swallow exceptions unless you have a very good reason.

try {
    riskyOperation();
}
catch (...) {
    cout << "Error occurred in riskyOperation" << endl;
    // Or log to file, or notify user, etc.
}

Summary

  • try-catch-throw: try wraps risky code, throw signals an error, catch handles it
  • Custom exceptions: Create exception classes to carry multiple pieces of information
  • Exception hierarchies: Use inheritance to group related exceptions; catch derived before base
  • Catch by reference: Always use catch (Exception& e) to avoid slicing
  • Rethrowing: Use throw; in a catch block to pass exception to higher-level handler
  • Exception safety: Always clean up resources, even when exceptions occur
  • Catch order: Most specific (derived) exceptions first, most general (base) last
  • Resource management: Use try-catch to ensure cleanup code runs
  • Never catch by value: Slicing destroys polymorphism
  • Never silently swallow exceptions: At least log them

You now have a solid foundation in exception handling. Practice writing exception-safe code, and always think about what happens when things go wrong!
