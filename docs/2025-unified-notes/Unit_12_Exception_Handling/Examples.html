Example 1: Bank Transaction Validator

Problem

Build a withdrawal validator for a banking system. The function must check three conditions before processing:

  • Amount must be positive (not zero or negative)
  • Sufficient funds available in account
  • Daily withdrawal limit not exceeded

If any validation fails, throw a descriptive exception. Test with multiple scenarios including valid withdrawals, insufficient funds, and limit violations.

Approach

We use exceptions for validation failures instead of error codes. Each validation check throws a string exception with a descriptive message if it fails. The caller wraps the function in try-catch blocks to handle errors appropriately. This approach is cleaner than returning special values like -1 or checking multiple boolean flags.

The validation order matters: check cheapest conditions first (positive amount) before expensive ones (database lookups for balance). This fails fast on obviously invalid input.

How It Works

  1. Validation order: We check conditions from simplest to most complex. Negative amounts fail immediately without checking balance or limits.
  2. Exception messages: Each thrown string contains specific details about what went wrong. For insufficient funds, we include both the balance and requested amount.
  3. Early exit: When any throw executes, the function stops immediately. Lines after the throw never run.
  4. Catch handling: Each test case wraps the function call in try-catch. If an exception occurs, it's caught and printed. Otherwise, the success message displays.
  5. Program continues: After catching an exception, the program doesn't crash. It continues to the next test case, demonstrating graceful error handling.
Why this is better than error codes: Compare to: int errorCode = processWithdrawal(...); if (errorCode == -1) { /* insufficient funds */ } else if (errorCode == -2) { /* limit exceeded */ }. Exceptions force the caller to handle errors explicitly.

Example 2: Anime Streaming Service Error Handler

Problem

Create an anime streaming service that validates episode requests. Build two custom exception classes:

  • EpisodeNotFoundException - stores anime title, requested episode number, and total available episodes
  • SubscriptionExpiredException - stores username and expiry date

Each exception class should have a display() method that prints formatted error information. The streaming function should check subscription status first, then validate episode numbers.

Approach

Custom exception classes let us store multiple pieces of error information instead of just a string message. When we catch these exceptions, we can call their display() methods to show formatted errors with all relevant details.

We check subscription first because there's no point validating episode numbers if the user can't watch anyway. This is another example of failing fast on the cheapest check.

How It Works

  1. Custom exception classes: These are just regular classes - nothing special about them. Any class can be thrown as an exception.
  2. Multiple data members: EpisodeNotFoundException stores three pieces of information (anime title, episode number, total episodes). This is much more useful than just throwing "episode not found".
  3. Display methods: Instead of simple error messages, we can format output nicely with borders and labels, making errors user-friendly.
  4. Catching specific types: We have separate catch blocks for each exception type. The order doesn't matter here since they're unrelated (neither inherits from the other).
  5. Catching by reference: We use catch (EpisodeNotFoundException& e) to avoid copying the exception object. This is more efficient and avoids potential slicing issues.
Important: Exception classes don't need to inherit from anything special. In Java, exceptions must extend Exception, but in C++ you can throw any type - even primitives like throw 42;. However, classes are better because they can carry multiple pieces of information.

Example 3: File Manager with Resource Cleanup

Problem

Write two versions of a file processing function:

  • Unsafe version: Allocates a file handle, processes it, and deletes it. If processing throws an exception, the file handle leaks.
  • Safe version: Uses try-catch to ensure the file handle is deleted even when exceptions occur.

Create a FileHandle class with a constructor that prints when opened and a destructor that prints when closed. This lets us visually track whether resources are being cleaned up properly.

Approach

The unsafe version demonstrates a common bug: when an exception is thrown, the function exits immediately and cleanup code after the throw never runs. This causes resource leaks.

The safe version wraps risky code in try-catch. If an exception occurs, the catch block performs cleanup (deletes the resource) then rethrows the exception using throw;. This ensures cleanup happens whether the function succeeds or fails.

How It Works

  1. Resource leak in unsafe version: When the exception is thrown, the function exits immediately. The delete file; line never executes. The FileHandle destructor never runs, so we never see "Closed file". The memory is leaked.
  2. Catch-all handler: The safe version uses catch (...) with three dots. This catches any exception type - useful when you need cleanup but don't care about the specific error.
  3. Rethrowing with throw: After cleanup, we use throw; with no argument. This rethrows the exact same exception object that was caught. Don't use throw error; because we don't have a named exception here.
  4. Two cleanup paths: The safe version has cleanup in both the catch block (error path) and after the try-catch (success path). This guarantees the resource is freed regardless of whether an exception occurs.
  5. Exception propagation: The exception still propagates to the caller after cleanup. The safe version doesn't hide the error - it just ensures cleanup happens first.
Real-world importance: In production systems, leaking file handles causes "too many open files" errors. Leaking database connections exhausts connection pools. Leaking memory eventually crashes the program. Exception-safe resource management is critical for reliable software.

Example 4: Music Player Playlist Manager

Problem

Build a playlist manager with exception hierarchies. Create a base exception class PlaylistException and two derived classes:

  • TrackNotFoundException - includes track title
  • PlaylistFullException - includes current count and maximum capacity

The base class should have a virtual display() method that derived classes override. Demonstrate catching exceptions at different levels: specific derived types first, then general base type.

Approach

Exception hierarchies work exactly like regular class hierarchies. We use inheritance to group related exceptions under a common base class. This lets us catch all playlist errors with one handler, or catch specific error types individually.

The base class method must be virtual to enable polymorphism. When we catch with a base class reference but the actual thrown object is a derived class, the derived class's display method will be called.

How It Works

  1. Exception inheritance: We use : public PlaylistException to create a hierarchy. Derived exceptions automatically get the base class's message and playlistName members.
  2. Protected members: The base class uses protected instead of private so derived classes can access message and playlistName. This is important - private members aren't accessible in derived classes.
  3. Virtual display method: The virtual keyword in the base class enables polymorphism. When we catch with PlaylistException& but the actual object is TrackNotFoundException, the derived class's display() is called.
  4. Catch order: Derived classes must be caught before base classes. If we put catch (PlaylistException& e) first, it would catch everything and the derived catches would never run.
  5. Test 4 polymorphism: We catch with the base class reference but throw a TrackNotFoundException. Because display() is virtual, we see the track-specific error message, not the generic base class message.
  6. Virtual destructor: The base class needs virtual ~PlaylistException() {}. This ensures proper cleanup if we ever delete a derived exception through a base class pointer.
Catch order reminder: If you write catch (PlaylistException& e) before catch (TrackNotFoundException& e), the base handler catches everything. The derived handler becomes unreachable dead code. Always put specific exceptions first, general exceptions last.
Flexibility benefit: With hierarchies, you can handle errors at different granularities. Need specific handling for each error type? Use multiple catches. Just want to log all playlist errors the same way? Use one base class catch. The hierarchy gives you options.
