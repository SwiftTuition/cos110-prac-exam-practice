How It Works - Step by Step

The validation sequence: The validateAge() function checks conditions in order from most fundamental to most specific. We check for negative ages first because that's a data type issue, then check age ranges.

Let's trace through validateAge(16):

  1. Check if (age < 0): 16 is not negative, so skip this check
  2. Check if (age < 18): 16 is less than 18, so this condition is TRUE
  3. Throw TooYoungException("Must be 18 or older to register", 16)
  4. Execution immediately jumps to the catch blocks in main()
  5. The first catch block checks if the exception is InvalidAgeException - NO, skip it
  6. The second catch block checks if the exception is TooYoungException - YES! Catch it
  7. Print error message and the attempted age (16)
  8. Continue execution after the try-catch block

Why separate exception classes?

We could have used just one generic AgeException class with different messages. But using separate classes allows us to:

  • Catch specific errors: We can handle "too young" differently from "negative age" if needed
  • Store relevant data: TooYoungException stores the attempted age so we can display it
  • Type safety: The compiler can verify we're catching the right types

Let's trace through validateAge(-5):

  1. Check if (age < 0): -5 is negative, so this condition is TRUE
  2. Throw InvalidAgeException("Age cannot be negative!")
  3. Execution jumps to catch blocks - the FIRST catch block matches
  4. Print "✗ Invalid Age: Age cannot be negative!"
  5. The other checks (age < 18, age > 120) are never evaluated because we already threw an exception
Key pattern: Check conditions from most fundamental to most specific. Once you throw an exception, the rest of the function doesn't execute - the exception immediately transfers control to the nearest matching catch block.

How It Works - Step by Step

Check order matters: We check network connectivity first, then subscription, then region. Why? Because if there's no network, we can't even verify the subscription or region restrictions.

Let's trace through Test 2 (expired subscription):

  1. Call checkAccess(false, true, true, "BAKI", "South Africa")
  2. Check if (!networkOk): networkOk is true, so !networkOk is false - skip
  3. Check if (!isSubscribed): isSubscribed is false, so !isSubscribed is TRUE
  4. Throw SubscriptionExpiredException("2025-10-15")

  6. First catch: Is it a NetworkException? No, skip
  7. Second catch: Is it a SubscriptionExpiredException? YES! Catch it

Using display() methods: Each exception class has its own display() method that knows how to format its specific error. This is cleaner than having all the formatting logic in main().

Let's trace through Test 4 (network error):

  1. Call checkAccess(true, true, false, "BAKI", "South Africa")
  2. Check if (!networkOk): networkOk is false, so !networkOk is TRUE
  3. Throw NetworkException(503) immediately
  4. The subscription and region checks are NEVER executed because we already threw
  5. Jump to catch blocks, first catch matches NetworkException
  6. Display "Network error (code 503)" and connection message

Why store data in exception objects?

  • SubscriptionExpiredException stores the expiration date so we can show when it expired
  • RegionBlockedException stores both the content title and region for a helpful error message
  • NetworkException stores the HTTP error code for debugging
Real-world pattern: Streaming services like Netflix, Crunchyroll, and Disney+ use exactly this pattern - checking network, authentication, and region restrictions in sequence, with specific error messages for each failure case.

What's Wrong?

The Bug

Memory leak in createArray() (lines 16-18)

The function allocates memory with new int[size] BEFORE checking if the size is valid. When we throw the exception on line 19, we never delete the allocated array!

Here's what happens with createArray(-3):

  1. Line 17: new int[size] allocates memory (even with negative size, implementation-defined behavior - might allocate, might crash)
  2. Line 18: Check if (size <= 0) - TRUE for -3
  3. Line 19: Throw exception and jump to catch block
  4. Problem: We never executed delete[] arr, so the memory leaked!
  5. The pointer arr is lost when we throw - we can never free it now

Second bug: Validation order is wrong

We should validate BEFORE allocating memory, not after. This prevents:

  • Memory leaks when validation fails
  • Undefined behavior from allocating with invalid sizes
  • Wasting resources on memory that will immediately be discarded

What We Fixed - Step by Step

Fix: Validate BEFORE allocating (lines 17-19)

  1. Check if size is invalid FIRST: if (size <= 0)
  2. If invalid, throw exception immediately - NO memory has been allocated yet
  3. Only allocate memory AFTER validation passes: int* arr = new int[size]

Why this fixes the leak:

In the buggy version, when we threw the exception, we had already allocated memory but didn't clean it up. In the fixed version, if we throw an exception, we haven't allocated anything yet - no leak possible!

Let's trace through the fixed createArray(-3):

  1. Check if (size <= 0): -3 is less than 0, so TRUE
  2. Throw InvalidSizeException("Size must be positive!")
  3. We NEVER reach line 21 where new int[size] would execute
  4. No memory allocated = no memory leaked!
  5. Exception caught in main(), error message printed
Golden rule for exception safety: ALWAYS validate input BEFORE allocating resources (memory, files, network connections, etc.). If validation fails, you want to throw the exception without having acquired any resources that need cleanup.
Exception safety principle: This is called the "RAII" (Resource Acquisition Is Initialization) principle - don't acquire resources until you're sure you can use them safely. Validate first, allocate second.

How It Works - Step by Step

Exception hierarchy structure:

LibraryException (base class)
├── LibraryFullException
├── AlbumNotFoundException
└── InvalidIDException

All three derived exceptions inherit from LibraryException, which means we can catch ANY library error with a single catch (LibraryException& e) block. This is polymorphism in action!

Why use virtual display()?

The base class declares display() as virtual, allowing derived classes to override it. When we catch with LibraryException& e, calling e.display() will invoke the CORRECT derived class version based on what was actually thrown (polymorphism).

Let's trace through adding an album with invalid ID:

  1. Call addAlbum(-1, "25", "Adele")
  2. Check if (id <= 0): -1 is less than 0, so TRUE
  3. Throw InvalidIDException("Album ID must be positive", -1)
  4. Jump to catch block in main()
  5. Catch with LibraryException& e - this catches InvalidIDException because it's a derived class
  6. Call e.display() - polymorphism ensures InvalidIDException::display() runs, not the base class version
  7. Output: "Invalid ID: Album ID must be positive" and "ID -1 is not valid (must be positive)."

Let's trace through adding the 6th album (library full):

  1. Library currently has 5 albums (count = 5, capacity = 5)
  2. Call addAlbum(6, "÷ (Divide)", "Ed Sheeran")
  3. Check if (id <= 0): 6 is positive, so FALSE - skip
  4. Check if (count >= capacity): 5 >= 5 is TRUE
  5. Throw LibraryFullException("Cannot add more albums", 5)
  6. Catch with LibraryException& e
  7. Call e.display() which invokes LibraryFullException::display()
  8. Output: "Library Full: Cannot add more albums" and "Maximum capacity is 5 albums."

Let's trace through searching for album ID 3:

  1. Call findAlbum(3)
  2. Check if (id <= 0): 3 is positive, so FALSE - skip
  3. Loop through albums array:
    • i=0: albums[0].id = 1, not equal to 3
    • i=1: albums[1].id = 2, not equal to 3
    • i=2: albums[2].id = 3, MATCH! Return this album
  4. Back in main(), we successfully got the album without throwing
  5. Print "✓ Found: 'Subliminal' by Maître Gims"

Let's trace through searching for non-existent ID 99:

  1. Call findAlbum(99)
  2. Check if (id <= 0): 99 is positive, so FALSE - skip
  3. Loop through all albums (i = 0 to 4), none have id = 99
  4. Loop completes without finding a match
  5. Throw AlbumNotFoundException("Album not in library", 99)
  6. Catch with LibraryException& e
  7. Call e.display() which invokes AlbumNotFoundException::display()
  8. Output: "Album Not Found: Album not in library" and "No album with ID 99 exists."

Why is the base class constructor called in derived classes?

Look at line 23: : LibraryException(msg), maxCapacity(capacity). The derived class constructor explicitly calls the base class constructor to initialize the message member. This is standard inheritance - the base class handles common data (message), and derived classes handle their specific data (maxCapacity, searchedID, etc.).

Real-world pattern: Exception hierarchies like this are used in professional codebases (Java, C#, Python). You can catch broadly (catch (LibraryException& e)) to handle any library error, or catch specifically (catch (InvalidIDException& e)) when you need special handling for certain errors.
