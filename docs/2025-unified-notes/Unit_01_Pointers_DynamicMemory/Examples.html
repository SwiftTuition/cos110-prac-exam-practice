Real-World Examples

Here are four complete examples showing pointers and dynamic memory in action. Each example builds on the concepts from Theory with thorough explanations and suggestions for experiments you can try.

Example 1

Student Grade Tracker with Pointers

The Scenario

Pieter, a tutor at Swift Tuition, tracks grades for three students: Chantelle, Ayanda, and Mpho. He needs functions that can modify the actual grade variables, not just copies of them. This is where pointers become useful.

The Problem We're Solving

When you pass a variable to a function normally (by value), C++ creates a copy of that variable for the function to use. Any changes the function makes only affect the copy, not your original variable. Look at what happens here: 

void tryToAddBonus(int grade, int bonus) {
    grade = grade + bonus;  // Only changes the local copy!
}

int main() {
    int chantelle = 75;
    tryToAddBonus(chantelle, 5);
    // chantelle is STILL 75! The function got a copy.
}

The grade parameter inside the function is a completely separate variable from chantelle. When the function ends, the copy disappears, and our original chantelle variable remains unchanged at 75.

To actually modify the original variable, we need to pass its address (where it lives in memory) instead of its value. That's what pointers let us do.

How This Code Works

Let's break down the applyBonus function line by line:

  1. Function signature: void applyBonus(int *gradePtr, int bonus)
    The int *gradePtr parameter means "gradePtr is a pointer to an int". It will store the memory address of an integer variable.
  2. Calling the function: applyBonus(&chantelle, 5);
    The & operator gets the address of chantelle. So we're passing the location where chantelle lives in memory, not its value.
  3. Modifying through the pointer: *gradePtr = *gradePtr + bonus;
    The *gradePtr on the left means "the value at the address stored in gradePtr". We read the current value (*gradePtr on the right), add the bonus, and write it back to the same memory location. This changes the original chantelle variable.
Swift Note: Think of pointers like house addresses. If I want to paint your house, you give me your address (&chantelle), I go to that location (*gradePtr), and make changes there. The changes happen at your actual house, not at a photograph of it.

Things to Experiment With

Experiment 1: Change the applyBonus function to use += instead of = ... +. Does *gradePtr += bonus; work the same way? Try it!
Experiment 2: What happens if you forget the & when calling the function? Try changing applyBonus(&chantelle, 5) to applyBonus(chantelle, 5). Read the compiler error carefully - it's telling you about a type mismatch.
Experiment 3: Add a cout statement inside applyBonus to print the address: cout << "Address: " << gradePtr << endl;. Then in main, print &chantelle. Are they the same? They should be - the function received the exact address of chantelle.
Experiment 4: Create a function void resetGrade(int *gradePtr) that sets a grade to 0. Call it with one of the student grades. Confirm it modifies the original variable.
Example 2

Dynamic Student Record System

The Scenario

Trevor runs a small tutoring business. Students enroll and unenroll at different times, so he can't know in advance how many student records he'll need. He needs to create student records dynamically (while the program is running) and clean them up when students complete their courses.

Why Dynamic Memory?

So far, all our variables have been automatic (also called stack variables). They're created when we declare them and destroyed automatically when they go out of scope: 

int main() {
    int student1 = 85;  // Created here
    int student2 = 78;  // Created here
    // ...
}  // Both destroyed here when main() ends

This works fine when you know exactly how many variables you need. But what if the number changes while the program runs? What if Trevor's business grows from 2 students to 50? We can't declare 50 variables - we need to create variables at runtime based on how many students actually enroll.

That's where dynamic memory allocation comes in. The new operator creates variables on the heap (a separate memory area), and those variables live until you explicitly destroy them with delete.

Understanding Each Step

Step 1: Creating with new

int *annelieScore = new int;

This line does three things:

  1. new int asks the operating system for enough memory to store one integer on the heap
  2. The OS finds a free spot in memory and reserves it for us
  3. The address of that memory location is returned and stored in annelieScore

After this line, annelieScore points to a valid integer in memory, but that integer contains garbage (whatever was in that memory before). That's why we immediately set it: *annelieScore = 0;

Step 2: Creating with initialization

int *siphoScore = new int(78);

This is a shortcut that combines allocation and initialization. It creates a new integer on the heap AND sets it to 78 in one line. This is better than doing it in two steps because there's never a moment where the memory contains garbage.

Step 3: Accessing the value

cout << *annelieScore;

Remember: annelieScore stores an address. To access the value at that address, we use the dereference operator *. Without it, we'd print the address (a hexadecimal number like 0x7ffd5e3c4a2c), not the score.

Step 4: Deallocating with delete

delete annelieScore;

This tells the operating system "I'm done with the memory at this address - you can use it for something else now." The memory is freed and returned to the OS. However, annelieScore still contains the old address! This is dangerous - it's now a dangling pointer pointing to memory we don't own anymore.

Step 5: Setting to NULL

annelieScore = NULL;

This makes the pointer "safe". NULL is a special value (0) that means "this pointer doesn't point to anything". Now if we accidentally try to use annelieScore later, we can check if (annelieScore == NULL) and avoid accessing invalid memory. Dereferencing a NULL pointer will crash immediately (which is actually good - it shows us there's a bug), while dereferencing a dangling pointer might appear to work but cause random, hard-to-find bugs later.

Best Practice: ALWAYS set pointers to NULL after deleting them. This prevents dangling pointer bugs. The pattern is: delete ptr; ptr = NULL;
Memory Leak Warning: If you create something with new but forget to delete it, that memory stays allocated even after your program no longer has access to it. This is called a memory leak. If it happens in a loop, your program will slowly consume more and more memory until it crashes or slows down the system.

Things to Experiment With

Experiment 1: Before deleting annelieScore, add a line that prints its address: cout << "Address: " << annelieScore << endl;. Then after setting it to NULL, print it again. You'll see it change from something like 0x55a2b3c4d5e6 to 0 (which is NULL).
Experiment 2: What happens if you comment out the delete siphoScore; line? The program still works, but you've created a memory leak. The memory is allocated but never freed. Try creating 1000 student records in a loop without deleting any - you'll see memory usage climb (though you'd need millions to actually run out of memory on modern systems).
Experiment 3: What happens if you try to use a pointer after deleting it? Comment out annelieScore = NULL;, then try to access *annelieScore after the delete. This is a dangling pointer - the results are undefined. It might work, might crash, or might give you garbage values.
Experiment 4: What happens if you delete the same pointer twice? Try adding another delete siphoScore; after the first one (before setting to NULL). This is called a double delete and usually causes a crash. But if you set to NULL after the first delete, the second delete is safe (deleting NULL does nothing).
Experiment 5: Create a third student record without using a pointer variable at all: new int(90); with no assignment. Can you access this value later? No! You allocated memory but lost the address immediately. This is an instant memory leak. The only way to access dynamically allocated memory is through a pointer variable that stores its address.
Example 3

Concert Ticket Allocation System

The Scenario

Karabo is organizing a Maître Gims concert in Johannesburg. VIP ticket sales open at 9 AM, and she doesn't know how many will sell until that moment. Once she knows the number, she needs to generate sequential ticket numbers, calculate revenue, and manage the allocation. This requires a dynamic array - an array whose size isn't known until runtime.

Regular Arrays vs Dynamic Arrays

You're familiar with regular arrays from COS 132: 

int tickets[5];  // Size must be a constant!
// You CANNOT do: int tickets[numVIP]; if numVIP is a variable

In C++98, array sizes must be known at compile time. They can't be variables that change while the program runs. But what if numVIP is entered by the user? We need to allocate an array after we know the size. That's what new[] does - it creates an array on the heap with a size determined at runtime.

Understanding Dynamic Arrays

Allocation: new[] with square brackets

int *ticketNumbers = new int[numVIP];

This allocates a block of memory large enough for numVIP integers. If numVIP is 5, it allocates space for 5 consecutive integers in memory. The address of the first integer is stored in ticketNumbers. Even though ticketNumbers is a pointer to a single int, it now points to the first element of an array.

Memory layout after new int[5]: 

ticketNumbers → [int][int][int][int][int]
                 ↑                        ↑
              index 0                  index 4

The pointer stores the address of the first element.
All 5 integers are consecutive in memory.

Accessing elements: Same as regular arrays

ticketNumbers[i] = 1001 + i;

Even though ticketNumbers is a pointer, we can use array notation [] to access elements. Under the hood, ticketNumbers[i] is actually shorthand for *(ticketNumbers + i) - the compiler calculates the address of the i-th element and dereferences it. But you can just think of it as a normal array. The syntax is identical.

Important: You MUST remember the size

Unlike regular arrays, dynamic arrays don't "remember" their size. The pointer ticketNumbers just stores an address - it has no idea how many elements you allocated. That's why we keep numVIP in a separate variable. If you lose numVIP, you have no way to know how large the array is, and you risk accessing memory beyond the array's end (buffer overflow).

Deallocation: delete[] with square brackets

delete [] ticketNumbers;

This is IMPORTANT. When you allocate an array with new[], you MUST deallocate with delete[] (with the brackets). Using plain delete only frees the first element, leaving the other 4 integers allocated - that's a memory leak. The brackets tell C++ "this is an array, free all elements."

⚠️ Common Mistake: Using delete instead of delete[] on an array. If you allocated with new[], you MUST use delete[]. If you allocated with new (single object), use delete. Mismatching causes undefined behavior (usually a crash or memory corruption).

Why This Pattern Matters

Dynamic arrays are everywhere in real programs:

  • User input: "How many students are enrolling?" - you don't know until the user tells you
  • File processing: "How many lines are in this file?" - you don't know until you read it
  • Network data: "How many packets will arrive?" - depends on network conditions
  • Data structures: Linked lists, trees, and graphs all use dynamic memory to grow and shrink as needed

This is why you'll use new and delete constantly in COS 110, especially when we cover data structures in Units 10-11 (linked lists, stacks, queues).

Things to Experiment With

Experiment 1: Change numVIP to different values (try 1, 10, 100). Notice how the same code works regardless of the array size. That's the power of dynamic allocation - the size is a runtime decision.
Experiment 2: What happens if you try to access ticketNumbers[numVIP]? This is one position past the end of the array (valid indices are 0 to numVIP-1). Try adding cout << ticketNumbers[numVIP] << endl;. It might print garbage, might crash, or might appear to work - this is undefined behavior. The program has no bounds checking.
Experiment 3: What happens if you forget delete[]? Comment out the delete line and run the program. It still works, but you've leaked memory. For a small program that runs once, this doesn't matter (the OS reclaims all memory when the program exits). But if this was in a loop running thousands of times, you'd slowly consume all available memory.
Experiment 4: What happens if you use delete instead of delete[]? Change delete [] ticketNumbers to delete ticketNumbers (no brackets). The program might crash, might appear to work, or might cause silent memory corruption. This is undefined behavior - the outcome depends on your compiler and system. ALWAYS match new[] with delete[].
Experiment 5: Can you create a 2D array dynamically? Try allocating an array of pointers: int **grid = new int*[3]; then in a loop, allocate each row: grid[i] = new int[4];. You now have a 3x4 grid. Don't forget to delete each row and then the array of pointers!
Experiment 6: Add code that lets the user input numVIP with cin. Now the array size is truly determined at runtime by user input. This is the most common use case for dynamic arrays.

Bug 1: Memory Leak (Lost Array)

Location: Line 24 - quantities = newItem;

What's wrong: The quantities pointer originally points to an array of 3 integers (allocated on line 9). When we reassign it to point to newItem, we lose the address of the original array. The 3 integers are still allocated in memory, but we have no way to access them anymore - the only pointer that knew their address now points to something else.

Why it's a problem: Those 3 integers will never be freed. They're leaked memory - allocated but inaccessible. In a long-running program or a loop, this would slowly consume all available memory.

Visual representation: 

After line 9:
quantities → [50][30][75]    (array of 3 ints)

After line 21:
newItem → [100]              (single int)

After line 24:
quantities → [100]           (now points to newItem's location)
             [50][30][75]    (orphaned! no pointer to them)

Bug 2: Wrong Delete Operator

Location: Line 28 - delete quantities;

What's wrong: After the reassignment, quantities points to the single integer originally allocated by newItem. That integer was allocated with new (not new[]), so using delete (not delete[]) is actually correct at this point. However, the original intent was probably to delete the array, which would require delete[].

But there's a deeper issue: we're deleting quantities, which now points to the same memory as newItem. This means newItem is now a dangling pointer (points to freed memory). If we tried to use newItem after this, we'd access invalid memory.

Bug 3: Incomplete Cleanup

What's wrong: We need to free both allocations: the original array AND the single integer. But because we lost the pointer to the array (bug #1), we can't free it. Even if we delete quantities (which frees the single int), the array is still leaked.

Additionally, we never set pointers to NULL after deleting, so they're dangling pointers.

The Correct Approach

Option 1: Delete the array before reassigning 

// Display initial inventory
cout << "Initial Inventory:" << endl;
for (int i = 0; i < numItems; i++) {
    cout << "  Item " << (i+1) << ": "
         << quantities[i] << " units" << endl;
}

// Clean up the array BEFORE reassigning the pointer
delete [] quantities;
quantities = NULL;

// Now create the new item
int *newItem = new int;
*newItem = 100;
quantities = newItem;  // Safe now - we freed the old memory

cout << "\nNew item added: " << *quantities << " units" << endl;

// Clean up the single integer
delete quantities;
quantities = NULL;

cout << "\nSystem shutting down..." << endl;

Option 2: Keep both allocations separate (better design) 

// Display initial inventory
cout << "Initial Inventory:" << endl;
for (int i = 0; i < numItems; i++) {
    cout << "  Item " << (i+1) << ": "
         << quantities[i] << " units" << endl;
}

// Create new item with its own pointer
int *newItem = new int(100);
cout << "\nNew item added: " << *newItem << " units" << endl;

// Clean up array
delete [] quantities;
quantities = NULL;

// Clean up single item
delete newItem;
newItem = NULL;

cout << "\nSystem shutting down..." << endl;

Key Lessons

  • Never reassign pointers without freeing the old memory first - you'll create a memory leak
  • Match your delete operators to your allocations: new → delete, new[] → delete[]
  • Every new needs exactly one delete - no more (double delete), no less (memory leak)
  • Set pointers to NULL after deleting - makes dangling pointers detectable
  • Keep allocations and deallocations symmetric and clear - if you allocate in one scope, try to deallocate in the same scope

In later units (especially Unit 4), you'll learn about destructors, which automate memory cleanup. But understanding manual memory management with new/delete is essential - you need to know what's happening under the hood.
