Example 1: Animal Sounds - Basic Polymorphism

This is the classic polymorphism example. We have different animals that make different sounds, but we want to treat them all as Animal objects and let each one make its own sound.

The Problem We're Solving

Without virtual functions, we'd need separate functions for each animal type: 

void makeDogSpeak(Dog* d) { /* ... */ }
void makeCatSpeak(Cat* c) { /* ... */ }
void makeBirdSpeak(Bird* b) { /* ... */ }

With polymorphism, we write ONE function that works for all animals: 

void makeAnimalSpeak(Animal* a) {  // Works for ANY animal!
    a->makeSound();
}

How It Works

Step 1: Create polymorphic array

Animal* zoo[3]; - Array of base class pointers that can hold any derived class.

Step 2: Store different derived objects

zoo[0] = new Dog(); - Each element points to a different derived class object.

Step 3: Call through base pointer

zoo[i]->makeSound(); - Because makeSound() is virtual, each object calls its own version.

🔬 Experiments

Experiment 1: Remove the virtual keyword from Animal::makeSound(). What output do you get?

What happens: All three animals print "Some generic animal sound".

Why: Without virtual, static binding is used. The compiler sees Animal* pointers and calls Animal::makeSound() for all of them, ignoring what they actually point to.

Lesson: The virtual keyword is essential for polymorphism.

Experiment 2: Add a new animal class (Snake) that says "Hissss!". Add it to the zoo. Does it work without modifying makeAnimalSpeak()?

What happens: Yes! You can add:

class Snake : public Animal {
public:
    void makeSound() {
        cout << "Hissss!" << endl;
    }
};

And use zoo[3] = new Snake(); - it works immediately.

Why: Polymorphism makes code extensible. You can add new derived classes without changing functions that use the base class.

Experiment 3: Remove the virtual destructor (virtual ~Animal() {}). Does the code still compile and run?

What happens: Code compiles and runs, output looks the same.

Hidden danger: If derived classes allocated memory (like int* data = new int[100]; in constructor and delete[] data; in destructor), that memory would leak!

Why: Without virtual destructor, delete zoo[i]; only calls Animal::~Animal(), not the derived destructors.

Rule: Always make base class destructor virtual when using polymorphism.

Experiment 4: Try storing by value instead of pointer: Animal zoo[3] = {Dog(), Cat(), Bird()}; What happens?

What happens: This won't compile correctly in C++98, but even if you initialize them separately, object slicing occurs.

Why: When you store by value, only the Animal parts fit in each array slot. The Dog/Cat/Bird parts get sliced off. All three become pure Animal objects.

Result: All would say "Some generic animal sound" because they're literally Animal objects now, not derived objects.

Lesson: Polymorphism requires pointers or references, never value copies.

🔬 Experiments

Experiment 1: Try creating a Shape object directly: Shape* s = new Shape(); What error do you get?

What happens: Compiler error: "cannot instantiate abstract class".

Why: Shape has pure virtual functions (= 0), making it abstract. You can't create objects of abstract classes.

Allowed: Shape* s = new Circle(5); - pointers to abstract classes are fine, as long as they point to concrete derived objects.

Experiment 2: Create a Square class that inherits from Rectangle (not Shape). Does polymorphism still work?

Code to try:

class Square : public Rectangle {
public:
    Square(double side) : Rectangle(side, side) {}
};

What happens: Works perfectly! Shape* s = new Square(5); is valid.

Why: Square inherits from Rectangle, which inherits from Shape. Polymorphism works through the whole inheritance chain.

Type relationships: Square IS-A Rectangle IS-A Shape.

Experiment 3: What if Circle implements getArea() but forgets to implement display()?

What happens: Circle becomes abstract! You can't instantiate it.

Why: To be a concrete (instantiable) class, you must implement ALL pure virtual functions from the base class. If even one is missing, the class remains abstract.

Error: "cannot instantiate abstract class Circle"

Experiment 4: Add a getPerimeter() pure virtual function to Shape. What breaks?

What happens: All three shape classes (Circle, Rectangle, Triangle) stop compiling!

Why: Adding a new pure virtual function to the base class means ALL derived classes must implement it. Until they do, they're all abstract.

Fix: Add double getPerimeter() implementation to each derived class.

Lesson: Adding pure virtual functions to a base class is a breaking change - all derived classes must update.

Experiment 1: Add another hero - Uraraka with "Zero Gravity" quirk (makes objects float). Does she integrate seamlessly?

Code to add:

class Uraraka : public Hero {
public:
    Uraraka() : Hero("Ochaco Uraraka", 75) {}

        cout << "  -> Makes objects weightless!" << endl;
    }

    void displayInfo() {
        cout << "Hero: " << name << endl;
        cout << "Quirk: Zero Gravity" << endl;
        cout << "Power Level: " << powerLevel << endl;
    }
};

What happens: Works perfectly! Add team[3] = new Uraraka(); and she's part of the team.

Why: The polymorphic design means heroShowcase() works for ANY hero without modification.

Experiment 2: Add a trainQuirk() function that increases powerLevel. Should it be virtual?

Implementation: Add to Hero base class:

virtual void trainQuirk() {
    powerLevel += 5;
    cout << name << " trained! Power level: " << powerLevel << endl;
}

Should it be virtual? Yes, if different heroes train differently!

For example, Deku might gain more from training (+10 instead of +5) because he's still learning his quirk.

Rule: Make it virtual if behavior might differ across derived classes. Keep it non-virtual if it's always the same.

Experiment 3: What if you make powerLevel private instead of protected?

What happens: Code won't compile! Derived classes can't access powerLevel.

Error in derived classes: "powerLevel is private in Hero"

Fix options:

  1. Keep powerLevel as protected (current approach)
  2. Make it private and add protected int getPowerLevel() and void setPowerLevel(int p)

Protected members are accessible to derived classes but not to outsiders - perfect for inheritance!

Experiment 4: Try calling activateQuirk() through a reference instead of a pointer.

Change function to:

void heroShowcase(Hero& h) {  // Reference instead of pointer
    h.displayInfo();        // Use . instead of ->
    h.activateQuirk();
}

Calling it: heroShowcase(*team[i]); (dereference pointer)

What happens: Works identically! Polymorphism works with references too.

Advantage: References can't be NULL, making them safer if NULL isn't a valid input.

Experiment 1: Are Troop, Building, and Spell abstract or concrete classes?

Answer: They're concrete! You can create objects of them.

Why: They implement ALL pure virtual functions from Card (deploy() and displayInfo()). Even though they're derived from an abstract class, they become concrete by implementing all required functions.

Experiment 2: Create a specific HogRider class that inherits from Troop. Does it need to implement deploy()?

Answer: No, it doesn't HAVE to (but it can if you want custom behavior).

Why: Troop already implements deploy(), so HogRider inherits that implementation.

Minimal implementation:

class HogRider : public Troop {
public:
    HogRider() : Troop("Hog Rider", 4, 800, 160) {}
    // That's it! Inherits deploy() and displayInfo()
};

Custom behavior (optional): Override deploy() to add "HOOOG RIIIDEEER!" sound effect.

Experiment 3: Can you store cards in a Troop* array instead of Card*?

What happens: You can only store Troop objects (and classes derived from Troop).

Problem: Troop* deck[4]; can't hold Building or Spell objects because they don't inherit from Troop.

Error if you try: "cannot convert Building* to Troop*"

Lesson: Use the most general base class (Card*) when you need to store different derived types together.

Experiment 4: Add a getElixirCost() function to Card. Should it be virtual?

Implementation:

int getElixirCost() {  // NOT virtual
    return elixirCost;
}

Should it be virtual? No! Every card returns its elixir cost the same way - just return the member variable. The behavior doesn't change across derived classes.

Rule: Only make functions virtual if different derived classes need different implementations. Simple getters usually don't need to be virtual.

Note: If you wanted derived classes to calculate cost differently (e.g., discounts), then make it virtual.

🔍 Analysis

Hint: Look at which destructors run. Both constructors run (Base and Derived), but do both destructors run?

Count the destructor messages in the output. How many do you see?

The Bug

Problem: Only the Base destructor runs! The Derived destructor never gets called.

Output analysis:

  • Both constructors run: "Base constructor" + "Derived constructor" (twice)
  • Only Base destructor runs: "Base destructor" (twice)
  • Missing: "Derived destructor" never appears!

Why This Happens

When you delete ptr1; where ptr1 is Base*, the compiler looks at the destructor. The Base destructor is NOT virtual, so static binding is used. Only Base::~Base() runs.

Result: derivedData never gets deleted - memory leak!

The Fix

Make the Base destructor virtual:

class Base {
    // ... members ...
public:
    virtual ~Base() {  // Add 'virtual' keyword!
        delete[] baseData;
        cout << "Base destructor" << endl;
    }
};

After fix: Both destructors run in correct order (Derived first, then Base).

The Rule

CRITICAL RULE: If a class has ANY virtual functions, make the destructor virtual too. Always. No exceptions.

Why: If you're using polymorphism (virtual functions), you're likely deleting through base pointers. Without a virtual destructor, derived destructors won't run - guaranteed memory leak.
