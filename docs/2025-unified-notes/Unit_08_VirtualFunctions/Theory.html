Welcome to Virtual Functions and Polymorphism

You've learned inheritance - creating classes based on other classes. Now we're going to unlock inheritance's real power: polymorphism. This is the ability to use a base class pointer or reference to call derived class functions.

Without virtual functions, inheritance is just code reuse. With virtual functions, you get true polymorphism: objects that behave according to their actual type, not the pointer type you're using to access them.

Prerequisites

Before starting this unit, you need to understand:

  • Inheritance (base classes and derived classes)
  • Access specifiers (public, protected, private)
  • Pointers and dynamic memory (new, delete)
  • Constructors and destructors in inheritance hierarchies
  • Function redefinition (overriding functions in derived classes)

If any of these concepts feel unclear, review Unit 7 (Inheritance) and Unit 1 (Pointers & Dynamic Memory) before continuing.

1. What is Polymorphism and Why Do We Need It?

The Real-World Problem

Suppose you're building a zoo management system. You have different animals: Dogs, Cats, Birds. Each animal makes a different sound, but you want to write one function that can make ANY animal speak without knowing which specific type it is.

You want to write code like this: 

void makeAnimalSpeak(Animal* a) {  // Works for ANY animal
    a->makeSound();  // Dog barks, Cat meows, Bird chirps
}

int main() {
    Animal* zoo[3];
    zoo[0] = new Dog();
    zoo[1] = new Cat();
    zoo[2] = new Bird();

    for (int i = 0; i < 3; i++) {
        makeAnimalSpeak(zoo[i]);  // Each makes its own sound
    }
}

This ability - one function working with many different types of objects, where each object behaves according to its actual type - is called polymorphism (Greek for "many forms").

Polymorphism means: You can use a base class pointer (like Animal*) to refer to different derived objects (Dog, Cat, Bird), and when you call a function, the correct version for that specific object runs automatically.

What Happens Without Virtual Functions

Let's see what happens if we try this WITHOUT using virtual functions. Here's our first attempt: 

class Animal {
public:
    void makeSound() {
        cout << "Some generic animal sound" << endl;
    }
};

class Dog : public Animal {
public:
    void makeSound() {  // We want this to override Animal's version
        cout << "Woof!" << endl;
    }
};

int main() {
    Dog myDog;
    Animal* ptr = &myDog;  // Base pointer pointing to a Dog object

    ptr->makeSound();  // What prints?
    return 0;
}
Unexpected Result: This prints "Some generic animal sound" - NOT "Woof!".

Why Does This Happen?

Let's break down what the compiler does, step by step:

  1. Line: Animal* ptr = &myDog;
    You create a pointer of type Animal*. It points to a Dog object, but the pointer's type is Animal*.
  2. Line: ptr->makeSound();
    The compiler looks at the pointer's type: "This is an Animal* pointer."
  3. The compiler says: "Ok, I'll call Animal::makeSound()."
    It decides this at compile time based only on the pointer type.
  4. The compiler never checks what the pointer actually points to at runtime. It doesn't care that there's a Dog object there.

This is called static binding (or early binding): The compiler decides which function to call based on the pointer's type at compile time, not based on the actual object at runtime. 

Without virtual:

Animal* ptr = &myDog;
         |
         | Compiler only looks at THIS (pointer type)
         v
    Animal*  --> calls Animal::makeSound()

    (Ignores what ptr actually points to)

The Solution: Virtual Functions

To make polymorphism work, we need to tell the compiler: "Don't decide at compile time. Wait until runtime, check what the pointer actually points to, and call the right function for that object."

We do this by adding the virtual keyword to the base class function: 

class Animal {
public:
    virtual void makeSound() {  // Added 'virtual' keyword
        cout << "Some generic animal sound" << endl;
    }
};

class Dog : public Animal {
public:
    void makeSound() {  // Automatically virtual (overrides base)
        cout << "Woof!" << endl;
    }
};

int main() {
    Dog myDog;
    Animal* ptr = &myDog;

    ptr->makeSound();  // Now prints "Woof!" ✓
    return 0;
}

Now here's what happens:

  1. Line: Animal* ptr = &myDog;
    Same as before - Animal* pointer to a Dog object.
  2. Line: ptr->makeSound();
    The compiler sees that makeSound() is virtual.
  3. The compiler says: "I won't decide now. I'll generate code that checks at runtime what ptr actually points to."
  4. At runtime, the program checks: "This pointer points to a Dog object."
  5. The program calls Dog::makeSound(). Output: "Woof!" ✓

This is called dynamic binding (or late binding): The decision about which function to call is made at runtime based on the object's actual type, not the pointer type. 

With virtual:

Animal* ptr = &myDog;
         |
         | At runtime, check what ptr points to
         v
    Dog object --> calls Dog::makeSound()

    (Uses actual object type, not pointer type)
Summary:
  • Polymorphism: One interface, many implementations. Use base pointers to work with different derived objects.
  • Without virtual: Compiler uses pointer type (static binding) - wrong function gets called.
  • With virtual: Program checks actual object type at runtime (dynamic binding) - correct function gets called.
Swift Note: The virtual keyword only needs to go in the base class declaration. Derived classes automatically inherit the "virtualness" (though you can write virtual there too for clarity). Once a function is virtual in the base class, it stays virtual in all derived classes forever.

2. Understanding the Virtual Keyword - What Does It Actually Mean?

Let's be very clear about what virtual actually does, because it's a simple concept that seems confusing at first.

What "Virtual" Means

The word virtual is a keyword you put in front of a function declaration in a class. Here's the syntax: 

class Animal {
public:
    virtual void makeSound() {  // The word 'virtual' goes here
        cout << "Generic sound" << endl;
    }
};

That's it. Just the word virtual before the return type.

What It Tells the Compiler

When you write virtual, you're giving the compiler a specific instruction:

"Don't decide which version of this function to call at compile time. Instead, wait until the program runs, check what type of object we actually have, and call the right version for that object."

Without virtual, the compiler decides at compile time based on the pointer type:
Animal* ptr → "Always call Animal::makeSound()"

With virtual, the decision happens at runtime based on the actual object:
Animal* ptr pointing to a Dog → "Check at runtime: it's a Dog, call Dog::makeSound()"

Where to Put Virtual

Rule 1: Put it in the base class

The virtual keyword goes in the base class function declaration. That's where you're saying "this function should use dynamic binding."

Rule 2: Derived classes inherit "virtualness"

Once a function is virtual in the base class, it's automatically virtual in all derived classes. You don't need to write virtual again (but you can if you want, for clarity).

class Animal {
public:
    virtual void makeSound() { /* ... */ }  // Virtual here
};

class Dog : public Animal {
public:
    void makeSound() { /* ... */ }  // Automatically virtual
    // (You could write 'virtual void makeSound()' but don't need to)
};

Virtual = "Check at Runtime"

Think of virtual as a switch that changes when the decision happens:

  • Without virtual: Compiler decides at compile time (static binding)
  • With virtual: Program decides at runtime (dynamic binding)
Simple Rule: If you want polymorphism (different derived classes behaving differently when called through base pointers), make the function virtual in the base class. That's all there is to it.
⚡ Swift Quiz
Quick Check: If a base class function is NOT virtual, which version gets called when using a base class pointer to a derived object?
Answer: The base class version gets called. Without virtual, the compiler uses static binding - it looks at the pointer type (Base*) and calls Base::function(), ignoring what the pointer actually points to. This is why virtual functions are needed for polymorphism.

3. Pure Virtual Functions - What Does "= 0" Mean?

Now that you understand virtual, let's look at a variation: pure virtual functions.

The Problem: No Default Makes Sense

Sometimes a base class function shouldn't have a default implementation. For example, what's the "default sound" for an Animal? There isn't one - only specific animals (Dog, Cat, Bird) have sounds. Writing a default implementation is pointless because it will never be used.

The Syntax: = 0

To say "this function has NO implementation in the base class," you add = 0 at the end: 

class Animal {
public:
    virtual void makeSound() = 0;  // Pure virtual function
    //                       ^^^^
    //                       This makes it "pure"
};

Let's break down what each part means:

  • virtual - "Use dynamic binding" (check type at runtime)
  • void makeSound() - The function signature
  • = 0 - "I'm NOT providing an implementation. Derived classes MUST provide one."

What = 0 Tells the Compiler

= 0 means: "This function has no body in this class. Any class that inherits from me MUST implement this function, or they'll be abstract too."

The = 0 is C++'s way of saying "no implementation here." It's called making the function pure virtual (as opposed to just virtual, which has an implementation).

Regular Virtual vs Pure Virtual

Here's the key difference: 

// Regular virtual - HAS implementation
class Animal {
public:
    virtual void makeSound() {
        cout << "Generic sound" << endl;  // Default implementation
    }
};

// Pure virtual - NO implementation
class Animal {
public:
    virtual void makeSound() = 0;  // No body, just = 0
};

Regular Virtual Function

Has a body: virtual void func() { /* code */ }

Meaning: "I have a default implementation, but derived classes can override it if they want."

Derived class requirement: Optional - can use base version or override

Pure Virtual Function

No body: virtual void func() = 0;

Meaning: "I have NO implementation. Derived classes MUST provide one."

Derived class requirement: Mandatory - must implement or stay abstract

Abstract Classes

A class with at least one pure virtual function is called an abstract class (or interface class). You cannot create objects of an abstract class: 

Animal a;  // ERROR: Cannot instantiate abstract class

Animal* ptr = new Dog();  // OK: Pointer to derived object

Abstract classes exist only to be inherited from. They define an interface that derived classes must implement.

Note: A derived class is still abstract if it doesn't implement all pure virtual functions from its base class. To become a concrete (instantiable) class, it must implement ALL pure virtual functions.

Syntax Summary

  • virtual void func(); - Regular virtual function (has default implementation)
  • virtual void func() = 0; - Pure virtual function (no default implementation)
⚡ Swift Quiz
Quick Check: What makes a class abstract, and what's the main restriction on abstract classes?
Answer: A class becomes abstract when it has at least one pure virtual function (declared with = 0). The main restriction is that you cannot instantiate (create objects of) an abstract class. You can only create pointers/references to abstract classes that point to derived, concrete objects.

3. Polymorphism with Base Class Pointers

Here's where virtual functions really shine. You can create an array of base class pointers, store different derived objects in them, and call the correct function for each object. 

int main() {
    Shape* shapes[3];

    shapes[0] = new Circle(5.0);
    shapes[1] = new Rectangle(4.0, 6.0);
    shapes[2] = new Circle(3.0);

    for (int i = 0; i < 3; i++) {
        shapes[i]->display();
        cout << "Area: " << shapes[i]->getArea() << endl;
    }

    // Clean up
    for (int i = 0; i < 3; i++) {
        delete shapes[i];
    }

    return 0;
}

Even though all elements are Shape* pointers, each one calls the correct derived class function. This is polymorphism in action.

How It Works: The vtable

When you declare a function virtual, the compiler creates a virtual table (vtable) for the class. This is a hidden array of function pointers. Each object has a hidden pointer (vptr) that points to its class's vtable. 

Object in memory:
+-------------------+
| vptr   -----------|----> [vtable for Circle]
| radius = 5.0      |      +------------------+
+-------------------+      | getArea ---------|-> Circle::getArea()
                           | display ---------|-> Circle::display()
                           +------------------+

When you call ptr->getArea(), the compiler generates code that:

  1. Follows the object's vptr to its vtable
  2. Looks up getArea() in the vtable
  3. Calls the function pointer found there

This happens at runtime, which is why it's called dynamic binding.

Swift Note: You don't need to understand vtables deeply, but knowing they exist helps explain why virtual functions have a small runtime cost (extra indirection) and memory cost (vptr in each object).
⚡ Swift Quiz
Quick Check: If you have Base* arr[10]; and store different derived objects in it, which function gets called when you do arr[i]->virtualFunc();?
Answer: The derived class's version gets called for each object. Even though all elements are Base* pointers, the virtual function mechanism looks at each object's actual type at runtime and calls the correct version. This is the whole point of polymorphism.

4. Polymorphism with References

Virtual functions work with references too, not just pointers: 

void makeHeroFight(Hero& h) {  // Reference parameter
    h.activateQuirk();  // Calls correct derived version
}

int main() {
    Deku myHero;
    makeHeroFight(myHero);  // Pass by reference
    return 0;
}

This is actually safer than pointers because references can't be NULL. When you pass a derived object by reference to a function that takes a base class reference, polymorphism still works.

Best Practice: Use references for function parameters when you want polymorphism but don't need NULL as a valid value. Use pointers when you need to store objects in arrays or need NULL as an option.

5. The Object Slicing Problem

Here's a common trap: What happens when you pass or assign a derived object by value to a base class variable? 

Deku myHero;
Hero h = myHero;  // Assignment by value

h.activateQuirk();  // What gets called?
Problem: This won't compile because Hero is abstract (has pure virtual functions). But even with a non-abstract base class, this causes object slicing.

When you assign a derived object to a base class variable by value, the derived parts get "sliced off". Only the base class parts are copied. Let's see this with a concrete example: 

class Vehicle {
public:
    int wheels;
    virtual void drive() {
        cout << "Driving a vehicle" << endl;
    }
};

class Car : public Vehicle {
public:
    bool hasRoof;
    void drive() {
        cout << "Driving a car" << endl;
    }
};

int main() {
    Car myCar;
    myCar.wheels = 4;
    myCar.hasRoof = true;

    Vehicle v = myCar;  // Object slicing!

    v.drive();  // Prints "Driving a vehicle" - NOT "Driving a car"
    // v.hasRoof doesn't exist - it was sliced off

    return 0;
}

The slicing happens because v is a Vehicle object, not a pointer or reference. It can only hold the Vehicle parts of myCar. The Car-specific data (hasRoof) and behavior (Car's drive()) are lost.

Swift Note: Polymorphism ONLY works with pointers and references, never with value copies. Always use Base* or Base& when you want polymorphic behavior.
⚡ Swift Quiz
Quick Check: Why doesn't polymorphism work with Base obj = derivedObject; (assignment by value)?
Answer: Object slicing occurs. When you assign a derived object to a base class variable by value, only the base class parts are copied. The derived class data and vtable pointer are lost. You end up with a pure base class object, not a derived object, so polymorphism can't work. Use pointers (Base*) or references (Base&) instead.

6. Virtual Destructors (CRITICAL!)

Here's one of the most important rules in C++: If a class has any virtual functions, its destructor should be virtual too.

Why? Consider this code: 

class Base {
public:
    ~Base() {  // NOT virtual!
        cout << "Base destructor" << endl;
    }
};

class Derived : public Base {
private:
    int* data;
public:
    Derived() {
        data = new int[100];
    }

    ~Derived() {
        delete[] data;
        cout << "Derived destructor" << endl;
    }
};

int main() {
    Base* ptr = new Derived();
    delete ptr;  // What destructor runs?

    return 0;
}
DANGER: Only the Base destructor runs! The Derived destructor never gets called, so data never gets deleted. Memory leak!

The Fix: Virtual Destructor

class Base {
public:
    virtual ~Base() {  // Now virtual!
        cout << "Base destructor" << endl;
    }
};

Now when you delete ptr;, the correct sequence happens:

  1. Derived destructor runs first (cleans up data)
  2. Base destructor runs second (automatic)
  3. No memory leak!
Important: Making the destructor virtual in the base class makes it virtual in all derived classes automatically. Always make your base class destructor virtual if the class has any other virtual functions.
⚡ Swift Quiz
Quick Check: What happens if you delete basePtr; where basePtr points to a derived object, but the base class destructor is NOT virtual?
Answer: Only the base class destructor runs. The derived class destructor never gets called, so any cleanup code in the derived destructor (like delete[] for dynamic memory) doesn't run. This causes memory leaks. Always make the base class destructor virtual when using inheritance with polymorphism.

7. When to Use Virtual Functions

Virtual functions aren't free - they have a small runtime and memory cost. Use them when you need them, but don't make every function virtual "just in case."

Use Virtual Functions When:

  • You want polymorphic behavior (calling derived functions through base pointers/references)
  • You're designing a base class that others will inherit from
  • You want to force derived classes to implement a function (use pure virtual)
  • You need an interface or abstract base class

Don't Use Virtual Functions When:

  • The function will never be overridden in derived classes
  • You're not using pointers or references to the base class
  • Performance is absolutely critical and the overhead matters
  • The class will never be used as a base class
Best Practice: If you're writing a base class that's meant to be inherited from, make the destructor virtual and make any functions that should have different behavior in derived classes virtual too.

Common Use Cases

1. Interface Classes (All Pure Virtual)

class Drawable {
public:
    virtual void draw() = 0;
    virtual ~Drawable() {}
};

2. Polymorphic Collections

Drawable* objects[100];
objects[0] = new Circle();
objects[1] = new Rectangle();
objects[2] = new Triangle();

for (int i = 0; i < 3; i++) {
    objects[i]->draw();  // Each draws itself correctly
}

3. Strategy Pattern

class SortStrategy {
public:
    virtual void sort(int* arr, int size) = 0;
    virtual ~SortStrategy() {}
};

class BubbleSort : public SortStrategy { /* ... */ };
class QuickSort : public SortStrategy { /* ... */ };

8. Common Mistakes with Virtual Functions

Mistake #1: Forgetting Virtual in Base Class

class Base {
public:
    void func() { }  // NOT virtual
};

class Derived : public Base {
public:
    void func() { }  // Won't be called polymorphically
};

// Problem:
Base* ptr = new Derived();
ptr->func();  // Calls Base::func, not Derived::func

Mistake #2: Forgetting Virtual Destructor

class Base {
public:
    ~Base() { }  // NOT virtual - memory leak risk!
};

Mistake #3: Using Value Instead of Pointer/Reference

void process(Base b) {  // Pass by value - slicing!
    b.virtualFunc();    // Won't call derived version
}

// Fix: Use reference or pointer
void process(Base& b) {  // Pass by reference
    b.virtualFunc();     // Now calls derived version
}

Mistake #4: Different Signatures

class Base {
public:
    virtual void func(int x);
};

class Derived : public Base {
public:
    void func(double x);  // Different parameter type!
    // This is NOT an override - it's a new function
};

For a derived function to override a base virtual function, the signature must match exactly (same parameters, same const-ness, same return type - with some exceptions for covariant returns).

9. Summary

Key Concepts:
  • Virtual functions enable polymorphism - calling derived functions through base pointers/references
  • Use virtual keyword in base class, derived classes inherit it automatically
  • Pure virtual functions (= 0) have no implementation, force derived classes to provide one
  • Abstract classes have at least one pure virtual function, cannot be instantiated
  • Polymorphism ONLY works with pointers and references, NOT value copies (object slicing)
  • ALWAYS make base class destructor virtual when using polymorphism
  • Virtual functions use vtables for dynamic binding (runtime overhead)
Swift Note: Quick Reference
  • Regular virtual: virtual void func();
  • Pure virtual: virtual void func() = 0;
  • Virtual destructor: virtual ~ClassName();
  • For polymorphism use: Base* ptr or Base& ref
  • Avoid: Base obj = derived; (causes slicing)
