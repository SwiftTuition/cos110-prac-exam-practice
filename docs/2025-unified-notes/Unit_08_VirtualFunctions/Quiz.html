Section 1: Multiple Choice Questions

Question 1

Virtual Function Keyword

What does the virtual keyword tell the compiler?

  1. This function must be defined in derived classes
  2. Use dynamic binding - decide which function to call at runtime
  3. This function cannot be redefined in derived classes
  4. This function is private and cannot be inherited

Answer: B - Use dynamic binding - decide which function to call at runtime

Why B is correct:

The virtual keyword enables dynamic (late) binding. When you call a virtual function through a base class pointer or reference, the decision of which version to call is made at runtime based on the actual object type, not the pointer type.

Why other options are wrong:

  • A: Incorrect - Regular virtual functions don't have to be redefined. Only PURE virtual functions (= 0) must be implemented in derived classes.
  • C: Incorrect - Virtual functions can and often are redefined in derived classes. That's the whole point!
  • D: Incorrect - virtual has nothing to do with access specifiers. Virtual functions are typically public.
Question 2

Pure Virtual Function Syntax

What does = 0 mean in a virtual function declaration?

  1. The function returns 0
  2. The function has no implementation - derived classes must provide one
  3. The function should be called zero times
  4. The function is private

Answer: B - The function has no implementation - derived classes must provide one

Why B is correct:

The = 0 syntax creates a pure virtual function. It means "I'm not providing an implementation in this base class. Every derived class MUST provide its own implementation." This makes the class abstract - you cannot create objects of it.

Why other options are wrong:

  • A: Incorrect - = 0 has nothing to do with return values. It's about implementation.
  • C: Incorrect - The function should actually be called normally through polymorphism. = 0 doesn't restrict how often it's called.
  • D: Incorrect - Pure virtual functions are typically public, not private.
Question 3

Abstract Classes

When is a class considered abstract?

  1. When it has at least one private member
  2. When it has at least one pure virtual function
  3. When it has a virtual destructor
  4. When it uses protected inheritance

Answer: B - When it has at least one pure virtual function

Why B is correct:

A class is abstract if it has at least one pure virtual function (= 0). You cannot create objects of an abstract class. The purpose is to create interfaces and force derived classes to implement specific behaviors.

Why other options are wrong:

  • A: Incorrect - Private members don't make a class abstract. Almost every class has private members!
  • C: Incorrect - Virtual destructors are important for polymorphism but don't make a class abstract.
  • D: Incorrect - Protected inheritance is rare and doesn't relate to abstract classes.
Question 4

Static vs Dynamic Binding

Without the virtual keyword, which binding is used?

  1. Dynamic binding (runtime decision)
  2. Static binding (compile-time decision)
  3. Late binding
  4. No binding occurs

Answer: B - Static binding (compile-time decision)

Why B is correct:

Without virtual, C++ uses static (early) binding. The compiler decides which function to call based on the POINTER TYPE at compile time. If you have Animal* ptr = new Dog();, calling ptr->speak() calls Animal's version, NOT Dog's version (unless speak is virtual).

Why other options are wrong:

  • A: Incorrect - Dynamic binding only happens with virtual functions.
  • C: Incorrect - Late binding is another name for dynamic binding, which requires virtual.
  • D: Incorrect - Binding always occurs. The question is WHEN it happens (compile-time or runtime).
Question 5

Virtual Destructors

Why should base class destructors be virtual when using polymorphism?

  1. To make the class abstract
  2. To ensure derived class destructors are called when deleting through base pointers
  3. To improve performance
  4. Virtual destructors are never needed

Answer: B - To ensure derived class destructors are called when deleting through base pointers

Why B is correct:

If you have Animal* ptr = new Dog(); and later delete ptr;, without a virtual destructor, only Animal's destructor runs! Dog's destructor never runs, causing memory leaks if Dog allocated resources. Making the destructor virtual ensures BOTH destructors run (Dog's then Animal's).

Why other options are wrong:

  • A: Incorrect - Destructors with = 0 can make classes abstract, but that's not the main reason for virtual destructors.
  • C: Incorrect - Virtual functions have a tiny performance overhead (vtable lookup). They're for correctness, not performance.
  • D: Incorrect - This is dangerous advice! Always use virtual destructors in polymorphic base classes.
Question 6

Object Slicing

What is object slicing?

  1. Deleting part of an object's memory
  2. When derived class parts are lost during assignment to base class by value
  3. Dividing an object into multiple pieces
  4. A memory optimization technique

Answer: B - When derived class parts are lost during assignment to base class by value

Why B is correct:

If you do Animal a = dog; (where dog is a Dog object), the Dog-specific data is "sliced off." Only the Animal part is copied to a. This is why polymorphism requires pointers or references - they don't slice.

Example:

Dog d;
Animal a = d;  // SLICING! Dog parts lost
a.speak();     // Calls Animal::speak(), not Dog::speak()

Animal* ptr = &d;  // NO slicing - pointer!
ptr->speak();      // Calls Dog::speak() if virtual

Why other options are wrong:

  • A: Incorrect - It's about copying, not deleting memory.
  • C: Incorrect - Not about physically dividing objects.
  • D: Incorrect - It's a problem to avoid, not an optimization!
Question 7

Polymorphism Requirements

What is required for polymorphism to work in C++?

  1. Virtual functions and base class objects
  2. Virtual functions and base class pointers/references
  3. Pure virtual functions only
  4. Multiple inheritance

Answer: B - Virtual functions and base class pointers/references

Why B is correct:

Polymorphism needs TWO things:

  1. Virtual functions - enables dynamic binding
  2. Base class pointers/references - allows pointing to derived objects without slicing

Example:

Animal* ptr = new Dog();  // Pointer to derived object
ptr->speak();             // Calls Dog::speak() if virtual

Why other options are wrong:

  • A: Incorrect - Base class objects cause slicing. You need pointers/references.
  • C: Incorrect - Regular virtual functions work for polymorphism. Pure virtual isn't required (though common in interfaces).
  • D: Incorrect - Single inheritance is sufficient for polymorphism.
Question 8

Virtual Table (vtable)

What is a vtable?

  1. A table storing all class member variables
  2. A hidden table of function pointers for virtual functions
  3. A table of all objects created
  4. A debugging feature

Answer: B - A hidden table of function pointers for virtual functions

Why B is correct:

Every class with virtual functions has a vtable (virtual table) - a hidden array of function pointers. Each object has a hidden pointer (vptr) to its class's vtable. When you call a virtual function, the program looks up the correct function in the vtable at runtime.

How it works:

  1. Create Dog object → vptr points to Dog's vtable
  2. Call ptr->speak() → Follow vptr to vtable
  3. Look up speak in vtable → Get Dog::speak address
  4. Call Dog::speak()

Why other options are wrong:

  • A: Incorrect - vtables store function pointers, not data members.
  • C: Incorrect - vtables are per-class, not per-object.
  • D: Incorrect - vtables are how C++ implements polymorphism, not a debugging tool.
Question 9

Can You Instantiate Abstract Classes?

Can you create an object of an abstract class?

  1. Yes, always
  2. No, never
  3. Only if you provide implementations for pure virtual functions
  4. Only with dynamic memory allocation

Answer: B - No, never

Why B is correct:

You CANNOT instantiate an abstract class. The compiler prevents it. Abstract classes exist to define interfaces and common behavior. You can only create objects of CONCRETE (non-abstract) derived classes that implement all pure virtual functions.

Example:

class Animal {  // Abstract
public:
    virtual void speak() = 0;  // Pure virtual
};

class Dog : public Animal {
public:
    void speak() { cout << "Woof"; }  // Implementation
};

int main() {
    Animal a;    // ERROR! Cannot instantiate abstract class
    Dog d;       // OK! Dog is concrete
    Animal* ptr = new Dog();  // OK! Pointer to derived object
}

Why other options are wrong:

  • A: Incorrect - You can never create abstract class objects.
  • C: Incorrect - If you provide implementations, it's no longer abstract! But you still can't instantiate the base class; you instantiate the derived class.
  • D: Incorrect - Allocation method doesn't matter. Abstract is abstract.
Question 10

Overriding vs Overloading

What's the difference between overriding and overloading virtual functions?

  1. Overriding is same signature in derived class; overloading is different signatures
  2. They are the same thing
  3. Overriding is for constructors; overloading is for other functions
  4. Overloading requires virtual keyword; overriding doesn't

Answer: A - Overriding is same signature in derived class; overloading is different signatures

Why A is correct:

Overriding: Derived class provides a new implementation for a virtual function with the SAME signature as the base class. This enables polymorphism.

Overloading: Multiple functions with the same name but DIFFERENT signatures (parameters). Not specific to inheritance.

Example:

class Base {
public:
    virtual void show() { }       // Virtual function
    void print(int x) { }         // Overloaded
    void print(string s) { }      // Overloaded
};

class Derived : public Base {
public:
    void show() { }               // OVERRIDE (same signature)
    void show(int x) { }          // OVERLOAD (different signature)
};

Why other options are wrong:

  • B: Incorrect - They're different concepts with different purposes.
  • C: Incorrect - Both apply to regular functions, not just constructors.
  • D: Incorrect - Overriding requires virtual in the base class.
Question 11

Default Arguments and Virtual Functions

Can virtual functions have default arguments?

  1. No, virtual functions cannot have default arguments
  2. Yes, but the defaults are determined by the pointer type (static binding)
  3. Yes, and they use dynamic binding like the function call
  4. Only pure virtual functions can have default arguments

Answer: B - Yes, but the defaults are determined by the pointer type (static binding)

Why B is correct:

This is a tricky gotcha! While the FUNCTION CALL uses dynamic binding (runtime decision), the DEFAULT ARGUMENTS use static binding (compile-time decision based on pointer type). This is why it's dangerous to override default arguments - you get confusing behavior.

Example:

class Base {
public:
    virtual void print(int x = 5) {
        cout << "Base: " << x;
    }
};

class Derived : public Base {
public:
    void print(int x = 10) {
        cout << "Derived: " << x;
    }
};

Base* ptr = new Derived();
ptr->print();  // Prints: "Derived: 5" (Derived function, Base default!)

Why other options are wrong:

  • A: Incorrect - They can have defaults, but it's risky.
  • C: Incorrect - Only the function uses dynamic binding, not the defaults.
  • D: Incorrect - Regular virtual functions can also have defaults.
Question 12

Multiple Inheritance and Virtual Functions

Can a class inherit from multiple base classes that both have virtual functions?

  1. No, this causes a compilation error
  2. Yes, but you can only override one of them
  3. Yes, and you must override all pure virtual functions from all base classes
  4. Virtual functions are disabled in multiple inheritance

Answer: C - Yes, and you must override all pure virtual functions from all base classes

Why C is correct:

Multiple inheritance is allowed in C++ (though often avoided due to complexity). If multiple base classes have pure virtual functions, the derived class must implement ALL of them to be concrete. Otherwise, it remains abstract.

Example:

class Printable {
public:
    virtual void print() = 0;
};

class Saveable {
public:
    virtual void save() = 0;
};

class Document : public Printable, public Saveable {
public:
    void print() { }  // Must implement
    void save() { }   // Must implement
};

Why other options are wrong:

  • A: Incorrect - Multiple inheritance is legal (though complex).
  • B: Incorrect - You must override all pure virtuals from all bases to be concrete.
  • D: Incorrect - Virtual functions work normally in multiple inheritance.

Section 2: Code Tracing Questions

Question 13

Basic Virtual Function Call

What is the output of this code?

class Animal {
public:
    virtual void speak() { cout << "Animal"; }
};

class Dog : public Animal {
public:
    void speak() { cout << "Dog"; }
};

int main() {
    Animal* ptr = new Dog();
    ptr->speak();
    delete ptr;
    return 0;
}

Output:

Dog

Explanation:

  1. Animal* ptr = new Dog(); - Create Dog object, store address in Animal pointer
  2. ptr->speak(); - speak() is virtual, so use dynamic binding
  3. Runtime: Check actual object type (Dog), call Dog::speak()
  4. Output: "Dog"

Key Concept: Virtual functions use the actual object type (Dog), not the pointer type (Animal*).

Output:

Explanation:

  1. Animal* ptr = new Dog(); - Still creates Dog object
  2. ptr->speak(); - speak() is NOT virtual, so use static binding
  3. Compile-time: Check pointer type (Animal*), call Animal::speak()
  4. Output: "Animal"

Key Concept: Without virtual, the pointer type determines which function is called (static binding), even though the actual object is a Dog.

Question 15

Pure Virtual Function

Will this code compile? If not, why?

class Shape {
public:
    virtual void draw() = 0;
};

int main() {
    Shape s;
    return 0;
}

Answer: No, compilation error

Error Message:

error: cannot declare variable 's' to be of abstract type 'Shape'

Explanation:

Shape has a pure virtual function (draw() = 0), making it abstract. You CANNOT create objects of abstract classes. You can only create pointers/references to abstract classes that point to concrete derived objects.

Fix:

class Circle : public Shape {
public:
    void draw() { cout << "Drawing circle"; }
};

int main() {
    Circle c;            // OK! Circle is concrete
    Shape* ptr = &c;     // OK! Pointer to derived object
    ptr->draw();         // Calls Circle::draw()
}
Question 16

Object Slicing Demo

What is the output?

class Animal {
public:
    virtual void speak() { cout << "Animal"; }
};

class Dog : public Animal {
public:
    void speak() { cout << "Dog"; }
};

int main() {
    Dog d;
    Animal a = d;  // Assignment by value!
    a.speak();
    return 0;
}

Output:

Animal

Explanation:

  1. Dog d; - Create Dog object
  2. Animal a = d; - OBJECT SLICING! Copy only Animal part to a
  3. a is a true Animal object, not a Dog
  4. a.speak(); - Calls Animal::speak() because a IS an Animal

Key Concept: Assignment by value causes slicing. Even though speak() is virtual, a is genuinely an Animal object (not a Dog), so Animal::speak() is called. Use pointers/references to avoid slicing!

Correct approach:

Dog d;
Animal* ptr = &d;  // No slicing!
ptr->speak();      // Outputs: "Dog"
Question 17

Virtual Destructor Trace

What is the output?

class Base {
public:
    virtual ~Base() { cout << "~Base"; }
};

class Derived : public Base {
public:
    ~Derived() { cout << "~Derived"; }
};

int main() {
    Base* ptr = new Derived();
    delete ptr;
    return 0;
}

Output:

~Derived~Base

Line-by-Line Trace:

  1. Base* ptr = new Derived(); - Create Derived object
  2. delete ptr; - Destructor is virtual, so use dynamic binding
  3. Runtime: Check actual object type (Derived)
  4. Derived destructor runs first: Prints "~Derived"
  5. Base destructor runs automatically: Prints "~Base"
  6. Result: "~Derived~Base"

Key Concept: Virtual destructors ensure both derived and base destructors run, preventing memory leaks. Always make base class destructors virtual when using polymorphism!

Question 18

Non-Virtual Destructor Problem

What is the output if destructor is NOT virtual?

class Base {
public:
    ~Base() { cout << "~Base"; }  // NOT virtual!
};

class Derived : public Base {
public:
    ~Derived() { cout << "~Derived"; }
};

int main() {
    Base* ptr = new Derived();
    delete ptr;
    return 0;
}

Output:

~Base

Problem:

Only Base's destructor runs! Derived's destructor is NEVER called. This is a memory leak if Derived allocated resources.

Explanation:

  1. Destructor is NOT virtual → static binding
  2. Compiler checks pointer type (Base*) at compile time
  3. Calls Base::~Base() only
  4. Derived::~Derived() never runs → memory leak!

Example of the leak:

class Derived : public Base {
    int* data;
public:
    Derived() { data = new int[100]; }
    ~Derived() {
        delete[] data;  // NEVER CALLED! Memory leak!
        cout << "~Derived";
    }
};

Solution: Always make destructors virtual in polymorphic base classes!

Question 19

Multiple Polymorphic Calls

What is the output?

class Animal {
public:
    virtual void speak() { cout << "A"; }
};

class Dog : public Animal {
public:
    void speak() { cout << "D"; }
};

class Cat : public Animal {
public:
    void speak() { cout << "C"; }
};

int main() {
    Animal* arr[3];
    arr[0] = new Dog();
    arr[1] = new Cat();
    arr[2] = new Dog();

    for (int i = 0; i < 3; i++) {
        arr[i]->speak();
    }

}

Output:

DCD

Line-by-Line Trace:

  1. arr[0] = new Dog(); - arr[0] points to Dog
  2. arr[1] = new Cat(); - arr[1] points to Cat
  3. arr[2] = new Dog(); - arr[2] points to Dog
  4. Loop iteration 0: arr[0]->speak() → Dog::speak() → "D"
  5. Loop iteration 1: arr[1]->speak() → Cat::speak() → "C"
  6. Loop iteration 2: arr[2]->speak() → Dog::speak() → "D"
  7. Result: "DCD"

Key Concept: Arrays of base class pointers are powerful! Each pointer knows its actual object type at runtime and calls the correct function. This is polymorphism in action.

Question 21

Find the Bug 1

What's wrong with this code?

class Shape {
public:
    virtual void draw() = 0;
};

class Circle : public Shape {
public:
    void draw() { cout << "Circle"; }
};

class Square : public Shape {

    Square s;

}

Bug: Square doesn't implement pure virtual function

Problem:

Square inherits from Shape, which has a pure virtual function draw(). Since Square doesn't implement draw(), Square is ALSO abstract! You cannot create objects of abstract classes.

Compiler Error:

error: cannot declare variable 's' to be of abstract type 'Square'

Fix:

class Square : public Shape {
public:
    void draw() { cout << "Square"; }  // Implement draw()
};

Key Lesson: When inheriting from an abstract class, you MUST implement all pure virtual functions to make your derived class concrete (instantiable).

Question 22

Find the Bug 2

What's the memory problem here?

class Base {
public:
    ~Base() { cout << "~Base"; }  // NOT virtual!
};

class Derived : public Base {
    int* data;
public:
    Derived() {
        data = new int[1000];
    }

    ~Derived() {
        delete[] data;
        cout << "~Derived";
    }
};

int main() {
    Base* ptr = new Derived();
    delete ptr;  // Memory leak!
    return 0;
}

Bug: Non-virtual destructor causes memory leak

Problem:

When delete ptr; runs, only Base's destructor is called (static binding). Derived's destructor NEVER runs, so delete[] data; never executes. The 1000-integer array is leaked!

Output:

~Base

(Notice "~Derived" never prints!)

Fix: Make destructor virtual

class Base {
public:
    virtual ~Base() { cout << "~Base"; }  // Add virtual!
};

Now the output is:

~Derived~Base

Both destructors run, and memory is properly freed.

Rule: Always make base class destructors virtual when using polymorphism!

Question 23

Find the Bug 3

Why doesn't polymorphism work here?

class Animal {
public:
    virtual void speak() { cout << "Animal"; }
};

class Dog : public Animal {
public:
    void speak(int times) {  // Different signature!
        for (int i = 0; i < times; i++)
            cout << "Woof ";
    }
};

int main() {
    Animal* ptr = new Dog();
    ptr->speak();
    return 0;
}

Output:

Animal

Bug: Signature mismatch prevents overriding

Problem:

Dog::speak(int) has a DIFFERENT signature than Animal::speak(). This is NOT overriding - it's overloading! Since Dog doesn't override the no-parameter version, Animal::speak() is called.

What happened:

  • Animal has: virtual void speak()
  • Dog adds: void speak(int times) - different signature!
  • Dog doesn't override Animal::speak(), so it inherits the base version
  • ptr->speak(); calls Animal::speak()

Fix: Match the signature

class Dog : public Animal {
public:
    void speak() { cout << "Woof"; }  // Same signature - now it overrides!
};

Key Lesson: For overriding, signatures must match EXACTLY (name, parameters, const-ness).

Question 25

Find the Bug 5

Why does this exhibit unexpected behavior?

class Base {
public:
    virtual void print(int x = 10) {
        cout << "Base: " << x << endl;
    }
};

class Derived : public Base {
public:
    void print(int x = 20) {  // Different default!
        cout << "Derived: " << x << endl;
    }
};

int main() {
    Base* ptr = new Derived();
    ptr->print();  // What gets printed?
    return 0;
}

Output:

Derived: 10

Bug: Confusing mix of dynamic function call and static default argument

What happened:

  1. ptr->print(); - No argument provided, use default
  2. Default argument (10): Determined by pointer type (Base*) at compile time - STATIC BINDING
  3. Function call: Determined by object type (Derived) at runtime - DYNAMIC BINDING
  4. Result: Call Derived::print(10) - Derived function with Base's default!

Why this is confusing:

You get a weird mix: Derived's implementation with Base's default value. This violates the principle of least surprise.

Fix: Don't change default arguments in overrides

class Derived : public Base {
public:
    void print(int x = 10) {  // Same default as Base
        cout << "Derived: " << x << endl;
    }
};

Better Fix: Avoid defaults in virtual functions entirely

class Base {
public:
    virtual void print(int x) {  // No default
        cout << "Base: " << x << endl;
    }
};

// Caller must provide: ptr->print(10);

Key Lesson: Default arguments use static binding. Avoid changing them (or using them at all) in virtual function hierarchies.

Section 4: True/False

Question 26

True or False: Virtual Function Performance

Statement: Virtual functions have a small performance overhead compared to non-virtual functions due to vtable lookup.

True or False? Justify your answer.

Answer: TRUE

Justification:

Virtual functions do have a small overhead:

  • Space: Each object with virtual functions has a hidden vptr (pointer to vtable) - typically 8 bytes on 64-bit systems
  • Time: Each virtual function call requires a vtable lookup: follow vptr → index into vtable → get function address → call function

However:

  • The overhead is TINY in modern CPUs (nanoseconds per call)
  • It's almost never a performance bottleneck
  • The flexibility of polymorphism is worth it
  • Only use non-virtual when you've profiled and proven it's necessary

Conclusion: Yes, there's overhead, but it's negligible. Use virtual functions where they make sense architecturally.

Question 27

True or False: Virtual Propagation

Statement: Once a function is declared virtual in a base class, it remains virtual in all derived classes even if you don't use the virtual keyword again.

True or False? Justify your answer.

Answer: TRUE

Justification:

Once virtual, always virtual! If a base class declares a function as virtual, all overrides in derived classes are automatically virtual, even if you don't write the virtual keyword.

Example:

class Base {
public:
    virtual void foo() { }  // Virtual
};

class Derived : public Base {
public:
    void foo() { }  // Still virtual (even without keyword)!
};

class MoreDerived : public Derived {
public:
    void foo() { }  // Still virtual!
};

Best Practice:

Even though it's automatic, it's good style to include virtual in derived classes too for clarity. C++11 added the override keyword which is even better:

class Derived : public Base {
public:
    void foo() override { }  // C++11: explicitly marks override
};

Conclusion: Virtual is "sticky" - it propagates down the inheritance hierarchy automatically.

Question 28

True or False: Abstract Class Pointers

Statement: You can have a pointer to an abstract class, but you cannot have an object of an abstract class.

True or False? Justify your answer.

Answer: TRUE

Justification:

This is absolutely true and is fundamental to how abstract classes work:

You CANNOT create objects:

class Shape {
public:
    virtual void draw() = 0;  // Pure virtual - abstract class
};

Shape s;  // ERROR! Cannot instantiate abstract class

You CAN create pointers/references:

class Circle : public Shape {
public:
    void draw() { cout << "Circle"; }
};

Shape* ptr = new Circle();  // OK! Pointer to abstract type
Shape& ref = circle;        // OK! Reference to abstract type
ptr->draw();                // Calls Circle::draw() via polymorphism

Why this makes sense:

Abstract classes define interfaces. You can't have "just an interface" as a real object, but you can have pointers/references that use the interface to interact with concrete implementations. This is the foundation of polymorphism.

Question 29

Implementation: Abstract Shape Hierarchy

Task: Implement a shape hierarchy with polymorphism.

Create the following:

Shape (abstract base class):

  • Pure virtual function: void display() const
  • Virtual destructor

Rectangle (derived from Shape):

  • Constructor: Rectangle(double w, double h)

  • Implement: display() prints "Rectangle: W x H, Area = A"

Circle (derived from Shape):

  • Private member: radius
  • Constructor: Circle(double r)
  • Implement: getArea() returns π × r² (use 3.14159)
  • Implement: display() prints "Circle: Radius = R, Area = A"

Complete Implementation:

#include <iostream>
using namespace std;

// Abstract base class
class Shape {
public:
    virtual double getArea() const = 0;
    virtual void display() const = 0;
    virtual ~Shape() { }  // Virtual destructor
};

class Rectangle : public Shape {
private:
    double width;
    double height;

public:
    Rectangle(double w, double h) : width(w), height(h) { }

    double getArea() const {
        return width * height;
    }

    void display() const {
        cout << "Rectangle: " << width << " x " << height;
        cout << ", Area = " << getArea() << endl;
    }
};

class Circle : public Shape {
private:
    double radius;

public:
    Circle(double r) : radius(r) { }

    double getArea() const {
        return 3.14159 * radius * radius;
    }

    void display() const {
        cout << "Circle: Radius = " << radius;
        cout << ", Area = " << getArea() << endl;
    }
};

int main() {
    Shape* shapes[2];
    shapes[0] = new Rectangle(5, 3);
    shapes[1] = new Circle(4);

    for (int i = 0; i < 2; i++) {
        shapes[i]->display();
    }

    // Clean up
    for (int i = 0; i < 2; i++) {
        delete shapes[i];
    }

    return 0;
}

Expected Output:

Rectangle: 5 x 3, Area = 15
Circle: Radius = 4, Area = 50.2654

Key Points:

  • Shape cannot be instantiated (abstract)
  • Both derived classes implement all pure virtual functions
  • Polymorphism: shapes[i]->display() calls correct version
  • Virtual destructor ensures proper cleanup when deleting
  • Array of base class pointers enables treating different shapes uniformly
Question 30

Implementation: Vehicle Hierarchy with Virtual Destructor

Task: Demonstrate the importance of virtual destructors.

Create the following:

Vehicle (base class):

  • Virtual destructor that prints "~Vehicle"
  • Virtual function: void start() prints "Vehicle starting"

Car (derived from Vehicle):

  • Private member: int* engineData
  • Constructor: Allocates new int[100], prints "Car constructed"
  • Destructor: Deletes engineData, prints "~Car"
  • Override start(): prints "Car engine starting"

Test in main():

  • Create: Vehicle* v = new Car();
  • Call: v->start();
  • Delete: delete v;
  • Observe destructor output

Complete Implementation:

#include <iostream>
using namespace std;

class Vehicle {
public:
    virtual void start() {
        cout << "Vehicle starting" << endl;
    }

    virtual ~Vehicle() {
        cout << "~Vehicle" << endl;
    }
};

class Car : public Vehicle {
private:
    int* engineData;

public:
    Car() {
        engineData = new int[100];
        cout << "Car constructed" << endl;
    }

    void start() {
        cout << "Car engine starting" << endl;
    }

    ~Car() {
        delete[] engineData;
        cout << "~Car" << endl;
    }
};

int main() {
    cout << "Creating Car via Vehicle pointer:" << endl;
    Vehicle* v = new Car();

    cout << "\nCalling start():" << endl;
    v->start();

    cout << "\nDeleting via Vehicle pointer:" << endl;
    delete v;

    return 0;
}

Expected Output:

Creating Car via Vehicle pointer:
Car constructed

Calling start():
Car engine starting

Deleting via Vehicle pointer:
~Car
~Vehicle

Key Points:

  • Virtual destructor ensures Car's destructor runs first
  • If destructor wasn't virtual, ~Car would never run → memory leak!
  • Virtual start() enables polymorphic call
  • Notice destructor order: derived (~Car) then base (~Vehicle)

What if destructor wasn't virtual?

Change Vehicle destructor to: ~Vehicle() { } (remove virtual)

Output would be:

Creating Car via Vehicle pointer:
Car constructed

Calling start():
Car engine starting

Deleting via Vehicle pointer:
~Vehicle

Notice: ~Car never runs! The 100-integer array leaks!

Golden Rule: Always make destructors virtual in polymorphic base classes!
