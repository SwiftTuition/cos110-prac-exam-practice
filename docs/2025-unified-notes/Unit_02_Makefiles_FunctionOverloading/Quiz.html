Question 1
Makefile Syntax

True or False: In a makefile, commands MUST be indented with a TAB character, not spaces.

Justify your answer.

Answer: True

Justification:

Make requires commands to be indented with a TAB character (ASCII 9). If you use spaces instead, you'll get an error like "missing separator" or "*** missing separator. Stop."

Why this rule exists:

The make utility was designed in the 1970s to distinguish between dependency lines and command lines using tabs. This was a simple parsing strategy that stuck around for backward compatibility.

Common mistake: Many modern text editors convert tabs to spaces automatically. You must configure your editor to insert actual TAB characters when editing makefiles.

Question 2
Makefile Structure

What are the three components of a makefile rule?

Answer:

The three components of a makefile rule are:

  1. Target: The file you want to create (e.g., main.o or executable)
  2. Dependencies: The files that the target depends on (e.g., source files and headers)
  3. Command: The shell command to create the target (e.g., g++ -c main.cpp)

Format:

target: dependencies
	command

Example:

main.o: main.cpp Student.h
	g++ -c -std=c++98 main.cpp

This rule says: "To create main.o, which depends on main.cpp and Student.h, run the command g++ -c -std=c++98 main.cpp."

Question 3
Dependencies

Consider the following files:

  • main.cpp includes Student.h
  • Student.cpp includes Student.h
  • Student.h includes <iostream>

Which of the following makefile rules is correct for compiling main.cpp?

  1. main.o: main.cpp
  2. main.o: main.cpp Student.h
  3. main.o: main.cpp Student.h iostream
  4. main.o: main.cpp Student.cpp

Answer: B - main.o: main.cpp Student.h

Why B is correct:

When compiling main.cpp to create main.o, the dependencies should include:

  • The source file itself (main.cpp)
  • All project headers that the source file includes, directly or indirectly (Student.h)

If Student.h changes (e.g., you add a new method), main.cpp needs to be recompiled to see those changes.

Why other options are wrong:

  • A: Missing Student.h dependency. If Student.h changes, make won't know to recompile main.cpp.
  • C: System headers like <iostream> are not listed as dependencies because they don't change. Only list headers you wrote.
  • D: Student.cpp is not a dependency for main.o. Object files only depend on their own source file and the headers they include, not other source files.
Question 4
Code Tracing

Given this makefile:

ofiles = main.o Grade.o
gpp_o = g++ -c -std=c++98

gradeTracker: $(ofiles)
	g++ -std=c++98 $(ofiles) -o gradeTracker

main.o: main.cpp Grade.h
	$(gpp_o) main.cpp

Grade.o: Grade.cpp Grade.h
	$(gpp_o) Grade.cpp

What happens when you type make and all files are up to date?

Answer: Make outputs "make: 'gradeTracker' is up to date." and does nothing.

Explanation:

When you run make without arguments, it builds the first target in the file (gradeTracker).

Make's decision process:

  1. Check if gradeTracker exists
  2. Check if any dependency (main.o or Grade.o) is newer than gradeTracker
  3. If main.o or Grade.o don't exist or are out of date, recursively check their dependencies
  4. If everything exists and no source files have changed since the last build, do nothing

This is the key benefit of makefiles: They only recompile what changed, saving time on large projects. If you modify Grade.cpp, only Grade.cpp is recompiled and the executable is relinked. main.cpp is not recompiled.

Question 5
Variables

What is the purpose of using variables in makefiles (e.g., ofiles = main.o Student.o)?

Answer:

Variables in makefiles serve several purposes:

  1. Avoid repetition: Instead of typing main.o Student.o Grade.o multiple times, you type it once and use $(ofiles) everywhere else.
  2. Easier maintenance: If you add a new file to your project, you only need to update the variable definition, not every place the list appears.
  3. Consistency: Ensures you use the same compiler flags everywhere by storing them in a variable like gpp_o = g++ -c -std=c++98.
  4. Readability: Makes the makefile easier to read and understand.

Example:

ofiles = main.o Student.o Grade.o Course.o

main: $(ofiles)
	g++ $(ofiles) -o main

Without variables, you'd have to type the full list in multiple places, and adding Teacher.o would require changing every occurrence.

Question 6
Find the Bug

The following makefile has a bug. Identify and explain the problem:

ofiles = main.o Student.o
gpp_o = g++ -c -std=c++98

main: $(ofiles)
	g++ -std=c++98 $(ofiles) -o main

main.o: main.cpp Student.h
	$(gpp_o) main.cpp

Student.o: Student.cpp Student.h
	$(gpp_o) Student.cpp

clean:
	rm -f *.o main

You added a new file Grade.cpp and Grade.h, created a rule to compile it, but when you run make, you get "undefined reference" errors during linking.

Bug Location: Line 1 - ofiles variable

What's Wrong: You forgot to add Grade.o to the ofiles variable.

Why It's Wrong:

Even though you created a rule to compile Grade.cpp:

Grade.o: Grade.cpp Grade.h
	$(gpp_o) Grade.cpp

The linker never receives Grade.o because it's not in the dependency list for main. When make runs g++ -std=c++98 $(ofiles) -o main, it expands to g++ -std=c++98 main.o Student.o -o main, missing Grade.o.

How to Fix:

ofiles = main.o Student.o Grade.o

Why the Fix Works: Now when make links the executable, it includes Grade.o: g++ -std=c++98 main.o Student.o Grade.o -o main, resolving all references to functions defined in Grade.cpp.

Question 7
Compilation Flags

What is the difference between these two g++ commands?

  1. g++ -c -std=c++98 main.cpp
  2. g++ -std=c++98 main.cpp -o main

Answer:

Command A: g++ -c -std=c++98 main.cpp

  • Purpose: Compile only (don't link)
  • Output: Creates main.o (object file)
  • The -c flag: Tells g++ to stop after compilation, before linking
  • When to use: When compiling individual source files in a multi-file project

Command B: g++ -std=c++98 main.cpp -o main

  • Purpose: Compile and link in one step
  • Output: Creates main (executable)
  • No -c flag: g++ compiles and then links automatically
  • When to use: When compiling a single-file program, or as the final linking step

In a makefile context:

Use command A (with -c) to create object files from individual source files. Use command B (without -c) to link all object files into the final executable:

main.o: main.cpp
	g++ -c -std=c++98 main.cpp    # Compile only

main: main.o Student.o
	g++ -std=c++98 main.o Student.o -o main    # Link
Question 8
Makefile Targets

True or False: The target clean in a makefile must have dependencies.

Answer: False

Explanation:

The clean target typically has no dependencies because it performs a manual cleanup action rather than building a file.

Example:

clean:
	rm -f *.o main

How it works:

  • When you run make clean, make executes the command regardless of file timestamps
  • There's no actual file called "clean" being created
  • The target exists solely to run the cleanup command

This is called a "phony target": A target that doesn't represent a real file. Other common phony targets include run, test, and install.

Best practice: You can explicitly mark it as phony:

.PHONY: clean
clean:
	rm -f *.o main

This tells make that clean is not a real file, so it should always run the command even if a file named "clean" exists.

Question 9
Dependency Chain

You modify Student.h (adding a new method). Which files need to be recompiled?

Project structure:

  • main.cpp includes Student.h
  • Student.cpp includes Student.h
  • Grade.cpp includes Grade.h (not Student.h)

Answer: main.cpp and Student.cpp need to be recompiled. Grade.cpp does not.

Detailed explanation:

  1. main.cpp recompiled: It includes Student.h, so changes to Student.h affect it. Make will rebuild main.o.
  2. Student.cpp recompiled: It includes Student.h, so changes to Student.h affect it. Make will rebuild Student.o.
  3. Grade.cpp NOT recompiled: It doesn't include Student.h, so changes to Student.h don't affect it. Grade.o remains up to date.
  4. Final step - Relinking: After main.o and Student.o are rebuilt, make will relink all object files (main.o, Student.o, Grade.o) to create the new executable.

Why this matters:

This demonstrates the efficiency of makefiles. If your project has 100 source files and you only modify one header, only the files that include that header get recompiled. Everything else is reused, saving compilation time.

Makefile rules that make this work:

main.o: main.cpp Student.h       # Student.h listed → recompile if it changes
Student.o: Student.cpp Student.h   # Student.h listed → recompile if it changes
Grade.o: Grade.cpp Grade.h         # Student.h NOT listed → skip recompilation
Question 10
Makefile Best Practices

Why is it important to list header file dependencies in makefile rules?

Answer:

Listing header file dependencies is crucial for correctness and consistency. Here's why:

1. Ensures recompilation when headers change:

If you change a class definition in Student.h (e.g., add a method, change a data member), any file that includes Student.h needs to be recompiled to see those changes.

Without the dependency:

main.o: main.cpp
	g++ -c main.cpp

If main.cpp includes Student.h and you modify Student.h, make won't know to recompile main.cpp. Your program will use the old main.o with outdated class definitions, leading to subtle bugs or linker errors.

With the dependency:

main.o: main.cpp Student.h
	g++ -c main.cpp

Now make knows: "If Student.h is newer than main.o, recompile main.cpp."

2. Prevents using stale object files:

Without proper dependencies, you might have object files compiled with old header definitions linked with object files compiled with new header definitions, causing unpredictable behavior.

3. Automatic dependency tracking:

Make uses file timestamps to track what's out of date. By listing headers as dependencies, make can automatically determine the minimal set of files to recompile after any change.

Question 11
Function Signatures

Which of the following is NOT part of a function's signature?

  1. Function name
  2. Number of parameters
  3. Types of parameters
  4. Return type

Answer: D - Return type

Why D is correct:

The function signature consists of:

  • Function name
  • Number of parameters
  • Types of parameters (in order)

The return type is NOT part of the signature. This means you cannot overload functions that differ only in return type.

Example - Invalid overloading:

int getValue();      // Signature: getValue()
double getValue();   // ERROR: Same signature getValue()

The compiler can't distinguish between these because it doesn't know what type you want until after the function is called.

Example - Valid overloading:

int getValue();          // Signature: getValue()
int getValue(int x);     // Signature: getValue(int)
int getValue(double x);  // Signature: getValue(double)

These are all different signatures because they have different parameter lists.

Question 12
Overload Resolution

Given the following overloaded functions:

void display(int x);
void display(double x);
void display(int a, int b);

Which function is called by display(5)?

Answer: void display(int x)

Explanation:

The argument 5 is an int literal. The compiler performs overload resolution:

  1. Look for exact match: display(int) is an exact match for display(5).
  2. Exact match found: Call display(int).

Why not display(double)?

While 5 could be converted to 5.0 and call display(double), the compiler prefers exact matches over conversions. Since display(int) is an exact match, that version is chosen.

Why not display(int, int)?

The call display(5) provides only one argument, but display(int, int) requires two. This overload is not a candidate.

Key principle: The compiler always prefers exact matches over automatic type conversions.

}

Output:

Double: 10

    • Exact match: print(int)

Question 14
Ambiguity

Will the following code compile? If not, why?

void process(int a, double b);
void process(double a, int b);

int main() {
    process(5, 10);
    return 0;
}

Answer: No, it will not compile.

Error: Ambiguous function call

Why it fails:

The call process(5, 10) provides two int arguments. The compiler tries to find the best match:

  • Option 1: process(int, double) - Requires converting second argument (10) from int to double
  • Option 2: process(double, int) - Requires converting first argument (5) from int to double

Both options require exactly one conversion. Neither is "better" than the other. The compiler can't decide, so it gives an ambiguity error.

How to fix:

Solution 1: Explicitly cast one argument:

process(5, 10.0);        // Calls process(int, double)
process(5.0, 10);        // Calls process(double, int)

Solution 2: Rename the functions to make their purpose clearer:

void processIntFirst(int a, double b);
void processDoubleFirst(double a, int b);
Question 15
Overloading Rules

True or False: The following function declarations can coexist in the same program:

double calculate(int x);
int calculate(int x);

Answer: False

Explanation:

These functions cannot coexist because they have identical signatures:

  • Both have the name calculate
  • Both take one parameter of type int
  • Signature: calculate(int)

The only difference is the return type (double vs int), but return type is not part of the signature.

Why this restriction exists:

Consider this code:

calculate(5);

The compiler can't determine which version to call because it doesn't know what type you expect the return value to be. Even in a context like:

int result = calculate(5);

The compiler resolves overloading before considering the assignment target type. At the point of the function call, both versions match equally well.

Error message: "redefinition of 'calculate'" or "conflicting declaration"

Question 16
Type Conversion

Given:

void show(double x);
void show(int a, int b);

Which function is called by show(10)?

Answer: void show(double x)

Explanation:

The call show(10) provides one int argument. The compiler looks for matches:

  1. Check for exact match: There's no show(int) overload.
  2. Check for match with automatic conversion: int can be automatically converted (promoted) to double, so show(double) is a candidate.
  3. Check other candidates: show(int, int) requires two arguments but only one was provided. Not a candidate.
  4. Resolution: Only one candidate exists (show(double)), so the compiler converts 10 to 10.0 and calls show(double).

Key principle: If no exact match exists, the compiler will use automatic type conversions (like int → double) to find a match.

Common conversions used:

  • int → double
  • char → int
  • float → double
Question 17
Function Overloading

Why is function overloading useful?

Answer:

Function overloading provides several benefits:

1. Improved readability:

Instead of having multiple functions with different names:

double averageTwo(double a, double b);
double averageThree(double a, double b, double c);
double averageArray(double arr[], int size);

You can use one intuitive name:

double average(double a, double b);
double average(double a, double b, double c);
double average(double arr[], int size);

The function name communicates what it does, and the compiler picks the right version based on the arguments.

2. Easier to use:

Users don't need to remember multiple function names. They just call average(...) with whatever data they have.

3. Natural interface:

Overloading lets you provide different ways to use the same operation. For example, a print function could accept int, double, string, etc., all with the same name.

4. Works with operators:

Function overloading is the foundation for operator overloading (covered later in the course), which lets you define how operators like +, -, << work with your custom classes.

Question 18
Code Analysis

Will the following code compile successfully?

void calculate(int x, int y);
void calculate(int a, int b);

int main() {
    calculate(5, 10);
    return 0;
}

Answer: No, it will not compile.

Error: Redefinition or conflicting declarations

Why it fails:

Both functions have identical signatures:

  • Name: calculate
  • Parameters: (int, int)
  • Signature: calculate(int, int)

Parameter names don't matter for signatures:

The first function uses parameter names x, y. The second uses a, b. But the compiler only cares about types, not names. Both have the same signature: calculate(int, int).

This is a redefinition, not overloading:

Overloading requires different signatures. These have the same signature, so you're trying to define the same function twice.

Compiler error: Something like "redefinition of 'calculate'" or "function 'calculate' already has a body"

Key principle: Parameter names are for human readability in the function definition. The signature (used for overloading) is based only on parameter types and order.

Question 19
Overload Resolution

What are the three steps the compiler uses for overload resolution?

Answer:

The compiler resolves overloaded function calls in three steps:

Step 1: Look for Exact Match

The compiler first tries to find a function where the parameter types exactly match the argument types.

Example:

void func(int x);
void func(double x);

func(5);    // Exact match with func(int)

Step 2: Try Automatic Type Conversions

If no exact match is found, the compiler tries automatic type conversions (promotions and standard conversions).

Example:

void func(double x);
void func(int a, int b);

func(10);   // No exact match for func(int), converts 10 to 10.0 and calls func(double)

Step 3: Error if Ambiguous

If multiple functions match equally well (requiring the same number of conversions), the compiler gives an ambiguity error.

Example:

void func(int a, double b);
void func(double a, int b);

func(5, 10);   // ERROR: Both require one conversion, equally good matches

Priority: Exact matches are always preferred over conversions. If multiple functions require conversions, they must not be equally good (ambiguity).

Question 20
Find the Bug

The following code has a compilation error. Identify and explain the problem:

#include <iostream>
using namespace std;

int max(int a, int b) {
    return (a > b) ? a : b;
}

double max(int x, int y) {
    return (x > y) ? x : y;
}

int main() {
    cout << max(10, 20) << endl;
    return 0;
}

Bug Location: Lines 4-10 - Both function declarations

What's Wrong: Both max functions have the same signature but different return types.

Why It's Wrong:

Function signatures are determined by:

  • Function name: max (same for both)
  • Parameter types: (int, int) (same for both - parameter names a, b vs x, y don't matter)

Both functions have signature max(int, int). The only difference is the return type (int vs double), but return type is not part of the signature.

Compiler error: "redefinition of 'max'" or "functions that differ only in their return type cannot be overloaded"

How to Fix:

Option 1: Change parameter types:

int max(int a, int b);        // Works with ints
double max(double a, double b); // Works with doubles

Option 2: Use a single function with one return type:

int max(int a, int b) {
    return (a > b) ? a : b;
}

Why the fix works: Now functions have different signatures (max(int, int) vs max(double, double)) or there's no conflict (only one function exists).

Question 21
Default Parameters

Which of the following function declarations is valid?

  1. void func(int a, int b = 5, int c);
  2. void func(int a = 1, int b, int c = 3);
  3. void func(int a, int b = 2, int c = 3);
  4. void func(int a = 1, int b = 2, int c);

Answer: C - void func(int a, int b = 2, int c = 3);

Why C is correct:

Default parameters must be trailing (rightmost) parameters. Once you provide a default for a parameter, all parameters to the right must also have defaults.

In option C:

  • a has no default (OK - it's leftmost)
  • b has default = 2 (OK)
  • c has default = 3 (OK - comes after b which has default)

Why other options are wrong:

  • A: b has a default but c (to its right) doesn't. Invalid - defaults must be trailing.
  • B: a has default, b doesn't, c does. Invalid - b is between two defaulted parameters.
  • D: a and b have defaults but c doesn't. Invalid - once defaults start, they must continue to the end.

Valid patterns:

void f(int a, int b, int c);           // No defaults - OK
void f(int a, int b, int c = 3);       // Last param has default - OK
void f(int a, int b = 2, int c = 3);   // Last 2 params have defaults - OK
void f(int a = 1, int b = 2, int c = 3); // All params have defaults - OK

    cout << length * width * height << endl;
}

    showBox(5);
    showBox(5, 2);
    showBox(5, 2, 3);

Output:

10

Line-by-Line Trace:

  1. Call: showBox(5);
    • Provided: length = 5
    • Defaults used: width = 1, height = 1
    • Calculation: 5 * 1 * 1 = 5
    • Output: 5
  2. Call: showBox(5, 2);

Key insight: You can provide 1, 2, or 3 arguments. The function fills in defaults from right to left for any omitted arguments.

Question 23
Default Parameters

True or False: Default parameter values should be specified in both the function declaration (prototype) and the function definition.

Answer: False

Explanation:

Default parameter values should be specified only in the function declaration (prototype), typically in the header file. They should NOT be repeated in the function definition.

Correct pattern:

// student.h (header file)
void setGrade(int score = 0);   // ✅ Default here

// student.cpp (implementation file)
void setGrade(int score) {      // ✅ NO default here
    // function body
}

Incorrect pattern:

// student.h
void setGrade(int score = 0);

// student.cpp
void setGrade(int score = 0) {  // ❌ ERROR: Redefinition of default
    // function body
}

Why this rule exists:

  • The compiler only needs to see the defaults once (in the declaration) to know how to call the function
  • Repeating defaults in the definition can cause "redefinition" errors
  • Putting defaults in the header file (where declarations usually go) makes them visible to all files that include the header

Special case: If you define the function in the same file where you declare it (no separate .h/.cpp), you can put the default in the declaration or the definition, but not both.

Question 24
Code Analysis

Given the function:

void schedule(string subject, int duration = 60, string location = "Room 101");

Which of the following function calls is valid?

  1. schedule("Math");
  2. schedule("Math", 90);
  3. schedule("Math", "Room 202");
  4. schedule("Math", 90, "Room 202");

Answer: A, B, and D are valid. C is invalid.

Detailed analysis:

A: schedule("Math"); - ✅ Valid

  • Provides: subject = "Math"
  • Uses defaults: duration = 60, location = "Room 101"

B: schedule("Math", 90); - ✅ Valid

  • Provides: subject = "Math", duration = 90
  • Uses default: location = "Room 101"

C: schedule("Math", "Room 202"); - ❌ Invalid

  • This attempts to pass "Math" for subject and "Room 202" for duration
  • Type mismatch: duration expects int, but "Room 202" is a string
  • You cannot skip duration and provide location - arguments fill in from left to right

D: schedule("Math", 90, "Room 202"); - ✅ Valid

  • Provides all arguments: subject = "Math", duration = 90, location = "Room 202"
  • No defaults used

Key principle: You can only omit trailing arguments, not middle ones. To provide location, you must also provide duration.

Question 25
Ambiguity

Will the following code compile? If not, why?

void display(int x);
void display(int x, int y = 10);

int main() {
    display(5);
    return 0;
}

Answer: No, it will not compile.

Error: Ambiguous function call

Why it fails:

The call display(5) could match either function:

  • Option 1: display(int) with argument x = 5
  • Option 2: display(int, int) with arguments x = 5, y = 10 (using default)

Both are equally valid interpretations. The compiler can't decide which you intended, so it gives an ambiguity error.

Why this is a problem:

When you combine function overloading with default parameters, you can accidentally create situations where one call signature matches multiple function declarations. This pattern should be avoided.

How to fix:

Option 1: Remove one of the functions:

// Keep only the version with default parameter
void display(int x, int y = 10);

Option 2: Make the functions more distinct:

void display(int x);
void display(int x, int y);  // Remove default

// Now caller must explicitly provide both arguments for second version
display(5);      // Calls display(int)
display(5, 10);  // Calls display(int, int)

General rule: Be cautious when combining overloading and default parameters. Make sure each possible call has a clear "best match" among the overloads.

Question 26
Integration

You have a multi-file project with overloaded functions. Which files need to be recompiled if you add a new overload to a header file?

Project structure:

  • main.cpp includes Calculator.h
  • Calculator.cpp includes Calculator.h
  • Display.cpp includes Display.h (not Calculator.h)

You add a new overload to Calculator.h.

Answer: main.cpp and Calculator.cpp need to be recompiled. Display.cpp does not.

Detailed explanation:

Files affected by Calculator.h change:

  • main.cpp: Includes Calculator.h, so it sees the new overload declaration. Must be recompiled to main.o.
  • Calculator.cpp: Includes Calculator.h. Must be recompiled to Calculator.o.
  • Display.cpp: Does NOT include Calculator.h, so changes to Calculator.h don't affect it. Display.o remains up to date.

Make's process:

  1. Check main.o: Depends on main.cpp and Calculator.h. Calculator.h changed → rebuild main.o
  2. Check Calculator.o: Depends on Calculator.cpp and Calculator.h. Calculator.h changed → rebuild Calculator.o
  3. Check Display.o: Depends on Display.cpp and Display.h. Neither changed → skip
  4. Relink: main.o or Calculator.o changed → relink all .o files into executable

This demonstrates makefile efficiency: Only files that include the changed header are recompiled, even in large projects with many source files.

Question 27
Code Tracing

What is the output of this program?

#include <iostream>
using namespace std;

void calculate(int x, int y = 5) {
    cout << x + y << " ";
}

void calculate(int x) {
    cout << x * 2 << " ";
}

int main() {
    calculate(10);
    calculate(10, 3);
    return 0;
}

Answer: This code will NOT compile due to ambiguity.

Error: Ambiguous call to overloaded function calculate(10)

Why it fails:

The call calculate(10) in main could match either:

  • Option 1: calculate(int x, int y = 5) with x = 10, y = 5 (using default)
  • Option 2: calculate(int x) with x = 10

Both match equally well. The compiler cannot decide which to call, so it gives an error.

The second call calculate(10, 3) would work:

It can only match calculate(int x, int y = 5) because that's the only overload that takes two arguments.

This is a common mistake:

Combining function overloading with default parameters can create ambiguous situations. This specific pattern (one overload with N parameters, another with N+1 parameters where the extra parameter has a default) should be avoided.

How to fix: Use one of these approaches, not both together:

  • Use only overloading (no defaults)
  • Use only one function with defaults (no overloading for this case)
Question 28
Makefile + Overloading

You have the following files:

  • utils.h declares three overloads: max(int, int), max(double, double), max(int, int, int)
  • utils.cpp defines all three overloads
  • main.cpp calls max(10, 20)

You add a fourth overload max(float, float) to utils.h and utils.cpp, but main.cpp doesn't use it.

When you run make, which files are recompiled?

Answer: Both main.cpp and utils.cpp are recompiled, even though main.cpp doesn't use the new overload.

Detailed explanation:

Why utils.cpp is recompiled:

  • utils.cpp includes utils.h
  • You modified utils.h (added new overload declaration)
  • Makefile rule: utils.o: utils.cpp utils.h
  • utils.h is newer than utils.o → recompile

Why main.cpp is recompiled:

  • main.cpp includes utils.h (to call max functions)
  • You modified utils.h
  • Makefile rule: main.o: main.cpp utils.h
  • utils.h is newer than main.o → recompile

Does it matter that main.cpp doesn't use the new overload?

No. Make doesn't analyze which declarations you actually use. It only checks: "Did a header that this file includes change?" If yes, recompile.

This is actually correct behavior:

Even though main.cpp doesn't call max(float, float), the header changed, and there could be side effects (like macro definitions, type changes, etc.). Make takes the safe approach and recompiles everything that includes the header.

Final step: After recompiling main.o and utils.o, make will relink to create the new executable.

Question 29
Find the Bug

The following code compiles but doesn't behave as expected. Identify the issue:

// math.h
double average(double a, double b);
double average(double a, double b, double c = 0.0);

// math.cpp
double average(double a, double b) {
    return (a + b) / 2.0;
}

double average(double a, double b, double c) {
    return (a + b + c) / 3.0;
}

// main.cpp
#include "math.h"
#include <iostream>
using namespace std;

int main() {
    cout << average(10.0, 20.0) << endl;
    return 0;
}

What's wrong with this design?

Bug: The call average(10.0, 20.0) is ambiguous.

What's Wrong:

The two overloads create an ambiguous situation:

  • average(double, double)
  • average(double, double, double = 0.0)

When you call average(10.0, 20.0), the compiler can't decide:

  • Option 1: Call average(double, double) with a = 10.0, b = 20.0
  • Option 2: Call average(double, double, double) with a = 10.0, b = 20.0, c = 0.0 (using default)

Both match equally well, so the compiler gives an ambiguity error.

Additionally, there's a logic error:

The three-parameter version divides by 3 even when c = 0.0 (the default). So average(10.0, 20.0) would compute (10 + 20 + 0) / 3 = 10, not the correct two-number average of 15.

How to Fix:

Option 1: Remove the two-parameter overload, keep only the one with default:

// math.h
double average(double a, double b, double c = 0.0);

// math.cpp
double average(double a, double b, double c) {
    if (c == 0.0) {
        return (a + b) / 2.0;  // Two values
    } else {
        return (a + b + c) / 3.0;  // Three values
    }
}

Option 2: Keep separate overloads but remove the default:

// math.h
double average(double a, double b);
double average(double a, double b, double c);  // No default

// Implementation stays the same

Now average(10.0, 20.0) unambiguously calls the two-parameter version.

Question 30
Comprehensive

You're working on a grading system project with these files:

  • main.cpp
  • Grade.h, Grade.cpp
  • Student.h, Student.cpp

Grade.h declares overloaded calculate functions:

double calculate(int score);
double calculate(int score, int bonus = 0);

What problems will occur, and how would you fix them?

Problems identified:

Problem 1: Ambiguous overloads

The two function declarations create an ambiguity:

  • calculate(int)
  • calculate(int, int = 0)

A call like calculate(85) could match either function (the first directly, the second using the default). This is a compilation error.

Problem 2: Makefile dependencies

If you later modify Grade.h, the makefile needs to know which files to recompile. Typical dependencies would be:

Grade.o: Grade.cpp Grade.h
Student.o: Student.cpp Student.h
main.o: main.cpp Grade.h Student.h

If Student.cpp also includes Grade.h, the dependency should be:

Student.o: Student.cpp Student.h Grade.h

How to fix the overloading issue:

Solution 1: Use a single function with default parameter:

double calculate(int score, int bonus = 0);

Implementation:

double calculate(int score, int bonus) {
    return (score + bonus) / 100.0;
}

Solution 2: Keep two distinct overloads without default:

double calculate(int score);
double calculate(int score, int bonus);  // Remove default

Now calculate(85) unambiguously calls the first version, and calculate(85, 5) calls the second.

Complete corrected example with makefile:

# Variables
ofiles = main.o Grade.o Student.o
gpp_o = g++ -c -std=c++98

# Link executable
gradeSystem: $(ofiles)
	g++ -std=c++98 $(ofiles) -o gradeSystem

# Compile each source file
main.o: main.cpp Grade.h Student.h
	$(gpp_o) main.cpp

Grade.o: Grade.cpp Grade.h
	$(gpp_o) Grade.cpp

Student.o: Student.cpp Student.h Grade.h
	$(gpp_o) Student.cpp

# Clean up
clean:
	rm -f *.o gradeSystem

With Grade.h containing:

double calculate(int score, int bonus = 0);

This eliminates the ambiguity and ensures proper recompilation when headers change.
