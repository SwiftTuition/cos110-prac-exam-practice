Example 1: Multi-File Grade Tracking System with Makefile

We're building a grade tracking system with three files. We'll create a makefile that handles compilation efficiently, only rebuilding what changed.

Project Structure

gradeTracker/
├── main.cpp
├── Grade.h
├── Grade.cpp
└── Makefile

File 1: Grade.h

// Grade.h - Header file
#ifndef GRADE_H
#define GRADE_H

#include <iostream>
#include <string>
using namespace std;

class Grade {
private:
    string studentName;
    int score;
public:
    Grade();
    Grade(string name, int s);
    void setScore(int s);
    void display();
};

#endif

File 2: Grade.cpp

// Grade.cpp - Implementation file
#include "Grade.h"

Grade::Grade() {
    studentName = "Unknown";
    score = 0;
}

Grade::Grade(string name, int s) {
    studentName = name;
    score = s;
}

void Grade::setScore(int s) {
    score = s;
}

void Grade::display() {
    cout << studentName << ": " << score << "%" << endl;
}

File 3: main.cpp

// main.cpp - Main program
#include "Grade.h"

int main() {
    Grade g1("Thabo Ndlovu", 85);
    Grade g2("Amahle Zuma", 92);
    Grade g3("Brandon Smith", 78);

    cout << "Grade Report:" << endl;
    g1.display();
    g2.display();
    g3.display();

    return 0;
}

File 4: Makefile

# Grade Tracking System Makefile
# Tab characters are used for indentation (not spaces!)

# Variables for reusability
ofiles = main.o Grade.o
gpp_o = g++ -c -std=c++98
gpp = g++ -std=c++98

# Main target: link all object files
gradeTracker: $(ofiles)
	$(gpp) $(ofiles) -o gradeTracker

# Compile main.cpp (depends on main.cpp and Grade.h)
main.o: main.cpp Grade.h
	$(gpp_o) main.cpp

# Compile Grade.cpp (depends on Grade.cpp and Grade.h)
Grade.o: Grade.cpp Grade.h
	$(gpp_o) Grade.cpp

# Run the program
run: gradeTracker
	./gradeTracker

# Clean up compiled files
clean:
	rm -f *.o gradeTracker

Step-by-Step Walkthrough

Step 1: Understanding the Dependencies

Let's trace what depends on what:

  • gradeTracker (executable) depends on main.o and Grade.o
  • main.o depends on main.cpp and Grade.h (because main.cpp includes Grade.h)
  • Grade.o depends on Grade.cpp and Grade.h

Step 2: First Build (make)

When you run make for the first time:

  1. Make sees the first target: gradeTracker
  2. Checks if main.o exists → No, so it builds it:
    • Runs: g++ -c -std=c++98 main.cpp
    • Creates main.o
  3. Checks if Grade.o exists → No, so it builds it:
    • Runs: g++ -c -std=c++98 Grade.cpp
    • Creates Grade.o
  4. All dependencies ready, now links:
    • Runs: g++ -std=c++98 main.o Grade.o -o gradeTracker
    • Creates gradeTracker executable

Step 3: Scenario - Modify Grade.cpp

Suppose you change the display() function in Grade.cpp to add more formatting.

When you run make again:

  1. Make sees Grade.cpp has a newer timestamp than Grade.o
  2. Recompiles only Grade.cpp: g++ -c -std=c++98 Grade.cpp
  3. main.o is still valid (nothing changed in main.cpp or Grade.h)
  4. Relinks: g++ -std=c++98 main.o Grade.o -o gradeTracker

Result: Saved time by not recompiling main.cpp!

Step 4: Scenario - Modify Grade.h

Now suppose you add a new method to Grade.h.

When you run make:

  1. Make sees Grade.h changed
  2. Both main.o and Grade.o depend on Grade.h
  3. Recompiles both:
    • g++ -c -std=c++98 main.cpp
    • g++ -c -std=c++98 Grade.cpp
  4. Relinks everything

Result: Both files were recompiled because they both include the changed header.

Expected Output

When you run make run:

Grade Report:
Thabo Ndlovu: 85%
Amahle Zuma: 92%
Brandon Smith: 78%

Experiments

🔬 Experiment 1: What happens if you forget to add Grade.h to the dependencies for main.o?

What happens: If you change Grade.h (e.g., add a new method), main.cpp won't be recompiled automatically.

Why this is dangerous: Your program might use outdated information. For example, if you add a method to Grade.h and call it in main.cpp, the compiler won't see the new method signature in the old main.o file.

Fix: Always list all headers that a .cpp file includes as dependencies: 

main.o: main.cpp Grade.h
	$(gpp_o) main.cpp

🔬 Experiment 2: What if you add a third class Course but forget to add Course.o to ofiles?

What happens: The makefile will compile Course.cpp into Course.o, but the linker won't include it in the final executable.

Error message: You'll get "undefined reference" errors when linking if main.cpp tries to use Course functions.

Fix: Update the ofiles variable: 

ofiles = main.o Grade.o Course.o

🔬 Experiment 3: Try using spaces instead of tabs before the g++ commands. What error do you get?

Error message: Makefile:XX: *** missing separator. Stop.

Why: Make requires TAB characters before commands. If you use spaces, make doesn't recognize them as command lines.

Fix: Use TAB characters (not spaces) for indentation of all commands in the makefile. Most editors have a setting to insert tabs when you press Tab.

🔬 Experiment 4: What happens if you run make twice in a row without changing any files?

Output: make: 'gradeTracker' is up to date.

Why: Make compares file timestamps. All object files are newer than their source files, and the executable is newer than the object files, so nothing needs rebuilding.

This is the power of makefiles: They only rebuild what changed, saving time on large projects.

Swift Note: The key to makefiles is getting the dependencies right. A good mental model: "If file X changes, which .o files need to be rebuilt?" List those .o files as targets with X as a dependency.

How the Compiler Chooses

Call 1: calculateAverage(85, 90)

Both arguments are int literals.

Matching process:

  • ✅ calculateAverage(int, int) - Exact match
  • ❌ calculateAverage(int, int, int) - Wrong number of parameters
  • ⚠️ calculateAverage(double, double) - Would require converting both ints to doubles
  • ❌ calculateAverage(int[], int) - Wrong types

Winner: Overload 1 (exact match beats conversion)

Call 2: calculateAverage(87.5, 92.3)

Both arguments are double literals.

Matching process:

  • ⚠️ calculateAverage(int, int) - Would require converting doubles to ints (loses precision, not preferred)
  • ✅ calculateAverage(double, double) - Exact match

Winner: Overload 3 (exact match)

Call 3: calculateAverage(quizzes, 5)

First argument is int[] (array), second is int.

Matching process:

  • ❌ All other overloads have wrong types
  • ✅ calculateAverage(int[], int) - Only match

Winner: Overload 4 (only possible match)

Experiments

🔬 Experiment 1: Add a call calculateAverage(85, 90.0). Which overload gets called?

Result: Calls calculateAverage(double, double)

Why: The second argument 90.0 is a double. The compiler converts 85 (int) to 85.0 (double) to match the (double, double) signature. This is preferred over converting 90.0 to 90 (which would lose precision).

🔬 Experiment 2: What if you remove the calculateAverage(double, double) overload and call calculateAverage(87.5, 92.3)?

Result: Calls calculateAverage(int, int)

Why: Without the double overload, the compiler converts both 87.5 and 92.3 to integers (87 and 92) to match the (int, int) signature.

Warning: This loses precision! The result would be based on 87 and 92, not the original values.

🔬 Experiment 3: Try adding another overload: int calculateAverage(int a, int b) (returns int instead of double). What happens?

Result: Compilation error!

Error message: error: ambiguous overload for 'calculateAverage' or redefinition of 'calculateAverage(int, int)'

Why: The signature is determined by the function name and parameter types only. Return type is NOT part of the signature. You can't have two functions with the same name and parameters but different return types.

🔬 Experiment 4: Add an overload for four integers. Test it with calculateAverage(80, 85, 90, 95).

Code to add:

double calculateAverage(int a, int b, int c, int d) {
    cout << "Called: calculateAverage(int, int, int, int)" << endl;
    return (a + b + c + d) / 4.0;
}

Result: When you call calculateAverage(80, 85, 90, 95), this new overload is called because it's the only one with 4 integer parameters.

Pattern: You can create as many overloads as needed, as long as each has a unique signature (different number or types of parameters).

How Default Parameters Work

Call 1: scheduleSession("Naledi Mokoena", "COS 110")

Only 2 arguments provided (student and subject).

Parameters used:

  • student = "Naledi Mokoena" (provided)
  • subject = "COS 110" (provided)
  • duration = 1 (default)
  • rate = 150 (default)
  • location = "Room 101" (default)

Call 2: scheduleSession("Pieter van der Merwe", "WTW 146", 2)

3 arguments provided.

Parameters used:

  • student = "Pieter van der Merwe" (provided)
  • subject = "WTW 146" (provided)
  • duration = 2 (provided)
  • rate = 150 (default)
  • location = "Room 101" (default)

Call 4: scheduleSession("Emma Johnson", "PHY 124", 2, 180, "Room 205")

All 5 arguments provided - no defaults used.

Parameters used: All provided values, no defaults.

Experiments

🔬 Experiment 1: What if you want to use the default rate (R150) but specify a custom location? Can you call scheduleSession("Student", "Subject", 1, "Room 202")?

Result: No, this won't compile!

Error: Type mismatch - the 4th parameter expects an int (rate) but you're passing a string (location).

Why: You can only omit parameters from right to left. To provide location, you MUST also provide duration and rate:

scheduleSession("Student", "Subject", 1, 150, "Room 202");

Lesson: Default parameters are convenient, but you can't skip middle ones.

🔬 Experiment 2: What happens if you move the default parameters to the left: void scheduleSession(string student, int duration = 1, string subject, int rate = 150)?

Result: Compilation error!

Error message: error: default argument missing for parameter 3 of 'void scheduleSession(...)'

Why: Default parameters must be the RIGHTMOST (trailing) parameters. Once you have a default parameter, all parameters to its right must also have defaults.

Valid: void f(int a, int b, int c = 5, int d = 10);

Invalid: void f(int a, int b = 5, int c, int d = 10);

🔬 Experiment 3: What if you put the default values in both the function declaration AND the definition?

Result: Compilation error!

Error message: error: redefinition of default argument

Why: Default values should only appear in the function DECLARATION (usually in the .h file), not in the definition (the .cpp file).

Correct pattern:

// session.h (declaration with defaults)
void scheduleSession(string student, string subject,
                     int duration = 1, int rate = 150);

// session.cpp (definition WITHOUT defaults)
void scheduleSession(string student, string subject,
                     int duration, int rate) {
    // Implementation
}

🔬 Experiment 4: Add another default parameter at the beginning: bool isPremium = false. Does this work?

Result: No, won't compile!

Why: Default parameters must be rightmost. isPremium would need to go AFTER location:

void scheduleSession(string student, string subject,
                     int duration = 1, int rate = 150,
                     string location = "Room 101", bool isPremium = false);

Or you could reorder non-default parameters, but all defaults must still be at the end.

Example 4: Student Management System (Makefiles + Overloading)

This example combines everything: a multi-file project with a makefile, plus overloaded functions for printing student information in different formats.

Project Structure

studentManager/
├── main.cpp
├── Student.h
├── Student.cpp
└── Makefile

File 1: Student.h

// Student.h
#ifndef STUDENT_H
#define STUDENT_H

#include <iostream>
#include <string>
using namespace std;

class Student {
private:
    string name;
    int studentID;
    double gpa;
public:
    Student(string n, int id, double g);

    // Overloaded print functions
    void print();                    // Basic format
    void print(bool showID);         // With or without ID
    void print(string prefix);       // With custom prefix
    void print(bool showID, bool showGPA);  // Detailed control
};

#endif

File 2: Student.cpp

// Student.cpp
#include "Student.h"

Student::Student(string n, int id, double g) {
    name = n;
    studentID = id;
    gpa = g;
}

// Overload 1: Basic format (name only)
void Student::print() {
    cout << name << endl;
}

// Overload 2: With optional ID
void Student::print(bool showID) {
    cout << name;
    if (showID) {
        cout << " (ID: " << studentID << ")";
    }
    cout << endl;
}

// Overload 3: With custom prefix
void Student::print(string prefix) {
    cout << prefix << name << " (GPA: " << gpa << ")" << endl;
}

// Overload 4: Full control
void Student::print(bool showID, bool showGPA) {
    cout << name;
    if (showID) {
        cout << " (ID: " << studentID << ")";
    }
    if (showGPA) {
        cout << " [GPA: " << gpa << "]";
    }
    cout << endl;
}

File 3: main.cpp

// main.cpp
#include "Student.h"

int main() {
    Student s1("Thandi Nkosi", 12345, 3.8);
    Student s2("Johan Botha", 12346, 3.5);
    Student s3("Lerato Dlamini", 12347, 3.9);

    cout << "=== Student Directory ===" << endl << endl;

    cout << "Basic format:" << endl;
    s1.print();
    s2.print();
    s3.print();
    cout << endl;

    cout << "With student IDs:" << endl;
    s1.print(true);
    s2.print(true);
    s3.print(true);
    cout << endl;

    cout << "With custom prefix:" << endl;
    s1.print("Honor Roll: ");
    s2.print("Regular: ");
    s3.print("Honor Roll: ");
    cout << endl;

    cout << "Full details:" << endl;
    s1.print(true, true);
    s2.print(true, true);
    s3.print(true, true);

    return 0;
}

File 4: Makefile

# Student Management System Makefile

# Variables
ofiles = main.o Student.o
gpp_o = g++ -c -std=c++98 -Wall
gpp = g++ -std=c++98 -Wall

# Main executable
studentManager: $(ofiles)
	$(gpp) $(ofiles) -o studentManager

# Compile main.cpp
main.o: main.cpp Student.h
	$(gpp_o) main.cpp

# Compile Student.cpp
Student.o: Student.cpp Student.h
	$(gpp_o) Student.cpp

# Run the program
run: studentManager
	./studentManager

# Clean compiled files
clean:
	rm -f *.o studentManager

# Rebuild from scratch
rebuild: clean studentManager

Basic format:

Johan Botha
Lerato Dlamini

With student IDs:
Thandi Nkosi (ID: 12345)
Johan Botha (ID: 12346)
Lerato Dlamini (ID: 12347)

With custom prefix:
Honor Roll: Thandi Nkosi (GPA: 3.8)
Regular: Johan Botha (GPA: 3.5)
Honor Roll: Lerato Dlamini (GPA: 3.9)

Full details:
Thandi Nkosi (ID: 12345) [GPA: 3.8]
Johan Botha (ID: 12346) [GPA: 3.5]
Lerato Dlamini (ID: 12347) [GPA: 3.9]

How Overloading Works Here

s1.print() - No Arguments

Calls: void Student::print()

Prints just the name with no additional information.

s1.print(true) - One bool Argument

Calls: void Student::print(bool showID)

Prints name with ID because showID = true.

s1.print("Honor Roll: ") - String Argument

Calls: void Student::print(string prefix)

Different type (string vs bool) means different overload.

s1.print(true, true) - Two bool Arguments

Calls: void Student::print(bool showID, bool showGPA)

Different number of parameters (2 vs 1) means different overload.

Experiments

🔬 Experiment 1: What if you add s1.print(false)? Which overload is called and what's printed?

Overload called: void Student::print(bool showID)

Output: Thandi Nkosi (no ID because showID = false)

Why: One bool argument matches the print(bool) signature. The value false means "don't show ID".

🔬 Experiment 2: Add another overload: void print(int format) where format codes control output. Does this create ambiguity with print(bool)?

Result: Yes, creates ambiguity!

Problem: s1.print(0) or s1.print(1) is ambiguous:

  • 0 and 1 can be treated as bool (false/true)
  • 0 and 1 are also valid int values

Fix: Use different function names or different parameter types that don't overlap.

🔬 Experiment 3: In the makefile, what happens if you change Student.h (add a new method) but forget to run make clean first?

What happens: Running make will rebuild both main.o and Student.o automatically.

Why: Both object files list Student.h as a dependency: 

main.o: main.cpp Student.h
Student.o: Student.cpp Student.h

Result: Make detects that Student.h is newer than the .o files and recompiles them. You don't need make clean - the dependencies handle it!

When to use make clean: When you want to force a complete rebuild (e.g., after changing compiler flags or to troubleshoot weird errors).

🔬 Experiment 4: Add the -Wall flag to the compiler commands. What does it do?

What -Wall does: Enables "all warnings" during compilation.

Why use it: Catches potential bugs like:

  • Unused variables
  • Comparisons that are always true/false
  • Missing return statements
  • Type conversion issues

Example warning: If you declare int x; but never use it, the compiler warns you.

Best practice: Always compile with -Wall and fix all warnings before submitting code.

Example 5: Advanced Makefile with Variables and Pattern Rules

This example shows a more sophisticated makefile that scales better for large projects with many source files.

Scenario: Course Management System

Suppose you're building a system with 5 classes: Student, Course, Grade, Instructor, and Department. Writing individual rules for each .o file gets tedious. Let's use pattern rules.

Project Structure

courseManager/
├── main.cpp
├── Student.h / Student.cpp
├── Course.h / Course.cpp
├── Grade.h / Grade.cpp
├── Instructor.h / Instructor.cpp
├── Department.h / Department.cpp
└── Makefile

Advanced Makefile

# Course Management System - Advanced Makefile

# Compiler settings
CXX = g++
CXXFLAGS = -std=c++98 -Wall -Wextra -pedantic
LDFLAGS =

# Source files (automatically find all .cpp files)
SOURCES = main.cpp Student.cpp Course.cpp Grade.cpp Instructor.cpp Department.cpp

# Object files (replace .cpp with .o)
OBJECTS = $(SOURCES:.cpp=.o)

# Executable name
TARGET = courseManager

# Default target: build the executable
all: $(TARGET)

# Link object files into executable
$(TARGET): $(OBJECTS)
	$(CXX) $(LDFLAGS) $(OBJECTS) -o $(TARGET)
	@echo "Build complete: $(TARGET)"

# Pattern rule: how to build any .o file from a .cpp file
%.o: %.cpp %.h
	$(CXX) $(CXXFLAGS) -c $< -o $@
	@echo "Compiled: $<"

# Special case: main.o depends on ALL headers (uses all classes)
main.o: main.cpp Student.h Course.h Grade.h Instructor.h Department.h
	$(CXX) $(CXXFLAGS) -c main.cpp
	@echo "Compiled: main.cpp"

# Run the program
run: $(TARGET)
	@echo "Running $(TARGET)..."
	@./$(TARGET)

# Clean compiled files
clean:
	rm -f $(OBJECTS) $(TARGET)
	@echo "Cleaned all build files"

# Rebuild everything from scratch
rebuild: clean all

# Show variables (for debugging the makefile)
debug:
	@echo "Sources: $(SOURCES)"
	@echo "Objects: $(OBJECTS)"
	@echo "Target: $(TARGET)"

# Declare phony targets (not actual files)
.PHONY: all run clean rebuild debug

What's New in This Makefile

1. Variables for Everything

  • CXX = g++ - Compiler command
  • CXXFLAGS = -std=c++98 -Wall -Wextra -pedantic - Compiler flags
  • SOURCES = ... - List of all source files
  • OBJECTS = $(SOURCES:.cpp=.o) - Auto-generate object file list

Benefit: To add a new class, just add its .cpp to SOURCES. Everything else updates automatically.

2. Pattern Rule (%.o: %.cpp %.h)

This single rule replaces 5 individual rules:

%.o: %.cpp %.h
	$(CXX) $(CXXFLAGS) -c $< -o $@

How it works:

  • % is a wildcard (matches any filename)
  • $< = first dependency (the .cpp file)
  • $@ = target name (the .o file)

So Student.o depends on Student.cpp and Student.h, and is compiled with the pattern rule.

3. Automatic Dependency Generation

OBJECTS = $(SOURCES:.cpp=.o) transforms the list:

  • Input: main.cpp Student.cpp Course.cpp ...
  • Output: main.o Student.o Course.o ...

4. Phony Targets

.PHONY: all run clean rebuild debug

Tells make these are command names, not files. Without this, if you had a file named "clean", make clean wouldn't work.

5. Silent Commands (@echo)

@echo "Build complete" - The @ prevents make from printing the command itself, only the output.

Without @: Shows echo "Build complete" then Build complete

With @: Shows only Build complete

Experiments

🔬 Experiment 1: Add a new class Schedule (Schedule.h and Schedule.cpp). What do you need to change in the makefile?

Changes needed: Just one line!

SOURCES = main.cpp Student.cpp Course.cpp Grade.cpp Instructor.cpp Department.cpp Schedule.cpp

Why so easy:

  • OBJECTS auto-updates to include Schedule.o
  • Pattern rule %.o: %.cpp %.h handles compiling Schedule.cpp
  • Main target $(TARGET): $(OBJECTS) automatically links the new .o file

If main.cpp uses Schedule: Also add Schedule.h to main.o dependencies.

🔬 Experiment 2: What does make debug show? Why is this useful?

Output:

Sources: main.cpp Student.cpp Course.cpp Grade.cpp Instructor.cpp Department.cpp
Objects: main.o Student.o Course.o Grade.o Instructor.o Department.o
Target: courseManager

Why useful: Helps debug the makefile itself. If you're not sure what files will be compiled or linked, make debug shows you the variable values without actually building anything.

🔬 Experiment 3: What's the difference between make clean and make rebuild?

make clean: Removes all .o files and the executable. Leaves you with just source files.

make rebuild: Runs clean then all, giving you a fresh build.

rebuild: clean all

When to use rebuild: When you've changed compiler flags, switched branches in git, or something seems broken but shouldn't be.

🔬 Experiment 4: The pattern rule assumes every .cpp has a matching .h. What if you add a utility file utils.cpp with no header?

Problem: The pattern rule %.o: %.cpp %.h would look for utils.h and fail if it doesn't exist.

Solution 1: Add a specific rule for utils.o: 

utils.o: utils.cpp
	$(CXX) $(CXXFLAGS) -c utils.cpp

Solution 2: Use a more flexible pattern rule: 

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@
Then manually add header dependencies for files that have them.

Swift Note: Advanced makefiles like this one are overkill for small projects, but they scale beautifully. Once set up, adding new files is trivial. Professional C++ projects use even more sophisticated build systems (CMake, Bazel), but understanding makefiles is foundational.
