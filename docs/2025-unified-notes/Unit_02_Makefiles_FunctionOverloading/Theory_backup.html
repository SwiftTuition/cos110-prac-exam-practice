1. How Compilation Works

Before we talk about makefiles, let's refresh how C++ code becomes an executable program.

The Three-Step Process

Turning your C++ code into a runnable program happens in three stages:

STEP 1: PREPROCESSING
    main.cpp ──────> (Preprocessor) ──────> Expanded source
    ↑                                           |
    │                                           |
    Includes headers (#include)                 |
                                                v
STEP 2: COMPILATION
    Expanded source ──────> (Compiler) ──────> main.o
    Student.cpp ──────> (Compiler) ──────> Student.o
    Course.cpp  ──────> (Compiler) ──────> Course.o
                                                |
                                                |
STEP 3: LINKING                                 v
    main.o + Student.o + Course.o ──────> (Linker) ──────> executable
  1. Preprocessing: The preprocessor handles #include directives, copying header file contents into your source files.
  2. Compilation: Each .cpp file is compiled separately into an object file (.o or .obj). Object files contain machine code but aren't complete programs yet.
  3. Linking: The linker combines all object files into one executable, resolving function calls between files.

Why This Matters

When you have multiple source files, you don't need to recompile every file when you make a small change. If you only modify Student.cpp, you can recompile just that file and relink. This saves time on large projects.

Makefiles automate this "only recompile what changed" process.

💡 Swift Quiz
Quick Check: If you change a function's implementation in Student.cpp but don't change Student.h, which files need to be recompiled?
Answer: Only Student.cpp needs to be recompiled (producing a new Student.o). Files that include Student.h don't need recompilation because the header (the interface) didn't change. After recompiling Student.cpp, you need to relink all object files to produce the final executable.

2. Makefiles: Automating Compilation

A makefile is a special file that tells the make program how to compile your project. It tracks dependencies between files so you only recompile what's necessary.

Basic Makefile Structure

Makefiles consist of rules. Each rule has three parts: 

target: dependencies
	command
  • Target: What you want to create (usually a .o file or an executable)
  • Dependencies: Files that the target depends on
  • Command: The shell command to create the target (MUST be indented with a TAB, not spaces!)
Important: Makefile commands must be indented with a TAB character, not spaces. If you use spaces, make will give you an error like "missing separator". This is one of the most common makefile mistakes.

Simple Example

Here's a makefile for a program with one source file: 

# Compile and link main.cpp into executable called "main"
main: main.cpp
	g++ -std=c++98 main.cpp -o main

# Run the program
run: main
	./main

# Clean up compiled files
clean:
	rm -f main

How it works:

  • main is the target (the executable we want to create)
  • main.cpp is the dependency (if main.cpp changes, we need to rebuild)
  • g++ -std=c++98 main.cpp -o main is the command to compile and link
  • run depends on main (build it first, then run it)
  • clean has no dependencies - it's a manual cleanup command
Note: To use a makefile, type make in your terminal. By default, it builds the first target in the file. You can build specific targets with make target_name (e.g., make clean).
💡 Swift Quiz
Quick Check: Why does the run target depend on main?
Answer: The run target executes ./main, which requires the main executable to exist. By listing main as a dependency, we ensure that if main doesn't exist or is out of date, make will build it before trying to run it.

3. Makefiles for Multi-File Projects

Real projects have multiple source files. Here's where makefiles shine: they track which files changed and only recompile those.

Separate Compilation Strategy

Instead of compiling everything in one command, we:

  1. Compile each .cpp file into a .o object file separately
  2. Link all .o files together into the final executable

Here's a makefile for a project with three files: main.cpp, Student.cpp, and Student.h: 

# Variables for reusability
ofiles = main.o Student.o
gpp_o = g++ -c -std=c++98

# Main target: link all .o files
main: $(ofiles)
	g++ -std=c++98 $(ofiles) -o main

# Compile main.cpp (depends on main.cpp and Student.h)
main.o: main.cpp Student.h
	$(gpp_o) main.cpp

# Compile Student.cpp (depends on Student.cpp and Student.h)
Student.o: Student.cpp Student.h
	$(gpp_o) Student.cpp

# Run the program
run: main
	./main

# Clean up
clean:
	rm -f *.o main

Understanding Variables

We use variables to avoid repetition:

  • ofiles = main.o Student.o defines a variable called ofiles
  • $(ofiles) uses the variable (expands to main.o Student.o)
  • gpp_o = g++ -c -std=c++98 stores the compile command (-c means "compile only, don't link")

Dependencies Explained

Why does main.o depend on Student.h?

If main.cpp has #include "Student.h", then changing Student.h (e.g., adding a new method) means main.cpp needs to be recompiled to see the changes. 

Dependency Chain:

main.o  depends on:  main.cpp, Student.h
    ↑
    If Student.h changes → main.o is out of date → recompile main.cpp

Student.o  depends on:  Student.cpp, Student.h
    ↑
    If Student.h changes → Student.o is out of date → recompile Student.cpp

main  depends on:  main.o, Student.o
    ↑
    If any .o file changes → main is out of date → relink
Swift Note: The tricky part of makefiles is getting the dependencies right. A good rule: list the .cpp file, plus all headers that file includes (directly or indirectly). If you forget a header dependency, your program might compile but use outdated code.
Static Example: Makefile Walkthrough

Below is a complete makefile for a simple grade tracking system. Read through it and understand what each part does. 

# Grade Tracking System Makefile
# Files: main.cpp, Grade.h, Grade.cpp

# Variables
ofiles = main.o Grade.o
gpp_o = g++ -c -std=c++98

# Link object files into executable
gradeTracker: $(ofiles)
	g++ -std=c++98 $(ofiles) -o gradeTracker

# Compile main.cpp
# Depends on: main.cpp (source) and Grade.h (because main.cpp includes it)
main.o: main.cpp Grade.h
	$(gpp_o) main.cpp

# Compile Grade.cpp
# Depends on: Grade.cpp (source) and Grade.h (its own header)
Grade.o: Grade.cpp Grade.h
	$(gpp_o) Grade.cpp

# Run the program (depends on gradeTracker being built first)
run: gradeTracker
	./gradeTracker

# Remove compiled files
clean:
	rm -f *.o gradeTracker
What happens when you type make?
  1. Make reads the first target (gradeTracker)
  2. Sees it depends on main.o and Grade.o
  3. Checks if main.o exists and is up to date:
    • If not, runs g++ -c -std=c++98 main.cpp
  4. Checks if Grade.o exists and is up to date:
    • If not, runs g++ -c -std=c++98 Grade.cpp
  5. Links object files: g++ -std=c++98 main.o Grade.o -o gradeTracker
Common Mistake: Forgetting to add a new .o file to the ofiles variable. If you add Course.cpp to your project, you must:
  1. Add Course.o to ofiles: ofiles = main.o Grade.o Course.o
  2. Add a rule to compile Course.cpp: 
    Course.o: Course.cpp Course.h
	$(gpp_o) Course.cpp
If you forget step 1, you'll get "undefined reference" errors during linking.
💡 Swift Quiz
Quick Check: Suppose main.cpp includes Grade.h, and Grade.h includes iostream. Do you need to list iostream in the dependencies for main.o?
Answer: No. You only list headers you wrote (like Grade.h). Standard library headers like iostream don't change, so you don't track them as dependencies. The rule: list your project's .h files that the .cpp file includes, not system headers.

4. Function Overloading

Function overloading lets you define multiple functions with the same name, as long as they have different parameter lists.

Why Overload Functions?

Suppose you want a function to calculate the average of numbers. You might need versions for 2 numbers, 3 numbers, or even an array. Without overloading, you'd need different names: 

double averageTwo(double a, double b);
double averageThree(double a, double b, double c);
double averageArray(double arr[], int size);

This works, but it's clunky. With overloading, you can use one name: 

double average(double a, double b);
double average(double a, double b, double c);
double average(double arr[], int size);

Now the function name tells you what it does, and the compiler figures out which version to call based on the arguments you pass.

Function Signatures

The function signature is what makes overloaded functions unique. It consists of:

  • The function name
  • The number of parameters
  • The types of parameters (in order)
Important: The return type is NOT part of the signature. You cannot overload functions that differ only in return type.
Function Signature Valid Overload?
double max(int a, int b) max(int, int) -
double max(double a, double b) max(double, double) ✅ Yes - different parameter types
int max(int a, int b) max(int, int) ❌ No - same signature as first version
double max(int a, int b, int c) max(int, int, int) ✅ Yes - different number of parameters

5. How the Compiler Picks the Right Overload

When you call an overloaded function, the compiler uses overload resolution to decide which version to call. It follows these steps:

Resolution Steps

  1. Exact Match: Try to find a version with parameters that exactly match the argument types.
  2. Match with Promotion: Try automatic type promotions (e.g., int to double).
  3. Error if Ambiguous: If multiple functions match equally well, the compiler gives an error.

Example: Exact Match

void print(int x);
void print(double x);

print(5);      // Calls print(int) - exact match
print(3.14);   // Calls print(double) - exact match

Example: Automatic Conversion

void show(double x);
void show(int a, int b);

show(10);      // Calls show(double) - int converts to double
show(5, 7);    // Calls show(int, int) - exact match

In the first call, 10 is an int. There's no show(int), so the compiler converts 10 to 10.0 and calls show(double).

Example: Ambiguity Error

void process(int a, double b);
void process(double a, int b);

process(5, 10);    // ERROR: Ambiguous!

Both 5 and 10 are integers. To call the first version, the compiler would convert 10 to double. To call the second version, it would convert 5 to double. Both require one conversion, so neither is "better". This is an ambiguous call, and the compiler gives an error.

Swift Note: Ambiguity errors can be frustrating because both overloads seem valid. The fix is to either rename one function or explicitly cast your arguments: process(5, 10.0) would call the first version.
💡 Swift Quiz
Quick Check: Given void calc(int x) and void calc(double x), which version does calc(5) call?
Answer: calc(int x). The argument 5 is an int, so there's an exact match with calc(int). Even though 5 could be converted to 5.0 and call calc(double), the compiler prefers exact matches over conversions.

6. Default Parameters

Default parameters let you specify default values for function parameters. If the caller doesn't provide those arguments, the defaults are used.

Basic Syntax

// Prototype (with defaults)
void showVolume(int length, int width = 1, int height = 1);

// Definition (NO defaults repeated)
void showVolume(int length, int width, int height) {
    cout << "Volume: " << length * width * height << endl;
}

// Usage
showVolume(10);         // Uses width=1, height=1 → Volume: 10
showVolume(10, 5);      // Uses height=1 → Volume: 50
showVolume(10, 5, 2);   // Uses all provided → Volume: 100

Rules for Default Parameters

  1. Rightmost parameters only: Default parameters must be the trailing parameters. You can't skip middle parameters.
  2. Declare defaults in prototype: Put defaults in the function declaration (usually in the .h file), NOT in the definition.
  3. Omit from right to left: When calling, you can only omit arguments from right to left.
Function Declaration Valid? Reason
void f(int a, int b = 5); ✅ Valid Default is rightmost
void f(int a = 1, int b); ❌ Invalid Default not rightmost
void f(int a, int b = 2, int c = 3); ✅ Valid All defaults are trailing
void f(int a = 1, int b, int c = 3); ❌ Invalid b has no default but comes after a
Common Mistake: Repeating default values in both prototype and definition. 
// grade.h
void setGrade(int score = 0);  // ✅ Defaults here

// grade.cpp
void setGrade(int score = 0) { ... }  // ❌ DON'T repeat!
This causes a redefinition error. Defaults belong only in the declaration.

Answer: No, it's invalid. You can only omit trailing parameters from right to left. To use a custom location, you must also provide the duration: schedule("Math", 60, "Room 202"). You can't skip duration and provide location.

7. Overloading with Default Parameters

You can combine function overloading and default parameters, but be careful about ambiguity.

Safe Combination

// Two clearly distinct overloads
void print(int x);
void print(string s, int width = 10);

print(42);             // Calls print(int)
print("Hello");        // Calls print(string, int) with width=10
print("Hello", 20);    // Calls print(string, int) with width=20

This works because print(42) has an exact match with print(int), and print("Hello") can only match print(string, int).

Dangerous Combination (Ambiguity)

void display(int x);
void display(int x, int y = 10);

display(5);    // ERROR: Ambiguous!

display(5) could call either version:

  • display(int) with argument 5
  • display(int, int) with arguments 5, 10 (using default for second parameter)

The compiler can't decide, so it gives an error. Avoid this pattern.

Swift Note: When combining overloading and defaults, make sure each function call has a clear "best match". If two overloads could match equally well (one using defaults, one not), you'll get an ambiguity error.

8. Common Mistakes

Makefile Mistakes

1. Spaces Instead of Tabs

# ❌ WRONG - Using spaces for indentation
main: main.cpp
    g++ -std=c++98 main.cpp -o main    # This looks fine but uses spaces!

# ✅ CORRECT - Using tab for indentation
main: main.cpp
	g++ -std=c++98 main.cpp -o main    # TAB character before command

Most text editors can be configured to "insert tabs" instead of spaces. In VS Code, check the bottom-right corner for "Spaces" or "Tab Size" and switch to tabs when editing makefiles.

2. Missing Dependencies

# ❌ WRONG - Student.o missing Grade.h dependency
# If Student.cpp includes Grade.h, changes to Grade.h won't trigger recompilation
Student.o: Student.cpp Student.h
	$(gpp_o) Student.cpp

# ✅ CORRECT - Include all headers that Student.cpp uses
Student.o: Student.cpp Student.h Grade.h
	$(gpp_o) Student.cpp

3. Forgetting to Update ofiles Variable

# ❌ WRONG - Added Teacher.cpp but forgot to update ofiles
ofiles = main.o Student.o
# Teacher.o is never linked!

main: $(ofiles)
	g++ -std=c++98 $(ofiles) -o main

Teacher.o: Teacher.cpp Teacher.h
	$(gpp_o) Teacher.cpp

# ✅ CORRECT - Teacher.o included in ofiles
ofiles = main.o Student.o Teacher.o

main: $(ofiles)
	g++ -std=c++98 $(ofiles) -o main

Function Overloading Mistakes

4. Overloading on Return Type Only

// ❌ WRONG - Same signature, different return type
int calculate(double x);
double calculate(double x);  // ERROR: Signature is calculate(double)

// ✅ CORRECT - Different parameter types
int calculate(int x);
double calculate(double x);  // OK: Different signatures

5. Creating Ambiguous Overloads

// ❌ WRONG - Ambiguous calls possible
void process(int a, double b);
void process(double a, int b);

int main() {
    process(5, 10);    // ERROR: Both require 1 conversion
    process(5.0, 10.0);  // ERROR: Both require 1 conversion
}

// ✅ CORRECT - Make signatures more distinct
void processIntFirst(int a, double b);
void processDoubleFirst(double a, int b);
// Or use different names entirely

Default Parameter Mistakes

6. Defaults Not Rightmost

// ❌ WRONG - Default in middle
void schedule(string subject, int duration = 60, string room);  // ERROR

// ✅ CORRECT - All defaults are trailing
void schedule(string subject, string room, int duration = 60);

7. Repeating Defaults in Definition

// schedule.h
void schedule(string subject, int duration = 60);

// schedule.cpp
// ❌ WRONG - Repeating default
void schedule(string subject, int duration = 60) { ... }

// ✅ CORRECT - No defaults in definition
void schedule(string subject, int duration) { ... }

8. Trying to Skip Middle Arguments

void createAccount(string name, double balance = 0.0, string type = "savings");

// ❌ WRONG - Can't skip balance and provide type
createAccount("Alice", "checking");  // ERROR: Wrong types

// ✅ CORRECT - Must provide all arguments up to the one you want
createAccount("Alice", 0.0, "checking");

Summary

In this unit, you learned two important skills for working with multi-file C++ projects:

Makefiles

  • Makefiles automate compilation by tracking file dependencies
  • Rules consist of: target: dependencies followed by tab-indented commands
  • Use variables (ofiles, gpp_o) for reusability
  • Each .o file depends on its .cpp source and all headers it includes
  • The main executable depends on all .o files
  • Common mistakes: spaces instead of tabs, missing dependencies, forgetting to add new files to ofiles

Function Overloading

  • Function overloading lets you use the same name for functions with different parameter lists
  • The signature (name + parameter types) must be unique
  • The compiler uses overload resolution: exact match → automatic conversion → ambiguity error
  • Return type is NOT part of the signature
  • Watch for ambiguity when multiple overloads could match equally well

Default Parameters

  • Default parameters provide default values for trailing function parameters
  • Defaults must be rightmost in the parameter list
  • Declare defaults in the prototype (header file), not the definition
  • You can only omit arguments from right to left when calling
  • Be careful combining overloading and defaults - can create ambiguity
